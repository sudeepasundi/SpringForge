## Why it matters

Most SQL you will write is a `SELECT` with a `WHERE`. Getting it exactly right — the right columns,
the right rows, the right precedence of `AND` and `OR` — is the difference between a correct report and
one that is quietly wrong.

## How it works

### Choosing columns

<SqlPlayground
  dataset="shop"
  query={`SELECT name,
       price,
       price * 1.18 AS price_with_tax,   -- an expression, with an alias
       'in stock' AS note                -- a constant
FROM product;`}
/>

- `SELECT *` returns every column. Handy for exploring; avoid it in application code (Part 5 explains why).
- `AS` gives a column an **alias**. Quote aliases with spaces: `AS "Unit price"`.
- `SELECT DISTINCT city FROM customer` removes duplicate rows from the result.

<SqlPlayground
  dataset="shop"
  title="IN, BETWEEN and LIKE"
  query={`SELECT name, city, country, signed_up_on
FROM customer
WHERE country IN ('India', 'UK')
  AND signed_up_on BETWEEN '2026-01-01' AND '2026-06-30'
  AND name LIKE '%a%';`}
/>

Dates here are stored as ISO-8601 text (`2026-01-01`), which sorts and compares correctly as text.
MySQL and PostgreSQL have real `DATE` and `TIMESTAMP` types.

<Callout type="pitfall" title="Case sensitivity differs">
SQLite's `LIKE` is case-insensitive for ASCII letters; PostgreSQL's `LIKE` is case-sensitive (use
`ILIKE`); MySQL depends on the column's collation (usually insensitive). `=` on text is
case-sensitive in SQLite and PostgreSQL. When it matters, compare `LOWER(email) = LOWER(?)`.
</Callout>

### AND binds tighter than OR

<Compare>
  <Bad title="Missing parentheses">

```sql
-- Intended: cheap items in Books OR Audio
SELECT name FROM product
WHERE category_id = 4 OR category_id = 6 AND price < 60;
-- Actually:  category_id = 4 OR (category_id = 6 AND price < 60)
```

Every Programming book comes back, whatever its price.

  </Bad>
  <Good title="Say what you mean">

```sql
SELECT name FROM product
WHERE (category_id = 4 OR category_id = 6)
  AND price < 60;
-- or: WHERE category_id IN (4, 6) AND price < 60
```

  </Good>
</Compare>

## Common mistakes

- Using `=` with a list — write `IN (…)`.
- Forgetting the `%` in `LIKE` patterns: `LIKE 'Java'` is the same as `= 'Java'`.
- Comparing dates stored as text in another format (`05/01/2026`) — they do not sort as dates.
- Double quotes for strings: standard SQL uses **single quotes** for text and double quotes for names.
