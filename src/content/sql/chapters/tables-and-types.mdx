## Why it matters

A column's type is a decision you live with for years. Money stored as floating point loses cents;
timestamps without a time zone drift; `VARCHAR(20)` for names rejects real people. And every change to a
table in production is a migration that must not lock it for an hour.

<SqlPlayground
  dataset="shop"
  title="Why not floating point for money"
  query={`SELECT 0.1 + 0.2              AS float_sum,
       0.1 + 0.2 = 0.3        AS equals_point_three,
       ROUND(0.1 + 0.2, 2)    AS rounded;`}
/>

<Callout type="note" title="SQLite's flexible typing">
SQLite stores each value with its own type; a column's declared type is only an **affinity**. `NUMERIC`
columns here hold floats, which is why these chapters round money. Add `STRICT` to a table
(`CREATE TABLE t (…) STRICT`) for real type checking. MySQL and PostgreSQL enforce types strictly
(MySQL in its default strict mode).
</Callout>

Identities are not gap-free: rolled-back inserts and server restarts skip numbers. Never rely on ids
being consecutive.

### Generated columns

A column computed from others, kept in sync by the database:

<SqlPlayground
  dataset="shop"
  query={`CREATE TABLE line (
  quantity   INTEGER NOT NULL,
  unit_price NUMERIC NOT NULL,
  total      NUMERIC GENERATED ALWAYS AS (quantity * unit_price) STORED
);

INSERT INTO line (quantity, unit_price) VALUES (3, 9.99), (1, 45.00);
SELECT * FROM line;`}
/>

Supported by SQLite, MySQL 5.7+ and PostgreSQL 12+ (stored only in PostgreSQL before 18).

### ALTER TABLE

<SqlPlayground
  dataset="shop"
  query={`ALTER TABLE customer ADD COLUMN phone TEXT;
ALTER TABLE customer RENAME COLUMN city TO town;

SELECT id, name, town, phone FROM customer LIMIT 3;`}
/>

SQLite supports adding, renaming and dropping columns but not changing a column's type or constraints;
for those it needs the rebuild-and-copy recipe. MySQL and PostgreSQL support `ALTER COLUMN`/`MODIFY`.

<Callout type="prod" title="ALTER TABLE on a big production table">
Some alterations rewrite the whole table and lock it. Adding a nullable column is instant in modern
MySQL and PostgreSQL; adding a `NOT NULL` column with a default, changing a type, or adding an index
may not be. Use online tools (`CREATE INDEX CONCURRENTLY` in PostgreSQL, `ALGORITHM=INPLACE` in MySQL,
gh-ost/pt-online-schema-change) and the expand–migrate–contract pattern. Run changes as versioned
migrations ([Flyway](/learn/data/migrations)).
</Callout>

### DROP

`DROP TABLE IF EXISTS coupon;` removes the table and its data. There is no undo outside a transaction
(PostgreSQL) or a backup.

## Exercises

<SqlExercise
  dataset="shop"
  prompt="Create a table wishlist with columns customer_id (INTEGER, NOT NULL), product_id (INTEGER, NOT NULL) and added_on (TEXT, default CURRENT_DATE), with (customer_id, product_id) as the primary key. Insert customer 1 with product 10, then select customer_id and product_id."
  solution={`CREATE TABLE wishlist (
  customer_id INTEGER NOT NULL,
  product_id  INTEGER NOT NULL,
  added_on    TEXT DEFAULT CURRENT_DATE,
  PRIMARY KEY (customer_id, product_id)
);

SELECT customer_id, product_id FROM wishlist;`}
