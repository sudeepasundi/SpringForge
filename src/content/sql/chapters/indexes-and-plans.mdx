## Why it matters

The same query can take 2 milliseconds or 20 seconds depending on whether the database can use an
index. Most production database problems are a missing index, an index the query cannot use, or a query
that reads far more than it needs. The **query plan** tells you which — and you can watch it change
right here.

## How it works

### What an index is

An index is a separate, sorted structure (a **B-tree**) over one or more columns, pointing back at the
table's rows. Finding a value in it takes a few steps instead of reading every row. The
[Fundamentals chapter on indexes](/fundamentals/databases-and-indexes) explains the structure.

### Reading a plan in SQLite

`EXPLAIN QUERY PLAN` shows what SQLite will do:

<SqlPlayground
  dataset="shop"
  title="Before: a full scan"
  query={`EXPLAIN QUERY PLAN
SELECT id, ordered_at FROM orders WHERE customer_id = 2;`}
/>

`SCAN orders` means every row is read. Add an index and look again:

<SqlPlayground
  dataset="shop"
  title="After: an index search"
  query={`CREATE INDEX ix_orders_customer ON orders (customer_id);

EXPLAIN QUERY PLAN
SELECT id, ordered_at FROM orders WHERE customer_id = 2;`}
/>

`SEARCH orders USING INDEX ix_orders_customer (customer_id=?)` — the database jumps straight to the
matching rows. With 28 orders it makes no visible difference; with 28 million it is the difference
between milliseconds and minutes.

### Composite indexes and column order

An index on `(customer_id, ordered_at)` is sorted by customer, then by date within each customer. It
serves filters on the **leading** column(s), and can also deliver rows already sorted:

<SqlPlayground
  dataset="shop"
  query={`CREATE INDEX ix_orders_customer_date ON orders (customer_id, ordered_at);

EXPLAIN QUERY PLAN
SELECT id FROM orders WHERE customer_id = 2 ORDER BY ordered_at DESC;   -- uses it, no sort step

EXPLAIN QUERY PLAN
SELECT id FROM orders WHERE ordered_at >= '2026-06-01';                 -- leading column missing: scan`}
/>

The second plan says `SCAN orders USING COVERING INDEX …`: `SCAN` still means every entry is read — it
just reads the (smaller) index instead of the table. Only `SEARCH` means the index narrowed the rows.

Rule of thumb for column order: columns compared with `=` first, then the range or sort column.

### Covering indexes

If the index contains every column the query needs, the table is never touched:

<SqlPlayground
  dataset="shop"
  query={`CREATE INDEX ix_orders_status_cover ON orders (status, customer_id);

EXPLAIN QUERY PLAN
SELECT customer_id FROM orders WHERE status = 'PENDING';`}
/>

`USING COVERING INDEX` — the answer comes from the index alone. PostgreSQL's `INCLUDE (…)` adds
non-key columns to an index for exactly this.

### Plans in MySQL and PostgreSQL

```sql
-- PostgreSQL: ANALYZE actually runs the query and reports real timings
EXPLAIN (ANALYZE, BUFFERS) SELECT … ;
--   Seq Scan on orders            ← full scan
--   Index Scan using ix_… on …    ← index lookup, then table
--   Index Only Scan using …       ← covering
--   rows=… (estimated) vs actual rows=…  ← big gaps mean stale statistics: run ANALYZE

-- MySQL
EXPLAIN ANALYZE SELECT … ;          -- 8.0.18+
EXPLAIN SELECT … ;
--   type: ALL            ← full scan
--   type: ref / range    ← index used
--   Extra: Using index   ← covering;  Using filesort ← an extra sort step
```

### The cost of indexes

Every index slows `INSERT`, `UPDATE` and `DELETE` (each index must be updated) and uses disk and
memory. Index what your real queries filter, join and sort on; drop indexes nothing uses (PostgreSQL's
`pg_stat_user_indexes`, MySQL's `sys.schema_unused_indexes`).

## In a Spring and Java app

- Log slow queries (`slow_query_log` in MySQL, `log_min_duration_statement` in PostgreSQL) and read
  their plans.
- Index creation belongs in migrations ([Flyway](/learn/data/migrations)); see also
  [Performance Tuning](/learn/production/performance-tuning).
