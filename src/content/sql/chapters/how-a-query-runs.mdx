## Why it matters

"Why can't I use my column alias in `WHERE`?" "Why does `HAVING` exist when we already have `WHERE`?"
"Why is this column 'not in GROUP BY'?" All three have the same answer: a `SELECT` is **written** in one
order but **evaluated** in another. Once you know that order, SQL errors start making sense.

## How it works

### Written order versus logical order

```sql
SELECT   c.country, COUNT(*) AS customers      -- 5
FROM     customer c                             -- 1
WHERE    c.signed_up_on >= '2026-01-01'         -- 2
GROUP BY c.country                              -- 3
HAVING   COUNT(*) > 1                           -- 4
ORDER BY customers DESC                         -- 6
LIMIT    3;                                     -- 7
```

This is the **logical** order — the meaning of the query. The planner may physically do things
differently (use an index, filter earlier), but the result must be as if it followed these steps.

### What the order explains

**Aliases are not visible in WHERE**, because `SELECT` (step 5) runs after `WHERE` (step 2):

<SqlPlayground
  dataset="shop"
  title="Not portable"
  query={`-- Standard SQL rejects this (PostgreSQL: column "line_total" does not exist)
SELECT order_id, quantity * unit_price AS line_total
FROM order_item
WHERE line_total > 100;`}
/>

SQLite happens to accept that query as an extension, so this runner shows no error — MySQL and
PostgreSQL both reject it. Write the portable form: repeat the expression, or use a subquery or CTE.

<SqlPlayground
  dataset="shop"
  query={`SELECT order_id, quantity * unit_price AS line_total
FROM order_item
WHERE quantity * unit_price > 100;`}
/>

**Aliases are visible in ORDER BY**, because it runs after `SELECT`:

<SqlPlayground
  dataset="shop"
  query={`SELECT order_id, quantity * unit_price AS line_total
FROM order_item
ORDER BY line_total DESC
LIMIT 5;`}
/>

**Aggregates cannot appear in WHERE**, because groups do not exist yet at step 2. Filtering on an
aggregate is exactly what `HAVING` (step 4) is for.

**Every selected column must be grouped or aggregated**: after `GROUP BY country`, each output row is a
whole group, so `SELECT name` would be ambiguous — which customer's name? PostgreSQL rejects it; MySQL
rejects it with `ONLY_FULL_GROUP_BY` (the default since 5.7); SQLite picks an arbitrary row.

<Callout type="pitfall" title="SQLite is forgiving — your production database is not">
SQLite accepts some non-standard queries (aliases in `WHERE`, ungrouped columns). Code that "works" in
SQLite-based tests can fail against MySQL or PostgreSQL. Write the standard form.
</Callout>
