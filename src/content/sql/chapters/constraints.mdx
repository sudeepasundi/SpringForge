## Why it matters

Application code has bugs, runs in several versions at once during a deploy, and is not the only thing
that writes to the database (scripts, admin tools, other services). Constraints are rules the
**database** enforces on every write, so bad data is rejected at the door instead of discovered in a
report months later.

### Foreign keys and ON DELETE / ON UPDATE

What should happen to orders when their customer is deleted?

<DecisionTable
  columns={['Deleting the parent…', 'Use for']}
  rows={[
    { label: 'NO ACTION / RESTRICT (default)', verdict: 'good', cells: ['…fails while children exist', 'Most relationships — make deletion explicit'] },
    { label: 'CASCADE', cells: ['…deletes the children too', 'Children that are part of the parent (order → order items)'] },
    { label: 'SET NULL', cells: ['…sets the child column to NULL', 'Optional links (employee → manager)'] },
    { label: 'SET DEFAULT', cells: ['…sets the child column to its default', 'Rare'] },
  ]}
/>

<SqlPlayground
  dataset="shop"
  title="CASCADE in action"
  query={`CREATE TABLE cart (id INTEGER PRIMARY KEY, customer_id INTEGER NOT NULL REFERENCES customer(id));
CREATE TABLE cart_item (
  cart_id    INTEGER NOT NULL REFERENCES cart(id) ON DELETE CASCADE,
  product_id INTEGER NOT NULL REFERENCES product(id),
  quantity   INTEGER NOT NULL CHECK (quantity > 0),
  PRIMARY KEY (cart_id, product_id)
);

INSERT INTO cart VALUES (1, 7);
INSERT INTO cart_item VALUES (1, 4, 2), (1, 8, 1);

DELETE FROM cart WHERE id = 1;                -- its items go too
SELECT COUNT(*) AS items_left FROM cart_item;`}
/>

<Callout type="pitfall" title="Cascades can delete more than you meant">
A chain of `ON DELETE CASCADE` can remove a large part of the database from one `DELETE`. Use it only
for true ownership, and prefer soft deletes for business entities.
</Callout>

<Callout type="note" title="SQLite enforces foreign keys only when asked">
SQLite ignores foreign keys unless `PRAGMA foreign_keys = ON` is set per connection (the runners here
turn it on). MySQL's InnoDB and PostgreSQL always enforce them.
</Callout>

### Index your foreign keys

Deleting a customer makes the database look for referencing orders; without an index on
`orders.customer_id`, that is a full scan — and joins on the column are slow. PostgreSQL does **not**
create these indexes automatically; MySQL does.

### Composite and partial uniqueness

<SqlPlayground
  dataset="hr"
  query={`-- one row per employee per project already: PRIMARY KEY (employee_id, project_id)
-- a unique rule on part of a table: at most one Lead per project
CREATE UNIQUE INDEX one_lead_per_project ON assignment (project_id) WHERE role = 'Lead';

INSERT INTO assignment (employee_id, project_id, role, hours) VALUES (5, 1, 'Developer', 10);
SELECT project_id, COUNT(*) AS leads FROM assignment WHERE role = 'Lead' GROUP BY project_id;`}
/>

Partial unique indexes work in SQLite and PostgreSQL. MySQL does not have them; a common workaround is
a generated column that is `NULL` for rows the rule should ignore.

### Naming constraints

Named constraints make errors readable and migrations possible:

```sql
CONSTRAINT uq_customer_email UNIQUE (email),
CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customer(id),
CONSTRAINT ck_order_item_qty CHECK (quantity > 0)
```

<KeyTakeaways
  points={[
    'Constraints make the database reject bad data from every writer, not just your application.',
    'NOT NULL, PRIMARY KEY, UNIQUE, FOREIGN KEY and CHECK cover most rules.',
    'ON DELETE decides what happens to children: RESTRICT by default, CASCADE for owned rows, SET NULL for optional links.',
