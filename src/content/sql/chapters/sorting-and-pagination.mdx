## Why it matters

Without `ORDER BY`, a database may return rows in **any** order — and that order can change between
runs, versions or after an index is added. Every list you show a user, and every page of an API, needs
an explicit, deterministic order. And the obvious way to page through data gets slower with every page.

## How it works

### ORDER BY

<SqlPlayground
  dataset="shop"
  query={`SELECT name, category_id, price
FROM product
ORDER BY category_id ASC, price DESC;`}
/>

- `ASC` (the default) or `DESC`, per column.
- Sort by several columns: the second breaks ties in the first.
- You may sort by an alias or an expression: `ORDER BY price * stock DESC`.
- Sorting by column position (`ORDER BY 2`) works but breaks when someone reorders the `SELECT` list.

### Ties make order nondeterministic

Two engineers earn 125000. Sorting only by salary leaves their relative order up to the database:

<Compare>
  <Bad title="Ties in the sort key">

```sql
SELECT first_name, salary
FROM employee
ORDER BY salary DESC;
-- Arjun and Priya may swap between runs
```

  </Bad>
  <Good title="Add a unique tie-breaker">

```sql
SELECT first_name, salary
FROM employee
ORDER BY salary DESC, id;
-- always the same order
```

Essential for pagination: without it, a row can appear on two pages or on none.

  </Good>
</Compare>

`LIMIT` without `ORDER BY` returns an arbitrary set of rows.

### Pagination: OFFSET versus keyset

**Offset pagination** asks for "page 3" as `LIMIT 10 OFFSET 20`. Simple, and fine for small tables — but
the database must still read and discard every skipped row, so page 5,000 reads 50,000 rows. Rows added
or deleted between requests also shift everything, causing duplicates or gaps.

**Keyset (seek) pagination** remembers where the last page ended and asks for rows after it:

<SqlPlayground
  dataset="shop"
  title="Keyset pagination — the next page after order 10"
  query={`-- page 1
SELECT id, ordered_at, status FROM orders
ORDER BY id
LIMIT 5;

-- next page: the client sends back the last id it saw (5)
SELECT id, ordered_at, status FROM orders
WHERE id > 5
ORDER BY id
LIMIT 5;`}
/>

With an index on the sort key, every page costs the same. Sorting by a non-unique column needs a
tie-breaker in both the `ORDER BY` and the `WHERE`:

```sql
-- newest first, ties broken by id; the client sends the last (ordered_at, id)
SELECT id, ordered_at FROM orders
WHERE ordered_at < :last_at OR (ordered_at = :last_at AND id < :last_id)
ORDER BY ordered_at DESC, id DESC
LIMIT 20;
-- PostgreSQL and MySQL 8 can also write: WHERE (ordered_at, id) < (:last_at, :last_id)
```

## In a Spring and Java app

Spring Data's `Pageable` uses offset pagination; for large tables consider keyset queries (Spring Data's
`ScrollPosition` / `Window` supports them). See [API Design](/learn/web-rest/api-design).

  points={[
    'Without ORDER BY, row order is undefined — always sort lists you show or page through.',
    'Add a unique tie-breaker (usually the primary key) so the order is deterministic.',
    'NULL placement differs by database; NULLS FIRST / NULLS LAST makes it explicit where supported.',
    'LIMIT/OFFSET is simple but slows down on deep pages and shifts when data changes.',
    'Keyset pagination (WHERE key > last_seen ORDER BY key LIMIT n) stays fast and stable.',
