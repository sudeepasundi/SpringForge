## Why it matters

Almost every application stores its important data in a relational database, and SQL is how you talk
to it. ORMs such as JPA write SQL for you — until a page is slow, a report is wrong or a migration
fails, and then you need to read and write it yourself. SQL is also one of the few skills that has
stayed useful, almost unchanged, for fifty years.

## How it works

### Tables, rows and columns

A relational database stores data in **tables**. Each **row** is one thing (a customer, an order);
each **column** is one fact about it, with a type. Every example in this section runs against a real
database in your browser — press **Run** (or Ctrl/⌘ + Enter) to try it, change the query, and press
**Reset** to start again.

### Keys connect tables

- A **primary key** uniquely identifies each row (`customer.id`).
- A **foreign key** is a column that refers to a primary key in another table (`orders.customer_id`
  refers to `customer.id`). The database refuses values that point nowhere.

Splitting data into related tables — rather than repeating the customer's details on every order —
is what makes a database **relational**. You recombine the pieces with **joins** when you query.

Click **Schema** in any runner to see every table, its columns and its foreign keys.

<SqlPlayground
  dataset="shop"
  title="Orders with their customer's name"
  query={`SELECT o.id, o.ordered_at, o.status, c.name AS customer
FROM orders o
JOIN customer c ON c.id = o.customer_id
ORDER BY o.id
LIMIT 5;`}
/>

### SQL is declarative

You describe **what** you want, not **how** to get it. The database's **query planner** decides
whether to scan a table or use an index, and in what order to join. That is why the same query can be
fast or slow depending on indexes — covered in Part 5.
