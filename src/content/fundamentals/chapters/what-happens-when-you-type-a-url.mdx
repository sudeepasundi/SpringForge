## Why it matters

"What happens when you type a URL into a browser and press Enter?" is one of the most common interview
questions because a good answer touches everything in this part. It is also the mental model you use
when a page is slow: which of these steps is taking the time?

<Steps>
  <Step title="Parse the input">

The browser decides whether you typed a URL or a search. It splits the URL into **scheme** (`https`),
**host** (`shop.example.com`), **port** (default 443), **path** (`/products/42`) and query. HSTS may
force `https` even if you typed `http`.

  </Step>
  <Step title="Resolve the name (DNS)">

Browser cache → OS cache and `/etc/hosts` → recursive resolver → root, TLD and authoritative servers.
The result is an IP address, often of a **CDN** or **load balancer** rather than a single server.

  </Step>
  <Step title="Open a TCP connection">

The three-way handshake with that IP on port 443 — or a reused connection if one is already open. With
HTTP/3, a QUIC connection over UDP combines this step and the next.

  </Step>
  <Step title="Negotiate TLS">

The client and server agree on a TLS version and cipher, the server presents its **certificate**, the
browser checks it is valid for `shop.example.com` and signed by a trusted CA, and both derive session
keys. From now on everything is encrypted. ALPN picks HTTP/2 or HTTP/1.1.

  </Step>
  <Step title="Send the HTTP request">

`GET /products/42` with headers: `Host`, `Accept`, cookies, `User-Agent`, and so on.

  </Step>
  <Step title="Pass through the edge">

A CDN may answer straight from its cache. Otherwise a load balancer or reverse proxy terminates TLS,
applies rules (rate limits, routing by path), and forwards the request to a healthy application instance.

  </Step>
  <Step title="The application handles it">

The web server hands the request to a thread; the framework routes it to a controller; the code checks
authentication, reads from a cache or database (each its own network hop), and renders HTML or JSON.

  </Step>
  <Step title="The response comes back">

Status, headers (`Content-Type`, `Cache-Control`, `Set-Cookie`) and a body, usually compressed. The
browser stores cookies and caches what it is allowed to.

  </Step>
  <Step title="The browser renders the page">

It parses HTML into the DOM, discovers CSS, JavaScript and images and fetches them (often in parallel
over the same HTTP/2 connection), builds the CSSOM, runs scripts, lays out the page and paints it.
JavaScript may then make further API calls.

  </Step>
</Steps>

## How to answer in an interview

Structure beats detail. Walk the layers in order — **DNS → TCP → TLS → HTTP → load balancer →
application → database → response → rendering** — and offer to go deeper on any step. Mention caching
at each level (browser, DNS, CDN, application) and the fact that connections are reused.
