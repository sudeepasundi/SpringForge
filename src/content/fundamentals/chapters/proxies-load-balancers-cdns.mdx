## Why it matters

In production, a request almost never goes straight from a user to your application. It passes through
a CDN, a load balancer, maybe an API gateway and a sidecar proxy. Each one can cache, retry, time out,
rewrite headers or hide the client's real IP. When something behaves strangely, it is often one of these.

## How it works

### Forward and reverse proxies

A reverse proxy commonly terminates TLS, routes by host or path, compresses, caches, rate-limits,
adds security headers and hides the internal topology.

### Load balancers

A load balancer spreads requests across several instances of a service, and stops sending traffic to
unhealthy ones.

### Layer 4 versus layer 7

    { label: 'Layer 7 (application)', verdict: 'good', cells: ['HTTP: host, path, headers, cookies', 'Route /api to one service and /static to another, retry, rewrite, authenticate, balance per request', 'Nginx, Envoy, AWS ALB, API gateways'] },

A layer-4 balancer spreads **connections**. With long-lived HTTP/2 or gRPC connections, all of a
client's requests stick to one backend — a layer-7 balancer spreads individual **requests**.

### Balancing algorithms

- **Round robin** — next instance in turn. Simple; ignores load.
- **Least connections / least outstanding requests** — better when request costs vary.
- **Weighted** — bigger instances get more; also used for canary releases (5% to the new version).
- **Hash-based** (client IP, a header, a cookie) — the same client goes to the same instance.
- **Power of two choices** — pick two at random, use the less loaded one; a good default at scale.

### Health checks

The balancer probes each instance (for example `GET /actuator/health/readiness`) and removes failing
ones. **Readiness** means "send me traffic"; **liveness** means "I am not stuck — do not restart me".
Mixing them up causes restart loops when a database blips.

### Sticky sessions

Pinning a user to one instance lets that instance keep session data in memory — but that instance
becomes a single point of failure for the user, and scaling or deploying disrupts sessions.
**Stateless services** (sessions in a shared store, or in tokens) avoid the problem.

### What proxies change

<Callout type="pitfall" title="The client IP is now the proxy's">
Behind a proxy, `request.getRemoteAddr()` is the proxy. The original is in `X-Forwarded-For` (and
`X-Forwarded-Proto` says the user used HTTPS). Only trust these headers from your own proxies, or anyone
can spoof them — in Spring Boot, set `server.forward-headers-strategy`.
</Callout>

Proxies also add their own **timeouts** (an idle timeout shorter than your client pool's keep-alive
causes "connection reset"), **body size limits** (`413 Payload Too Large`), and sometimes **retries** —
which can duplicate non-idempotent requests.

### CDNs

A **content delivery network** is a worldwide fleet of reverse proxies. Users connect to a nearby edge
location, which serves cached responses or forwards to your origin.

- Great for static assets (images, JS, CSS) and cacheable API responses.
- Obeys `Cache-Control` — `public, max-age=31536000, immutable` for fingerprinted assets; `no-store`
  for personal data.
- Also absorbs attacks (DDoS) and terminates TLS close to the user.
- The risk: caching something personal because a header was wrong.

### API gateways and service meshes

An **API gateway** is a layer-7 reverse proxy with API features: authentication, rate limits per client,
request transformation, aggregation. A **service mesh** puts a small proxy (sidecar) next to every
service to handle mTLS, retries and telemetry for service-to-service calls.

## When you'll meet it

- **502 / 504 from the proxy** — the backend crashed, refused, or was slower than the proxy's timeout.
- **Logs show the same IP for every user** — forwarded headers are not being read.
- **Redirect loop to http** — the app does not know the original request was HTTPS.
- **One pod gets all the gRPC traffic** — layer-4 balancing of long-lived connections.
- **Users see someone else's page** — a CDN cached a personalised response.
- **Interview:** "Layer 4 versus layer 7 load balancing?" and "How would you do a zero-downtime deploy?"
