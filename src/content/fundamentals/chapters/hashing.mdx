## Why it matters

Hashing is everywhere: `HashMap` lookups, Git commit ids, file-download checksums, cache keys, password
storage, sharding data across servers, and deduplicating uploads. Knowing what a hash guarantees — and
what it does not — prevents both slow code and security mistakes.

## How it works

### What a hash function is

A **hash function** takes input of any size and returns a fixed-size output (the **hash**, or
**digest**). The same input always gives the same output.

```java
"hello".hashCode();                                       // 99162322 (32-bit int)
MessageDigest.getInstance("SHA-256")
        .digest("hello".getBytes(UTF_8));                  // 32 bytes:
// 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

Changing one character changes the output completely (the **avalanche effect**):

```text
SHA-256("hello")  = 2cf24dba5fb0a30e…
SHA-256("hellp")  = fdd7585e08c4e2af…   (unrelated)
```

### Properties of a cryptographic hash

- **Pre-image resistance** — given a hash, you cannot find an input that produces it.
- **Second pre-image resistance** — given an input, you cannot find a *different* input with the same hash.
- **Collision resistance** — you cannot find *any* two inputs with the same hash.
- **Deterministic and fast** — fast is good for integrity checks, bad for passwords.

A hash is **one-way**: there is no key and no "decrypt". Because outputs are fixed-size and inputs are
not, collisions must exist (the **pigeonhole principle**) — a good hash just makes them impossible to
find in practice.

### Hash tables: hashing for speed

A hash table turns a key into an array index: `index = hash(key) mod capacity`. Lookup is then O(1) on
average instead of scanning.

- **Collisions** are handled by chaining (a list or tree per bucket) or by probing other slots.
- A good hash spreads keys evenly; a bad one (every key → the same bucket) makes lookups linear.
- Equal keys must have equal hashes — the `equals`/`hashCode` contract in Java.

<Callout type="pitfall" title="A hash is not a secret">
Hashing a guessable value hides nothing: anyone can hash every phone number and compare. Hashing an
email address to "anonymise" it is reversible by brute force. And a plain hash cannot prove *who* made
it — anyone can compute SHA-256. For that you need a key (HMAC or a signature).
</Callout>

## When you'll meet it

- **Verifying a downloaded JDK or container image** — `sha256sum` against the published value.
- **`HashMap` slow with many entries** — a poor `hashCode`.
- **Choosing a partition key** — the hash decides which Kafka partition or database shard gets the data.
- **Reviewing code that uses MD5** — fine for a cache key, never for security.
- **Interview:** "What is hashing? What is a collision? Hashing versus encryption?"
