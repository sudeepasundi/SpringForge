## Why it matters

Your Spring Boot service is "one program", yet it handles two hundred requests at once, uses four
CPU cores, and still stalls completely when one database call hangs. To understand why — and to read
a thread dump, size a pool, or answer "what is the difference between a process and a thread?" — you
need a picture of what the operating system does with your code.

## How it works

### Program, process, thread

When you run `java -jar app.jar`, the OS creates **one process** — the JVM. Inside it, the JVM
starts many **threads**: `main`, garbage-collector threads, JIT-compiler threads, and, once Tomcat
starts, a pool of request-handling threads.

**Isolation is the key difference.** One process cannot read another's memory; if one crashes, the
others survive. Threads in the same process share memory, which makes communication cheap — and
makes bugs like race conditions possible.

### The scheduler and context switches

A machine has a few CPU cores but thousands of threads. The OS **scheduler** gives each runnable
thread a short time slice, then pauses it and runs another. Pausing one thread and resuming another is
a **context switch**: the CPU registers are saved and restored, and caches go cold.

  <Step title="The timer fires or the thread blocks">

Either its time slice ended, or it asked for something slow (disk, network, a lock).

  </Step>
  <Step title="The kernel saves its state">

Program counter, registers and stack pointer go into the thread's kernel record.

  </Step>
  <Step title="The scheduler picks another runnable thread">

Using priorities and fairness rules.

  </Step>
  <Step title="Its state is restored and it runs">

The whole switch takes microseconds — cheap once, expensive when it happens hundreds of thousands of
times a second.

  </Step>
</Steps>

Concurrency is **dealing with** many things at once (interleaving on one core). Parallelism is
**doing** many things at once (on several cores). A web server needs concurrency; number-crunching
wants parallelism.

### CPU-bound versus I/O-bound

  columns={['Spends its time', 'More threads than cores helps?', 'Example']}

Most business services are I/O-bound: a request spends a few milliseconds computing and tens of
milliseconds waiting. That is why a 4-core server runs 200 request threads — and why virtual threads
(Java 21), which make waiting almost free, matter so much.

### Talking between processes

Processes cannot share memory directly, so they use **inter-process communication**: pipes
(`ps aux | grep java`), sockets (HTTP between services), shared files, or message queues. A
microservice architecture is, underneath, processes talking over sockets.

## When you'll meet it

- **"The app uses 100% CPU on one core."** A single thread is stuck in a loop; a thread dump
  (`jcmd <pid> Thread.print`) shows which.
- **"We added threads and it got slower."** CPU-bound work with more threads than cores only adds
  context switches.
- **"One slow dependency froze the whole service."** Every request thread was waiting on it and the
  pool ran out — the resilience part covers the fix.
- **Containers.** A Docker container is a process (or a few) with isolation tricks, not a small VM.

## In a Spring and Java app

- Tomcat's request pool (`server.tomcat.threads.max`, default 200) is a pool of platform threads.
- `spring.threads.virtual.enabled=true` switches request handling to virtual threads.
- The [Threads chapter](/java/threads-and-memory-model) and
  [Virtual Threads](/java/virtual-threads) go deeper on the Java side.
