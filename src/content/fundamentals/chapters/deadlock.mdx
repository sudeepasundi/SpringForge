## Why it matters

At 2 a.m. the service stops responding. CPU is at zero, memory is fine, nothing is in the error log.
Requests pile up and time out. A thread dump shows two threads, each waiting forever for something the
other one holds. That is a **deadlock**: no crash, no error — just silence.

The classic cause is a money transfer:

```java
void transfer(Account from, Account to, long amount) {
    synchronized (from) {           // Thread 1: transfer(acc1, acc2) locks acc1
        synchronized (to) {         // Thread 2: transfer(acc2, acc1) locks acc2
            from.debit(amount);     // each now waits for the other's lock — forever
            to.credit(amount);
        }
    }
}
```

### The four conditions (Coffman)

A deadlock can happen only if **all four** hold at once. Break any one and it cannot happen.

### Fix 1: a consistent lock order

```java
void transfer(Account from, Account to, long amount) {
    Account first  = from.id() < to.id() ? from : to;    // always lock the lower id first
    Account second = first == from ? to : from;
    synchronized (first) {
        synchronized (second) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
```

Both threads now try `acc1` first. One waits at the **first** lock while holding nothing, so no cycle can form.

### Fix 2: timeouts

```java
if (first.lock.tryLock(100, MILLISECONDS)) {
    try {
        if (second.lock.tryLock(100, MILLISECONDS)) {
            try { /* transfer */ } finally { second.lock.unlock(); }
        } else {
            throw new RetryLaterException();   // back off, release, retry with jitter
        }
    } finally { first.lock.unlock(); }
}
```

### Prevention, avoidance, detection

- **Prevention** — design so one of the four conditions can never hold (lock ordering).
- **Avoidance** — decide at run time whether granting a resource could lead to deadlock (the banker's
  algorithm; mostly theoretical in application code).
- **Detection and recovery** — let it happen, notice the cycle, and break it by killing one party.
  **This is what databases do.**

## Deadlocks in databases

Two transactions update the same two rows in opposite orders:

```sql
-- Transaction 1                         -- Transaction 2
UPDATE account SET … WHERE id = 1;       UPDATE account SET … WHERE id = 2;
UPDATE account SET … WHERE id = 2;       UPDATE account SET … WHERE id = 1;   -- cycle
```

The database's deadlock detector spots the cycle, picks a **victim**, and rolls it back with an error
(MySQL error 1213, PostgreSQL `40P01`). The other transaction continues.

So in database code, deadlocks are **expected occasionally** under load. The right response:

1. Touch rows in a consistent order (for example, sorted by id).
2. Keep transactions short; do not call external services inside them.
3. Add the right indexes, so updates lock fewer rows.
4. **Retry** the failed transaction a few times — it is safe, because it was rolled back.

## Deadlocks between services

With no global detector, distributed systems usually rely on **timeouts**: if service A calls B, which
calls back into A, and both wait on exhausted thread pools, only a timeout breaks the cycle. Avoid
synchronous call cycles between services entirely.

## When you'll meet it

- **A service that hangs with zero CPU** — take a thread dump; the JVM prints "Found one Java-level deadlock".
- **`Deadlock found when trying to get lock; try restarting transaction`** in a MySQL log.
- **Nested `@Transactional` calls that use two connections** from a small pool — each waits for a
  connection the other holds.
- **Interview:** "What is a deadlock? What are the four necessary conditions? How do you prevent it?"
