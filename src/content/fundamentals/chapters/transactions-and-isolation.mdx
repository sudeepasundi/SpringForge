## Why it matters

Money leaves one account but never arrives in the other. Two admins edit the same product and one edit
silently disappears. A report adds up to a different total each time it runs. Transactions and isolation
levels are the database features that prevent these — if you understand what they actually promise.

Note that **lost updates are possible at Read Committed** — the most common default — unless you guard
against them.

### Locking versus MVCC

- **Locking**: readers and writers take locks; conflicting transactions wait (and can deadlock).
- **MVCC** (multi-version concurrency control): writers create new row versions; readers see a
  consistent **snapshot** without blocking writers. PostgreSQL, MySQL InnoDB and Oracle all use MVCC for
  reads, and still lock rows for concurrent writes.

### Keep transactions short

Long transactions hold locks, block others, grow undo logs and raise deadlock odds. Never wait for user
input, call a slow external API or send email inside one — do that before or after.

### Beyond one database

A transaction covers one database. Updating a database **and** publishing a message, or two services'
databases, cannot be one ACID transaction in practice. Patterns such as the **transactional outbox** and
**sagas** give eventual consistency instead — see
[Consistency, CAP and Idempotency](/fundamentals/consistency-cap-idempotency).

## When you'll meet it

- **Half-finished work after an exception** — missing transaction boundaries.
- **An edit silently overwritten** — a lost update; add `@Version`.
- **Overselling stock under load** — check-then-act; use an atomic update or a lock.
- **Deadlocks under load** — see [Deadlock](/fundamentals/deadlock); keep transactions short and retry.
