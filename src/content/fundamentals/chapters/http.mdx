## Why it matters

Almost every service you build speaks HTTP. Choosing the right method and status code, knowing which
calls are safe to retry, understanding cookies and caching headers, and knowing what HTTP/2 changed are
the difference between an API that behaves and one that double-charges customers.

## How it works

### A request and a response

HTTP is text-shaped (HTTP/1.1 literally is text; HTTP/2 and 3 encode the same ideas in binary).

```http
POST /orders HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi…
Idempotency-Key: 7f9c2b1e-…

{"sku": "BOOK-42", "quantity": 1}
```

```http
HTTP/1.1 201 Created
Location: /orders/981
Content-Type: application/json
Cache-Control: no-store

{"id": 981, "status": "PENDING"}
```

A request has a **method**, a **path**, **headers** and an optional **body**. A response has a
**status code**, headers and an optional body. HTTP itself is **stateless**: each request carries
everything the server needs; state lives in cookies, tokens or the database.

### Methods, safety and idempotency

- **Safe**: does not change anything on the server.
- **Idempotent**: doing it twice has the same effect as doing it once — so it is safe to **retry**.

<Callout type="prod" title="Retrying a POST">
A client times out waiting for `POST /payments`. Did the payment happen? It cannot know. Retrying
blindly may charge twice. The fix is an **idempotency key**: the client sends a unique key, and the
server stores the result per key and returns the same result for a repeat.
</Callout>

401 means "who are you?" (log in); 403 means "I know who you are, and no". 502 and 504 come from a
proxy or gateway: the service behind it failed or was too slow.

### Headers worth knowing

- `Content-Type` / `Accept` — the body's format, and the formats the client wants.
- `Authorization` — credentials, usually `Bearer <token>`.
- `Cache-Control`, `ETag`, `If-None-Match` — caching and conditional requests (a `304` saves re-sending the body).
- `Location` — where a created or moved resource is.
- `Retry-After` — with 429 or 503, when to try again.
- `X-Forwarded-For` / `Forwarded` — the original client, as seen by a proxy.
- `traceparent` — a distributed-tracing id.
- CORS: `Origin`, `Access-Control-Allow-Origin` — whether a browser page from another origin may read the response.

### Cookies

A server sets `Set-Cookie: SESSION=abc; HttpOnly; Secure; SameSite=Lax; Path=/`, and the browser sends
`Cookie: SESSION=abc` on later requests to that site.

- `HttpOnly` — JavaScript cannot read it (limits XSS damage).
- `Secure` — only sent over HTTPS.
- `SameSite` — limits sending it on cross-site requests (CSRF defence).

Server-side, **connection pools** in HTTP clients keep connections alive between calls, avoiding a TCP
and TLS handshake per request.

## When you'll meet it

- **Designing an API**: resources as nouns, the right method, `201` with `Location`, `409` for
  conflicts, `422` for validation.
- **Deciding what to retry**: idempotent methods on 502, 503, 504 and timeouts — never a plain POST
  without an idempotency key.
- **Debugging**: `curl -v` shows the request line, headers, TLS details and redirects.
- **Browser errors that are really CORS**: the server must answer the preflight `OPTIONS` correctly.
- **Interview:** "PUT versus PATCH", "401 versus 403", "Is HTTP stateless?", "What did HTTP/2 change?"
