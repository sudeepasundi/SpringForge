## Why it matters

"Just add a cache" is the most common performance advice — and caches cause some of the most confusing
bugs: stale prices, users seeing each other's data, and outages when the cache empties. To use caches
well you need a sense of *how much faster* each layer is, and what it costs to keep a copy.

Two lessons: **memory is thousands of times faster than the network**, and **the network is where most
of your request time goes**. Caching is about moving data up this ladder.

### What a cache is

A cache is a **smaller, faster copy** of data whose source of truth lives somewhere slower. The same
idea repeats at every level: CPU caches, the OS page cache, an in-process map, Redis, a CDN, the
browser.

- **Hit ratio** = hits ÷ lookups. A cache with a 20% hit ratio mostly adds latency and complexity.
- **TTL** (time to live) bounds how stale an entry can get.
- **Eviction** decides what to drop when the cache is full.

An LRU cache is a hash map (for O(1) lookup) plus a doubly linked list ordered by recency (for O(1)
eviction) — a classic interview exercise.

### Caching strategies

- **Cache-aside** (lazy loading): the application reads the cache, falls back to the source, and fills
  the cache. Simple and common.
- **Read-through / write-through**: the cache library itself loads from and writes to the source.
- **Write-behind**: writes go to the cache and are flushed to the database later — fast, but data can be
  lost.
- **Refresh-ahead**: popular entries are reloaded before they expire.

### The hard parts

> "There are only two hard things in computer science: cache invalidation and naming things."

<Compare>
  <Bad title="Update the database, forget the cache">

```java

// the cache still says the old price for up to 10 minutes
```

  </Bad>
  <Good title="Evict on write (and keep a TTL as a safety net)">

```java
productRepository.updatePrice(id, newPrice);

```

With several instances, each in-process cache must be told too — which is why shared caches (Redis)
are popular.

  </Good>

- **Stampede (thundering herd)**: a popular entry expires and a thousand requests all hit the database
  at once. Fix with request coalescing, early refresh, or jittered TTLs.
- **Cold start**: after a restart or a cache flush, the database suddenly sees the full load.
- **Wrong key**: a cache key without the user id shows one user's data to another.
- **Caching nulls**: caching "not found" protects the database from repeated misses — but set a short TTL.

## When you'll meet it

- **"Prices on the page are out of date"** — invalidation or TTL.
- **"The database fell over after Redis restarted"** — cold cache, the database was sized for a warm one.
- **"The service got slower after adding a cache"** — low hit ratio, or serialisation cost higher than
  the query.
- **Interview:** "Design an LRU cache" and "Where would you add caching to this system?"
