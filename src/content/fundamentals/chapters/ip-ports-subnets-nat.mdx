## Why it matters

Your app works on your laptop, then in Docker the browser gets "connection refused". A colleague says
"it's listening on localhost, bind it to 0.0.0.0". Another asks you to allow `10.20.0.0/16` in the
security group. These are everyday tasks, and they all rest on addresses, ports and subnets.

## How it works

### IP addresses

An **IPv4** address is 32 bits, written as four bytes: `192.168.1.20`. That allows about 4.3 billion
addresses — not enough for every device, which is why NAT exists. An **IPv6** address is 128 bits,
written in hex: `2001:db8::8a2e:370:7334` (`::` stands for a run of zeros).

### Subnets and CIDR

An address has a **network** part and a **host** part. CIDR notation says how many leading bits are the
network: `/24` means the first 24 bits.

Hosts in the same subnet talk directly; traffic to another subnet goes through a **gateway** (router).
In cloud networks (a VPC), you split an address range into subnets per availability zone and per role
(public, private, database).

### Ports and sockets

An IP address gets a packet to a **machine**; a **port** (0–65535) gets it to a **program**. A
connection is identified by four values — source IP, source port, destination IP, destination port —
so one server port can serve thousands of clients.

- **Well-known ports**: 22 SSH, 53 DNS, 80 HTTP, 443 HTTPS, 3306 MySQL, 5432 PostgreSQL, 6379 Redis,
  9092 Kafka.
- **Ephemeral ports**: the OS picks a temporary source port (often 32768–60999) for each outgoing connection.
- Ports below 1024 need extra privileges on Linux.

### localhost versus 0.0.0.0

<Compare>
  <Bad title="Bound to localhost inside a container">

```yaml
server:
  address: 127.0.0.1    # only reachable from inside the container itself
```

Docker forwards traffic to the container's network interface, not its loopback, so the published
port answers "connection refused" or resets.

  </Bad>
  <Good title="Bound to all interfaces">

```yaml
server:
  address: 0.0.0.0      # Spring Boot's default when address is not set
```

Then control exposure with the published ports, network policies and firewalls — not by binding to
loopback.

  </Good>
</Compare>

And the mirror image: inside a container, `localhost` is the container. To reach a database in another
container, use its service name (`db:5432`), not `localhost:5432`.

### NAT

**Network address translation** lets many private hosts share one public IP. The router rewrites the
source address and port of outgoing packets and remembers the mapping so replies find their way back.

Consequences: outside hosts cannot start connections to hosts behind NAT (why peer-to-peer is hard),
and a server sees many users behind one IP (why rate limiting by IP is crude). In the cloud, a **NAT
gateway** gives private subnets outbound internet access; a service with no public IP cannot be reached
from outside.

## When you'll meet it

- **Security groups and firewall rules** are written in CIDR.
- **"Address already in use"** — another process holds the port (`ss -ltnp` shows which).
- **Port exhaustion** — thousands of short outgoing connections use up ephemeral ports; reuse
  connections with a pool.
- **Allow-listing a partner** — they give you their NAT gateway's public IPs.
- **Interview:** "How many hosts are in a /26?" (64 addresses.)

## In a Spring and Java app

- `server.port` and `server.address` control Spring Boot's listener; Docker networking is in
  [Containerising](/learn/cloud-native/containerising).
- Connection pools (HikariCP, HTTP clients) exist partly to avoid exhausting ports.
