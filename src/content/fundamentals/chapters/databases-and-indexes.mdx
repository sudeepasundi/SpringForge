## Why it matters

Most application slowness is database slowness, and most database slowness is a missing or unusable
index. Choosing between SQL and NoSQL, designing tables, and reading a query plan are core skills — and
none of them are taught in an electronics degree.

**Start with a relational database** unless you have a specific reason not to. NoSQL systems usually
give up joins or multi-row transactions in exchange for a particular access pattern or scale.

### Keys, relationships and normalisation

- A **primary key** uniquely identifies a row. A **foreign key** references a row in another table and
  the database enforces that it exists.
- Relationships: one-to-many (a customer has many orders), many-to-many (via a join table).
- **Normalisation** stores each fact once — a customer's address lives in `customer`, not copied into
  every order — avoiding update anomalies. **Denormalisation** deliberately duplicates data to make reads
  faster, at the cost of keeping copies in sync.

### What an index is

Without an index, `WHERE email = ?` checks every row: a **full table scan**, O(n). An index is a separate,
sorted structure — almost always a **B-tree** — mapping column values to row locations, so the lookup is
O(log n).

- A B-tree is wide and shallow: millions of rows need only 3–4 page reads.
- Leaves are sorted and linked, so indexes also serve **range queries** (`BETWEEN`, `>`), `ORDER BY` and prefix `LIKE 'abc%'`.
- Primary keys and unique constraints create indexes automatically. In MySQL's InnoDB, the table itself is
  stored in primary-key order (a **clustered index**).

### The cost of indexes

Every insert, update and delete must also update each index, and indexes use disk and memory. Index
what your queries filter, join and sort on — not every column.

### Composite indexes and the left-most rule

An index on `(customer_id, created_at)` is sorted by `customer_id`, then by `created_at` within each customer.

A **covering index** contains every column the query needs, so the table is never read.

### Reading a query plan

```sql
EXPLAIN ANALYZE
SELECT id, total FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;
```

```text
Limit  (actual time=0.041..0.058 rows=20)
  ->  Index Scan Backward using ix_orders_customer_created on orders
        Index Cond: (customer_id = 42)          ← good: an index scan
```

Warning signs: **Seq Scan** / `type: ALL` on a large table, **Sort** or **Using filesort** on big inputs,
row estimates wildly different from actual rows (stale statistics), and nested loops over large sets.

## When you'll meet it

- **A query that was fast becomes slow as data grows** — a missing index or a scan.
- **Writes get slower** — too many indexes.
- **`OFFSET 500000` pages crawl** — use keyset pagination (`WHERE id > :lastId ORDER BY id LIMIT 50`).
- **Choosing a database for a new service** — start relational; pick NoSQL for a clear access pattern.
- **Interview:** "How does an index work?", "Why not index every column?", "SQL versus NoSQL?"
