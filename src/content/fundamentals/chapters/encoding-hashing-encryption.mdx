## Why it matters

A code review finds this: `String secret = Base64.getEncoder().encodeToString(password.getBytes());` with
the comment "encrypted". It is not. Mixing up encoding, hashing and encryption is one of the most common
security mistakes juniors make — and one of the most common interview questions.

### Encoding

Encoding exists because some channels only accept certain characters. Base64 turns arbitrary bytes into
64 safe characters, so binary data can travel inside JSON, email or a URL.

```java
String encoded = Base64.getEncoder().encodeToString("hello".getBytes(UTF_8));   // aGVsbG8=
String decoded = new String(Base64.getDecoder().decode(encoded), UTF_8);          // hello
```

No secret is involved. **Anyone can decode it.** HTTP Basic authentication sends
`base64(user:password)` — which is why it is only acceptable over HTTPS. A JWT's header and payload are
Base64URL-encoded, so anyone holding a token can read its contents.

### Hashing

One-way. You cannot get the input back; you can only hash a candidate and compare. Used to check that
data has not changed, and — with a slow, salted algorithm — to store passwords so that even the database
owner cannot read them.

### Encryption

Two-way, with a key. Without the key, the ciphertext reveals nothing useful; with it, the original comes
back exactly. Used for data in transit (TLS) and at rest (encrypted disks, encrypted columns, secrets).

## When you'll meet it

- **Code review**: Base64 or a custom "XOR cipher" described as encryption.
- **"Can we decrypt the user's password to email it to them?"** No — passwords are hashed; offer a reset.
- **"Is the JWT encrypted?"** Usually not; it is signed. Do not put secrets in it.
- **Interview:** "What is the difference between encoding, hashing and encryption?" — answer with
  purpose, reversibility and keys.
