## Why it matters

Writing code is only part of the job. On day one in a team you will branch, open a pull request, get a
review, watch CI, and deploy — and later be asked why production is slow. Nobody teaches this in an
engineering degree, and it is where new developers most often feel lost.

## How it works

### Git in one picture

Git stores **snapshots** of your project as a chain of commits. A **branch** is just a movable pointer
to a commit.

Useful habits:

- **Small, focused commits** with messages that say *why*.
- **Short-lived branches** (hours to a couple of days) — long ones cause painful merges.
- **Never commit secrets**; add `.gitignore` early.
- `git revert` to undo a pushed commit safely; avoid rewriting shared history.
- `git bisect` finds the commit that introduced a bug by binary search.

### Pull requests and code review

A pull request proposes a change and invites review. Good ones are **small** (a few hundred lines at
most), explain **what and why**, include tests, and link the ticket.

As a reviewer, look for correctness and edge cases, security (the
[common vulnerabilities](/fundamentals/common-vulnerabilities)), missing tests, readability, and
whether it fits the design. Be specific and kind; separate blocking issues from suggestions.

### The testing pyramid

    E2E --- INT --- UNIT

- **Unit tests** check logic in isolation — fast and precise.
- **Integration tests** check that your code works with real infrastructure (Testcontainers).
- **Contract tests** check that services agree on their APIs.
- **End-to-end tests** check critical user journeys; keep them few, because they are slow and brittle.
- A test that sometimes fails for no reason (**flaky**) must be fixed or removed — it teaches people to ignore red builds.

### CI/CD

<Steps>
  <Step title="Continuous integration">

On every push: compile, run tests, lint, scan dependencies and secrets, build an artefact (a JAR, a
container image). A red build blocks the merge.

  </Step>
  <Step title="Continuous delivery">

The same artefact is promoted through environments — dev, staging, production — with configuration
changing, not the build.

  </Step>
  <Step title="Continuous deployment">

Every change that passes goes to production automatically, usually with safety nets.

  </Step>
</Steps>

Deployment strategies:

- **Rolling** — replace instances a few at a time.
- **Blue–green** — run the new version alongside the old, switch traffic at once, switch back if needed.
- **Canary** — send a small percentage of traffic to the new version, watch metrics, then widen.
- **Feature flags** — deploy code dark and turn features on separately from deploying.

Database changes must be **backward-compatible** across a deploy (expand, migrate, then contract),
because old and new versions run at the same time.

Alert on **symptoms users feel** (error rate, latency against an SLO), not on every CPU spike. When an
incident happens: mitigate first (roll back, scale, switch a flag), find the cause after, and write a
**blameless post-mortem** so the system — not a person — gets fixed.

### Environments and configuration

- Keep configuration out of the code (environment variables, config servers), and **secrets in a secrets
  manager**.
- Make environments as similar as possible — "works on my machine" usually means they differ.
- Everything as code: infrastructure, pipelines, dashboards, alerts.

## When you'll meet it

- **Your first week**: set up the repo, run the tests, make a small PR.
- **A merge conflict** — fetch, rebase, resolve, re-run tests.
- **A red pipeline** — read the failing step's log before re-running.
- **An on-call page** — check the dashboard, find the trace, roll back if in doubt.
- **Interview:** "Describe your development workflow", "How do you test?", "How do you deploy safely?"
