## Why it matters

A recommendation service slows from 50 ms to 30 seconds. Checkout calls it, so checkout threads wait.
Soon every thread is waiting, the health check fails, and the whole shop is down — because of a
non-essential widget. In distributed systems, **failure is normal**; resilience is designing so that a
failure stays small.

## How it works

### How things fail

- **Crash** — the process is gone; calls fail fast (connection refused).
- **Slow** — the worst kind: calls hang and consume your resources.
- **Partial** — some requests fail, some succeed.
- **Wrong** — the dependency answers, incorrectly.
- **Overload** — too many requests; everything slows at once.

**Cascading failure** is when one of these spreads upstream through waiting callers.

### Timeouts: the first defence

Every remote call needs a timeout. Without one, a slow dependency holds your thread forever.

```java
HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(1))             // time to establish the connection
        .build();
HttpRequest request = HttpRequest.newBuilder(uri)
        .timeout(Duration.ofSeconds(2))                     // time to wait for the response
        .build();
```

Set timeouts from the dependency's normal latency (for example a bit above its p99), and make sure a
caller's timeout is **longer than the sum** of what it waits on downstream — otherwise work continues
after the caller gave up.

### Retries: helpful and dangerous

Retries fix transient failures (a blip, a restarted instance) — and can multiply load on something that
is already struggling.

<Compare>
  <Bad title="Immediate, unlimited retries">

```java
while (true) {
    try { return inventory.reserve(item); }
    catch (Exception e) { /* try again immediately */ }
}
```

Thousands of clients doing this turn a small hiccup into a self-inflicted denial of service (a **retry storm**).

  </Bad>
  <Good title="Few retries, backoff with jitter, only when safe">

```java
RetryConfig config = RetryConfig.custom()
        .maxAttempts(3)
        .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(200, 2.0))  // 200 ms, ~400 ms, … with jitter
        .retryOnException(e -> e instanceof TransientException)
        .build();
```

  </Good>
</Compare>

Rules: retry only **idempotent** operations (or use idempotency keys); retry only **transient** errors
(timeouts, 503), not 400s; use **exponential backoff with jitter** so clients do not retry in lockstep;
and retry at **one layer**, not at every layer (3 retries × 3 layers = 27 calls).

### Circuit breakers

A circuit breaker watches calls to a dependency. When too many fail, it **opens** and fails calls
immediately for a while, giving the dependency room to recover and freeing your threads.

While open, return a **fallback** — cached data, a default, or a clear "temporarily unavailable" —
rather than an error page.

### Bulkheads

Named after a ship's watertight compartments: isolate resources so one failing dependency cannot consume
all of them. Give each dependency its own limited pool or concurrency limit (for example, at most 20
concurrent calls to recommendations). When it is slow, only those 20 wait.

### Rate limiting and load shedding

- **Rate limiting** caps how many requests a client may make (token bucket, sliding window) and answers
  `429 Too Many Requests` with `Retry-After`.
- **Load shedding** rejects some work early when the system is saturated — better to serve 80% of users
  well than 100% badly.

### Graceful degradation

Decide in advance what the product does without each dependency: show the page without recommendations,
accept orders and process payment later, serve slightly stale prices from cache.

### Observe and practise

- Measure latency percentiles (p50, p95, p99), error rates and saturation per dependency.
- Define **SLOs** (for example, 99.9% of checkout requests succeed within 500 ms) and alert on them.
- Test failure deliberately — kill instances, add latency — before production does it for you (**chaos engineering**).

## When you'll meet it

- **"One slow service took everything down"** — missing timeouts and bulkheads.
- **"The outage got worse when it started recovering"** — retry storm; add backoff, jitter and circuit breakers.
- **"Clients get 429"** — your rate limit, or theirs; honour `Retry-After`.
- **Interview:** "How do you make service-to-service calls resilient?", "What is a circuit breaker?"
