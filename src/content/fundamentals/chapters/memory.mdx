## Why it matters

"The pod was OOMKilled." "The service got slow after running for a week." "StackOverflowError on a
big input." All three are memory problems, and each has a different cause. Knowing where data
lives — and what the operating system does behind the scenes — tells you which one you are looking at.

```java
void handle(Request request) {        // a new stack frame for handle()
    int retries = 3;                  // primitive: lives in the frame
    Order order = new Order();        // the reference is in the frame; the Order object is on the heap
    process(order);                   // another frame on top
}                                     // frame popped; the Order is garbage once nothing references it
```

### Virtual memory

Every process believes it has a huge, private, continuous address space. That is an illusion kept by
the OS and the CPU's memory-management unit (MMU).

- Memory is split into fixed-size **pages** (usually 4 KB). The page table maps each virtual page to a
  physical **frame**.
- **Isolation**: process A's page 1 and process B's page 1 are different physical memory, so one
  program cannot read another's data.
- **Overcommit**: a process can reserve far more than it touches; physical frames are handed out only on
  first use.
- **Page fault**: touching a page that is not in RAM traps into the OS, which loads it (from disk if it
  was swapped out). Minor faults are cheap; major faults (disk reads) are thousands of times slower.

### Swap and thrashing

When RAM runs out, the OS moves rarely used pages to disk (**swap**). A little swapping is harmless. A
lot is **thrashing**: the machine spends its time moving pages in and out, and everything slows to a
crawl. For a JVM this is especially bad, because garbage collection touches the whole heap.

<Callout type="prod" title="Containers and the OOM killer">
In Kubernetes, a container that exceeds its memory limit is killed by the kernel's OOM killer — exit
code 137, `OOMKilled`. That is not a Java `OutOfMemoryError`: the JVM never got a chance to throw. It
usually means the **whole process** (heap plus metaspace, thread stacks, direct buffers) outgrew the
limit, so size the heap as a percentage of the limit and leave headroom.
</Callout>

### Garbage collection, in one paragraph

In Java you never free memory. The garbage collector periodically finds objects that are no longer
reachable from live references (stack variables, static fields) and reclaims them. Because most objects
die young, the heap is split into generations and young objects are collected cheaply and often. A
**memory leak** in Java is therefore not "forgot to free" but "still referenced by accident" — an
ever-growing static map, for instance.

<Terminal title="memory at a glance (Linux)">
{`$ free -h                          # RAM and swap in use
$ vmstat 1                         # si/so columns: swap in/out per second
$ ps -o pid,rss,vsz,cmd -p 4242    # RSS = physical memory actually used
$ jcmd 4242 GC.heap_info           # the JVM's heap view`}
</Terminal>

**RSS** (resident set size) is memory really in RAM; **VSZ** (virtual size) includes reserved but
untouched memory — it is normal for VSZ to be huge.
