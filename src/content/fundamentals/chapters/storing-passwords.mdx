## Why it matters

Databases leak — through SQL injection, a stolen backup, an insider, a misconfigured bucket. When yours
does, the question is whether attackers get **passwords** (which people reuse on their email and bank)
or something useless to them. How you store passwords decides that.

You never need the original password back — to log in, you hash what the user typed and compare.
That is why **hashing**, not encryption, is right.

### Why a salt

Without a salt, the same password always has the same hash:

```text
sha256("password123") = ef92b778bafe771e89245b89ecbc08a44a4e166c06659911881f383d4473e94f
```

Attackers precompute hashes of common passwords (**rainbow tables**) and look leaked hashes up
instantly — and they can see which users share a password.

A **salt** is a random value, unique per user, stored next to the hash and mixed into it. Identical
passwords now produce different hashes, and precomputed tables are useless. The salt is not secret.

### Why slow

SHA-256 is designed to be fast — a GPU computes billions per second, so an attacker can try every
8-character password quickly. **Password hashing functions are deliberately slow and tunable**:

- **bcrypt** — a work factor (cost); each +1 doubles the time. Widely supported.
- **scrypt** — also memory-hard, which makes GPU and ASIC attacks expensive.
- **Argon2id** — winner of the Password Hashing Competition; configurable time, memory and parallelism.
  The current recommendation for new systems.
- **PBKDF2** — many iterations of HMAC; acceptable where compliance requires it.

Tune the cost so one hash takes a noticeable fraction of a second (for example 100–500 ms) on your
servers. A user logs in once; an attacker must pay that price for every guess.

A bcrypt string such as `$2a$12$R9h/cIPz0gi.URNNX3kh2O…` contains the algorithm (`2a`), cost (`12`),
salt and hash together — you store just this one value.

### In code

```java
PasswordEncoder encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();

String stored = encoder.encode(rawPassword);        // "{bcrypt}$2a$10$…" — algorithm id prefixed
boolean ok = encoder.matches(attempt, stored);      // re-hashes with the stored salt and cost
if (encoder.upgradeEncoding(stored)) { /* re-hash with the current algorithm after a good login */ }
```

The `{id}` prefix lets you move to a stronger algorithm over time: new passwords use the new one, and
old ones are upgraded as users log in.

### Beyond hashing

- **Pepper**: an extra secret mixed in and kept outside the database (in a KMS), so a database-only leak
  is not enough.
- **Rate limiting and lockouts** slow online guessing; **MFA** makes a stolen password insufficient.
- **Check against breached-password lists** at registration.
- **Length over complexity rules**: allow long passphrases; do not force periodic changes without cause.
- **Never log passwords** — watch request logging and exception messages.
- **Comparisons in constant time** — libraries do this for you.
- **Password resets**: send a single-use, short-lived, random token; never email the password.

## When you'll meet it

- **"Can support tell the user their password?"** No — and if they could, the design is wrong.
- **Migrating from MD5 or SHA-1 hashes** — wrap them (bcrypt of the old hash) immediately, then upgrade on login.
- **Login endpoint too slow under load** — the cost factor is working; scale the auth service, add rate limits.
- **API keys and tokens** — store a hash of them too (a fast hash is fine for long random tokens, since they cannot be guessed).
- **Interview:** "How should passwords be stored? What is a salt? Why not SHA-256?"
