## The three ways to inject

<DecisionTable
  columns={['How', 'Use it', 'Why']}
  rows={[
    {
      label: 'Constructor',
      verdict: 'good',
      cells: ['Parameters of the constructor', 'Always, for required dependencies', 'Fields can be final; the object is never half-built; tests just call new'],
    },
    {
      label: 'Setter',
      verdict: 'mixed',
      cells: ['@Autowired on a setter', 'Genuinely optional or re-configurable collaborators', 'The object is usable before the setter runs, so the dependency must be optional'],
    },
    {
      label: 'Field',
      verdict: 'bad',
      cells: ['@Autowired on a field', 'Not in application code', 'Hides dependencies, cannot be final, tests need reflection or a Spring context'],
    },
  ]}
/>

```java title="The default shape — no @Autowired needed"
@Service
public class NotificationService {

    private final PreferenceRepository preferences;
    private final List<MessageSender> senders;

    public NotificationService(PreferenceRepository preferences, List<MessageSender> senders) {
        this.preferences = preferences;
        this.senders = senders;
    }
}
```

<Callout type="tip" title="When you actually need @Autowired">
Only when a class has **more than one constructor** — then mark the one Spring should use. With a
single constructor Spring uses it automatically, and the annotation is noise. A constructor with
seven parameters is not a reason to switch to field injection; it is a class doing too much.
</Callout>

## How Spring picks a bean

Every injection point is resolved **by type** first. When more than one bean matches, Spring narrows
in this order and stops at the first rule that leaves exactly one:

<Mermaid
  caption="By type, then qualifier, then primary, then name. If none of them leaves one bean, startup fails."
  alt="Flowchart of Spring's bean resolution: match by type; if several, filter by @Qualifier, then by @Primary, then by matching the parameter name to a bean name; otherwise fail with NoUniqueBeanDefinitionException."
  chart={`

    B -->|"1"| OK["inject it"]

    Q -->|"yes"| OK
    Q -->|"no"| P{"exactly one<br/>@Primary?"}
    P -->|"yes"| OK
    P -->|"no"| N{"a bean named like the<br/>parameter or field?"}
    N -->|"yes"| OK
    N -->|"no"| Y["NoUniqueBeanDefinitionException"]

    classDef err fill:#3a1414,stroke:#f87171,color:#f87171;

    class X,Y err;

/>

<Callout type="pitfall" title="The name fallback works — until someone renames a parameter">
`MessageSender smsSender` quietly resolves to the bean named `smsSender`. It is real behaviour, and
it is fragile: rename the parameter and the application either fails or, worse, picks something else.
Say what you mean with `@Qualifier`.
</Callout>

## Several beans of one type

<DecisionTable
  columns={['What it does', 'Use when']}
  rows={[
    { label: '@Qualifier("name")', verdict: 'good', cells: ['Picks one, visibly, at the injection point', 'This caller needs a specific implementation'] },
    { label: '@Primary', verdict: 'mixed', cells: ['Makes one the default everywhere', 'Overriding an auto-configured bean; a true default with rare exceptions'] },
    { label: 'List<T>', verdict: 'good', cells: ['Injects all of them, in @Order order', 'Strategies, handlers, validators — iterate or pick at runtime'] },
    { label: 'Map<String, T>', verdict: 'good', cells: ['All of them, keyed by bean name', 'Choosing an implementation by a runtime value'] },
    { label: 'Custom qualifier', verdict: 'good', cells: ['An annotation meta-annotated with @Qualifier', 'Many injection points; avoids stringly-typed names'] },
  ]}
/>

```java title="Picking at runtime instead of at wiring time"
public NotificationService(Map<String, MessageSender> sendersByName) {
    this.senders = sendersByName;        // {"emailSender" -> …, "smsSender" -> …}
}

void send(Channel channel, Message message) {
    senders.get(channel.beanName()).send(message);
}
```

Often the real answer to "which bean do I inject?" is **all of them** — the need for `@Qualifier` in
five places is usually a strategy pattern asking to be written.

## Optional, lazy and late dependencies

<DecisionTable
  columns={['Behaviour', 'Prefer it for']}
  rows={[
    { label: 'Optional<T>', verdict: 'good', cells: ['Empty when no bean exists', 'A collaborator that may not be configured'] },
    { label: 'ObjectProvider<T>', verdict: 'good', cells: ['Lazy lookup; getIfAvailable, getIfUnique, stream', 'Optional or prototype beans, and avoiding eager creation'] },
    { label: '@Lazy', verdict: 'mixed', cells: ['Injects a proxy resolved on first call', 'Expensive, rarely used beans'] },
    { label: '@Autowired(required = false)', verdict: 'bad', cells: ['Leaves the field null', 'Nothing — the null surfaces far from the cause'] },
  ]}
/>

```java
public ReportService(ObjectProvider<PdfRenderer> renderer) {
    this.renderer = renderer;
}

Report render(Report report) {
    return renderer.getIfAvailable(PlainTextRenderer::new).render(report);
}
```

## @Autowired, @Inject and @Resource

<DecisionTable
  columns={['Comes from', 'Resolves by', 'Notes']}
  rows={[
    { label: '@Autowired', cells: ['Spring', 'Type, then qualifier / primary / name', 'Has required = false'] },
    { label: '@Inject', cells: ['JSR-330 (jakarta.inject)', 'Type, like @Autowired', 'No required flag; use Optional or Provider'] },
    { label: '@Resource', cells: ['JSR-250 (jakarta.annotation)', 'Name first, then type', 'Fields and setters only — not constructors'] },
  ]}
/>

In a Spring application the choice rarely matters; constructor injection with no annotation at all
makes it disappear. `@Resource` is the one that behaves differently — it looks the bean up by **name**
before type.

## Circular dependencies

Spring Boot refuses them by default (`spring.main.allow-circular-references=false`), and constructor
injection cannot express them at all — which is a feature.

<Compare>
  <Bad title="Paper over it">

`@Lazy` on one side, or switching to field injection, makes the cycle compile and keeps the design
problem.

```java
public OrderService(@Lazy InvoiceService invoices) { … }
```

  </Bad>
  <Good title="Break it">

Two services that call each other usually share a responsibility. Extract it into a third class both
depend on, or replace one direction with an application event.

```java
public OrderService(PricingPolicy pricing) { … }
public InvoiceService(PricingPolicy pricing) { … }
```

  </Good>
</Compare>
