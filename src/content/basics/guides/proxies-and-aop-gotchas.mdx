## Which annotations are proxy-based

Many of Spring's most useful annotations do nothing by themselves. A **proxy** wrapped around your
bean intercepts calls and adds the behaviour.

## The six ways the annotation does nothing

<DecisionTable
  columns={['Why', 'Fix']}
  rows={[
    { label: 'Self-invocation', verdict: 'bad', cells: ['this.method() never passes through the proxy', 'Move the method to another bean'] },
    { label: 'Private method', verdict: 'bad', cells: ['Proxies cannot intercept private methods', 'Make it public, on a separate bean'] },
    { label: 'Final method or class', verdict: 'bad', cells: ['CGLIB cannot override final members', 'Remove final (Kotlin: the all-open plugin)'] },
    { label: 'Created with new', verdict: 'bad', cells: ['Spring never saw the object', 'Inject it'] },
    { label: 'Called from @PostConstruct', verdict: 'bad', cells: ['Proxies are created after initialisation', 'Use ApplicationReadyEvent'] },
    { label: 'Missing @Enable…', verdict: 'bad', cells: ['No advisor is registered at all', 'Add @EnableAsync / @EnableCaching'] },
  ]}
/>

<Compare>
  <Bad title="Self-invocation">

`audit` is marked `REQUIRES_NEW`, but it is called through `this`, so it runs inside `place`'s
transaction — and rolls back with it.

```java
@Service
public class OrderService {
    @Transactional
    public void place(Order order) {
        orders.save(order);
        audit(order);                        // this.audit() — no proxy
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void audit(Order order) { … }
}
```

  </Bad>
  <Good title="A separate bean">

The call now goes through `AuditService`'s proxy, so the new transaction really starts.

```java
@Service
public class OrderService {
    private final AuditService audit;

    @Transactional
    public void place(Order order) {
        orders.save(order);
        audit.record(order);                 // through the proxy
    }
}
```

  </Good>
</Compare>

<Callout type="pitfall" title="Injecting yourself is not the fix">
Self-injection (`@Lazy OrderService self`) or `AopContext.currentProxy()` does make the call go through
the proxy. It also means the class depends on its own proxy, which is confusing to read and easy to
break. A second bean is clearer.
</Callout>

## JDK or CGLIB

<DecisionTable
  columns={['How it works', 'Limitation']}
  rows={[
    { label: 'JDK dynamic proxy', cells: ['Implements the bean’s interfaces', 'Injecting the concrete class fails — the proxy is not one'] },
    { label: 'CGLIB proxy', verdict: 'good', cells: ['Subclasses the bean’s class', 'Final classes and final methods cannot be advised'] },
  ]}
/>

Spring Boot uses **CGLIB by default** (`spring.aop.proxy-target-class=true`), so you can inject either
the interface or the class.

## How to check in ten seconds

```java
@Autowired OrderService orders;

@Test
void is_proxied() {
    assertThat(AopUtils.isAopProxy(orders)).isTrue();
    // Or print it: dev.acme.OrderService$$SpringCGLIB$$0
    System.out.println(orders.getClass());
}
```

And to confirm the advice actually ran, turn on the relevant logger:

```yaml
logging.level:
  org.springframework.transaction.interceptor: TRACE   # "Getting transaction for …"
  org.springframework.orm.jpa.JpaTransactionManager: DEBUG
```

If the log line is missing for the call you care about, the proxy was bypassed.
