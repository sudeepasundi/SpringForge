## The problem JDBC solves

Every database speaks its own network protocol. MySQL, PostgreSQL, Oracle and SQL Server all accept
SQL, but the bytes that carry it are different for each.

**JDBC** (Java Database Connectivity) is the standard Java API that hides that difference. Your code
talks to a set of interfaces in `java.sql`; a **driver** — a jar supplied by the database vendor —
implements those interfaces for one particular database.

Swap the driver jar and the URL, and the same Java code runs against a different database — as long
as the SQL itself is portable.

## DriverManager or DataSource

```java title="DriverManager — fine for a quick experiment"
try (Connection con = DriverManager.getConnection(
        "jdbc:mysql://localhost:3306/shelf", "shelf_app", "shelf-app-pass")) {
    // …
}
```

`DriverManager` opens a **brand-new physical connection** every time. That means a TCP handshake,
authentication and session setup — tens of milliseconds — on every call.

```java title="DataSource — what real applications use"
public PlainJdbcBookDao(DataSource dataSource) {
    this.dataSource = dataSource;           // injected, usually a HikariCP pool
}

try (Connection con = dataSource.getConnection()) {    // borrowed from the pool
    // …
}                                                      // close() returns it to the pool
```

<Callout type="tip" title="close() on a pooled connection does not close it">
With a pool, `close()` hands the connection back for reuse. That is why you must **always** close it —
forgetting to is not a small leak, it is a pool that runs dry and an application that hangs.
</Callout>

## Where Spring fits

Plain JDBC is verbose: open, prepare, bind, execute, loop, map, close, and turn every checked
`SQLException` into something useful. Spring offers several layers on top, from thin to thick.

This section is about the first two. Everything else in Spring's data stack is built on them, so
understanding them is what lets you debug the rest.

## Everything goes through one Connection

<Steps>
  <Step title="Borrow a Connection">

From the `DataSource`. It carries the session: time zone, transaction state, isolation level.

  </Step>
  <Step title="Create a statement">

`prepareStatement(sql)` for anything with input. The SQL is fixed; values are bound afterwards.

  </Step>
  <Step title="Execute">

`executeQuery()` for SELECT, `executeUpdate()` for INSERT/UPDATE/DELETE.

  </Step>
  <Step title="Read the ResultSet">

Move the cursor with `next()`, read columns with `getString`, `getLong`, `getObject`…

  </Step>
  <Step title="Close everything, in reverse order">

ResultSet, then statement, then connection — which `try`-with-resources does for you.

  </Step>
</Steps>
