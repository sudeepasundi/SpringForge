## @Transactional over JDBC

With `spring-boot-starter-jdbc`, Boot registers a `DataSourceTransactionManager`. Annotate a service
method and every `JdbcTemplate`, `NamedParameterJdbcTemplate` and `JdbcClient` call inside it uses
**the same connection**, committed or rolled back together.

```java
@Transactional
public long borrow(long bookId, long memberId) {
    int taken = jdbc.update("UPDATE book SET copies_available = copies_available - 1 "
            + "WHERE id = ? AND copies_available > 0", bookId);
    if (taken == 0) {
        throw new NoCopiesAvailableException(bookId);      // rolls back
    }
    return loans.open(bookId, memberId, dueDate());         // JdbcClient, same transaction
}
```

This is the plain-JDBC transaction from [Transactions in Plain JDBC](/jdbc/jdbc-transactions),
written for you. The same rules as elsewhere in Spring apply — it works through a proxy, so it is
ignored on self-invocation and private methods; see
[Proxies & AOP Gotchas](/basics/proxies-and-aop-gotchas) and the
[transactions cheat sheet](/basics/transactions-cheat-sheet).

<Callout type="pitfall" title="Raw connections bypass the transaction">
`dataSource.getConnection()` inside a `@Transactional` method returns a **different** connection,
outside the transaction. If you must touch JDBC directly, use `DataSourceUtils.getConnection(dataSource)`
(and `releaseConnection`), or `jdbc.execute((Connection con) -> …)`, which both return the bound one.
</Callout>

### Useful attributes

```java
@Transactional(readOnly = true, timeout = 5)
public List<Book> catalogue() { … }

@Transactional(isolation = Isolation.READ_COMMITTED)
public void recount() { … }

@Transactional(rollbackFor = IOException.class)      // checked exceptions commit by default
public void importFile(Path file) throws IOException { … }
```

`readOnly = true` marks the connection read-only — Connector/J passes that to MySQL as a read-only
transaction — and lets a routing `DataSource` send the work to a replica.

## From SQLException to DataAccessException

Spring translates vendor error codes into a hierarchy of **unchecked** exceptions, so your code can
react to *what* went wrong without parsing MySQL error numbers.

```java
try {
    return loans.open(bookId, memberId, dueDate());
} catch (DuplicateKeyException e) {
    // uk_loan_open: this member already has this book
    throw new AlreadyBorrowedException(bookId, memberId, e);
}
```

<Callout type="tip" title="Let the constraint decide">
Checking "does this row exist?" before inserting has a race between the check and the insert. A
unique constraint plus `DuplicateKeyException` is both simpler and correct under concurrency.
</Callout>

<Callout type="pitfall" title="A caught exception can still doom the transaction">
Catching `DuplicateKeyException` inside the transaction is fine with plain JDBC — MySQL rolls back
only the failed statement. But if the exception passed through another `@Transactional` method
first, Spring has already marked the transaction rollback-only, and the commit later fails with
`UnexpectedRollbackException`. Catch it in the method that owns the transaction, or rethrow.
</Callout>

## Deadlocks and retries

InnoDB detects deadlocks and rolls back one of the transactions involved (error 1213). The whole
transaction is gone, so the only correct retry is to **run it again from the start** — from outside
the `@Transactional` method.

<Compare>
  <Bad title="Retrying inside the transaction">

The transaction was already rolled back; retrying the statement inside it cannot work.

```java
@Transactional
public long borrow(long bookId, long memberId) {
    try {
        return doBorrow(bookId, memberId);
    } catch (PessimisticLockingFailureException e) {
        return doBorrow(bookId, memberId);      // same dead transaction
    }
}
```

  </Bad>
  <Good title="Retrying around the transaction">

Each attempt calls the proxied method again, so each gets a new transaction.

```java
public long borrow(long bookId, long memberId) {       // not @Transactional
    for (int attempt = 1; ; attempt++) {
        try {
            return loanService.borrow(bookId, memberId);
        } catch (PessimisticLockingFailureException e) {
            if (attempt == 3) throw e;
            sleep(50L * attempt);
        }
    }
}
```

  </Good>
</Compare>

Spring Retry's `@Retryable` does the same declaratively — as long as it sits *outside* the
transaction boundary. To make deadlocks rarer: touch rows in a consistent order, keep transactions
short, and consider `READ COMMITTED`.
