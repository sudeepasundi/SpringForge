## Auto-commit is the default

A new JDBC connection is in **auto-commit** mode: every statement is its own transaction and is
committed as soon as it finishes.

That is wrong the moment two statements must succeed or fail together. Borrowing a book takes a copy
off the shelf **and** records the loan; if the second fails, the first must not stay.

## The pattern

```java
try (Connection con = dataSource.getConnection()) {
    con.setAutoCommit(false);                     // BEGIN
    try {
        takeCopy(con, bookId);
        long loanId = insertLoan(con, bookId, memberId);
        con.commit();                             // COMMIT
        return loanId;
    } catch (SQLException | RuntimeException e) {
        con.rollback();                           // ROLLBACK
        throw e;
    } finally {
        con.setAutoCommit(true);                  // leave the pooled connection clean
    }
}
```

Every statement in the transaction must use **the same `Connection`** — which is why the helper
methods take `con` as a parameter instead of borrowing their own.

<Callout type="pitfall" title="setAutoCommit(true) commits">
The JDBC specification says that changing auto-commit during a transaction commits it. If an
exception escapes without a rollback — say, you only caught `SQLException` and a
`RuntimeException` was thrown — the `finally` block quietly commits half the work. Roll back on
**every** failure before restoring auto-commit.
</Callout>

## Savepoints: undo part of a transaction

A savepoint marks a point you can roll back to without abandoning the whole transaction.

```java
Savepoint beforeAudit = con.setSavepoint("before_audit");
try {
    insertAudit(con, loanId, "checked out");
} catch (SQLException auditFailed) {
    con.rollback(beforeAudit);      // undo the audit only; the checkout survives
}
con.commit();
```

Use them sparingly — for genuinely optional steps. If you find yourself needing many, the work
probably wants to be split into separate transactions.

## Isolation levels

Isolation decides what one transaction can see of another's uncommitted or newly committed work.

```java
con.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);
```

<Callout type="tip" title="InnoDB is different from most databases here">
MySQL's InnoDB defaults to **REPEATABLE READ**, where PostgreSQL and SQL Server default to
READ COMMITTED. Under REPEATABLE READ, plain `SELECT`s read a snapshot taken at the first read, so
repeated reads in one transaction agree — but `SELECT … FOR UPDATE` and `UPDATE` see the latest
committed data. Many teams switch to READ COMMITTED for fewer gap locks and fewer deadlocks.
</Callout>

## Locking a row you are about to change

```java
try (PreparedStatement ps = con.prepareStatement(
        "SELECT copies_available FROM book WHERE id = ? FOR UPDATE")) {
    ps.setLong(1, bookId);
    // other transactions that try to lock or update this row now wait
}
```

`SELECT … FOR UPDATE` only means something inside a transaction; with auto-commit on, the lock is
released immediately. Often a conditional `UPDATE … WHERE copies_available > 0` does the same job
with no explicit lock at all.

## Keep transactions short

A transaction holds locks and a connection until it ends. Never keep one open while waiting on a
user, calling a remote service, or sending an email.

Spring manages all of this declaratively with `@Transactional` — see
[Spring Transactions and Exceptions](/jdbc/spring-transactions-and-errors). Knowing the manual
version is what makes that annotation predictable.
