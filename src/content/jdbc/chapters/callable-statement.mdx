## Stored procedures, briefly

A stored procedure is a named block of SQL kept in the database and run with `CALL`. It can take
parameters, change data, and return rows.

<DecisionTable
  columns={['Why teams use them', 'Why teams avoid them']}
  rows={[
    { label: 'Logic', cells: ['Runs next to the data, one round trip', 'Business rules split between Java and SQL'] },
    { label: 'Security', cells: ['Grant EXECUTE instead of table access', 'Another thing to version and review'] },
    { label: 'Testing', verdict: 'mixed', cells: ['—', 'Needs a real database; harder to unit test'] },
    { label: 'Deploying', verdict: 'mixed', cells: ['—', 'Changes ship through migrations, not the app'] },
  ]}
/>

A sensible default: keep business logic in Java, and use procedures when a legacy database already
has them or when one round trip genuinely matters. Either way you need to know how to call them.

## Writing one in MySQL

```sql
DELIMITER //

CREATE PROCEDURE checkout_book(
    IN  p_book_id   BIGINT,
    IN  p_member_id BIGINT,
    IN  p_days      INT,
    OUT p_loan_id   BIGINT)
BEGIN
    UPDATE book SET copies_available = copies_available - 1
     WHERE id = p_book_id AND copies_available > 0;

    IF ROW_COUNT() = 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'No copies available';
    END IF;

    INSERT INTO loan (book_id, member_id, due_on)
    VALUES (p_book_id, p_member_id, DATE_ADD(CURRENT_DATE, INTERVAL p_days DAY));

    SET p_loan_id = LAST_INSERT_ID();
END //

DELIMITER ;
```

<Callout type="tip" title="What DELIMITER is for">
The procedure body contains `;`, which the `mysql` client would treat as the end of the statement.
`DELIMITER //` changes the terminator temporarily. It is a client command, not SQL — Flyway
understands it in MySQL migrations; plain JDBC does not need it, because `executeUpdate` sends one
statement at a time.
</Callout>

<Terminal title="try it by hand">
{`mysql> CALL checkout_book(1, 1, 21, @loan);
mysql> SELECT @loan;
mysql> SHOW PROCEDURE STATUS WHERE Db = 'shelf';
mysql> SHOW CREATE PROCEDURE checkout_book\\G`}
</Terminal>

## Calling with CallableStatement

The JDBC escape syntax `{call name(?, ?)}` works with every driver; MySQL also accepts plain
`CALL name(?, ?)`.

```java title="IN and OUT"
try (CallableStatement cs = con.prepareCall("{call checkout_book(?, ?, ?, ?)}")) {
    cs.setLong(1, bookId);                          // IN
    cs.setLong(2, memberId);                        // IN
    cs.setInt(3, 21);                               // IN
    cs.registerOutParameter(4, Types.BIGINT);       // OUT — before execute()

    cs.execute();
    long loanId = cs.getLong(4);
}
```

```java title="INOUT"
try (CallableStatement cs = con.prepareCall("{call apply_discount(?, ?)}")) {
    cs.setBigDecimal(1, new BigDecimal("20.00"));   // value in
    cs.registerOutParameter(1, Types.DECIMAL);      // result out, same index
    cs.setInt(2, 15);
    cs.execute();
    BigDecimal discounted = cs.getBigDecimal(1);    // 17.00
}
```

```java title="A procedure that returns rows"
try (CallableStatement cs = con.prepareCall("{call books_by_author(?)}")) {
    cs.setLong(1, authorId);
    boolean hasResultSet = cs.execute();            // true: first result is rows
    if (hasResultSet) {
        try (ResultSet rs = cs.getResultSet()) {
            while (rs.next()) { … }
        }
    }
}
```

<Callout type="tip" title="More than one result">
A procedure can run several `SELECT`s. Read the first with `getResultSet()`, then call
`getMoreResults()` to move to the next; it returns `false` when the next result is an update count or
there are no more.
</Callout>

## The transaction trap

<Callout type="pitfall" title="With auto-commit on, each statement inside the procedure commits on its own">
MySQL does not wrap a procedure call in a transaction. If the `UPDATE` succeeds and the `INSERT`
fails, the copy is gone and no loan exists. Turn auto-commit off around the call and commit or roll
back yourself — or call it from a Spring `@Transactional` method, which does that for you.
</Callout>

`SIGNAL SQLSTATE '45000'` reaches Java as an `SQLException` whose `getSQLState()` is `"45000"` and
whose message is the `MESSAGE_TEXT` — which is how a procedure reports a business error.

For the Spring way to call procedures, with parameters looked up from database metadata, see
[SimpleJdbcCall](/jdbc/keys-and-simple-jdbc).
