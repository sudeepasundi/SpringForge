## Opening and closing, safely

Every JDBC object that talks to the database — `Connection`, `Statement`, `ResultSet` — holds a
resource and must be closed. `try`-with-resources closes them in reverse order, even when an
exception is thrown.

<Compare>
  <Bad title="Manual close">

If `executeQuery` throws, nothing is closed and the connection leaks. The `finally` versions of this
are longer, and still usually wrong.

```java
Connection con = dataSource.getConnection();
Statement st = con.createStatement();
ResultSet rs = st.executeQuery("SELECT COUNT(*) FROM book");
rs.next();
int count = rs.getInt(1);
con.close();                        // never reached on failure
```

  </Bad>
  <Good title="try-with-resources">

Each resource declared in the parentheses is closed automatically, last-opened first.

```java
try (Connection con = dataSource.getConnection();
     Statement st = con.createStatement();
     ResultSet rs = st.executeQuery("SELECT COUNT(*) FROM book")) {
    rs.next();
    return rs.getInt(1);
}
```

  </Good>
</Compare>

## Statement and its three execute methods

A `Statement` runs a SQL string exactly as given. Use it only for SQL that contains **no input from
anywhere** — the next chapter explains why.

```java
try (Connection con = dataSource.getConnection();
     Statement st = con.createStatement()) {

    st.executeUpdate("CREATE TABLE IF NOT EXISTS tag (id INT PRIMARY KEY, name VARCHAR(50))");

    int rows = st.executeUpdate("DELETE FROM loan_audit WHERE created_at < NOW() - INTERVAL 1 YEAR");
    System.out.println(rows + " old audit rows removed");

    boolean isQuery = st.execute("SHOW TABLES");
    if (isQuery) {
        try (ResultSet rs = st.getResultSet()) { /* … */ }
    } else {
        System.out.println(st.getUpdateCount() + " rows");
    }
}
```

## Reading a ResultSet

A `ResultSet` is a **cursor**. It starts *before* the first row; each `next()` moves forward one row
and returns `false` when there are no more.

<Mermaid
  caption="next() moves the cursor, getX() reads the current row. Calling getX() before the first next() throws."
  alt="Diagram of a ResultSet cursor starting before the first row, advancing with next() through three rows, and returning false after the last."
  chart={`
flowchart LR
    S["before first"] -->|"next() → true"| R1["row 1"]
    R1 -->|"next() → true"| R2["row 2"]
    R2 -->|"next() → true"| R3["row 3"]
    R3 -->|"next() → false"| E["after last"]
`}
/>

```java
try (ResultSet rs = ps.executeQuery()) {
    List<Book> books = new ArrayList<>();
    while (rs.next()) {                                 // zero or more rows
        books.add(new Book(
                rs.getLong("id"),                        // by column label
                rs.getString(2),                         // or by 1-based position
                rs.getString("title"),
                rs.getLong("author_id"),
                rs.getObject("published_on", LocalDate.class),
                rs.getBigDecimal("price"),
                rs.getInt("copies_available")));
    }
    return books;
}
```

<Callout type="tip" title="Label or index?">
Column labels are clearer and survive a reordered `SELECT`. Indexes are marginally faster and are the
only option when two columns share a name. If the query uses an alias (`SELECT COUNT(*) AS total`),
the label is the alias.
</Callout>

### NULL is the trap

Primitive getters cannot return `null`, so they return a default instead.

<Compare>
  <Bad title="getInt on a nullable column">

`born_year` is `NULL` for an author whose birth year is unknown — and `getInt` quietly returns `0`,
which is a real year.

```java
int bornYear = rs.getInt("born_year");     // NULL → 0
```

  </Bad>
  <Good title="getObject with a wrapper type">

`getObject(…, Integer.class)` returns `null` for SQL `NULL`. (`rs.wasNull()` right after a getter is
the older way to check.)

```java
Integer bornYear = rs.getObject("born_year", Integer.class);   // NULL → null
```

  </Good>
</Compare>

### What is in the result: ResultSetMetaData

```java
ResultSetMetaData meta = rs.getMetaData();
for (int i = 1; i <= meta.getColumnCount(); i++) {
    System.out.printf("%s %s nullable=%s%n",
            meta.getColumnLabel(i),
            meta.getColumnTypeName(i),
            meta.isNullable(i) == ResultSetMetaData.columnNullable);
}
```

Useful for generic tools — exporters, admin screens — where the columns are not known in advance.

## ResultSet options you will rarely need

`createStatement` and `prepareStatement` accept a result set **type** and **concurrency**.

<DecisionTable
  columns={['What it allows']}
  rows={[
    { label: 'TYPE_FORWARD_ONLY', verdict: 'good', cells: ['next() only — the default, and the fastest'] },
    { label: 'TYPE_SCROLL_INSENSITIVE', cells: ['previous(), absolute(n), last() on a snapshot'] },
    { label: 'CONCUR_READ_ONLY', verdict: 'good', cells: ['Read the rows — the default'] },
    { label: 'CONCUR_UPDATABLE', verdict: 'bad', cells: ['rs.updateString(…) then rs.updateRow() — write UPDATE statements instead'] },
  ]}
/>

For pagination, use `LIMIT … OFFSET` (or keyset pagination) in SQL rather than scrolling a large
result in Java.
