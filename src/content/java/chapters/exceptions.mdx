## The hierarchy

- **`Error`** — something is wrong with the JVM itself (out of memory, stack overflow). Do not catch
  these in application code.
- **Checked exceptions** — `Exception` and its subclasses *except* `RuntimeException`. The compiler
  forces every caller to catch or declare them.
- **Unchecked exceptions** — `RuntimeException` and its subclasses. No declaration needed.

Modern frameworks lean unchecked: Spring translates `SQLException` into its unchecked
`DataAccessException` hierarchy, and most application code throws unchecked domain exceptions that a
single handler turns into an HTTP response.

## `try`, `catch`, `finally`

```java
try {
    process(file);
} catch (FileNotFoundException e) {          // more specific first
    log.warn("Missing {}", file);
} catch (IOException | ParseException e) {   // multi-catch (Java 7): e is effectively final
    throw new ImportException("Cannot import " + file, e);
} finally {
    metrics.increment();                     // always runs — success, exception or return
}
```

<Callout type="pitfall" title="return in finally">
A `return` (or a new `throw`) inside `finally` silently **discards** the exception that was being
thrown. Never return from `finally`.
</Callout>

## try-with-resources

Anything implementing `AutoCloseable` can be declared in the `try` header. It is closed automatically,
in reverse order, however the block exits.

<Compare>
  <Bad title="Manual closing">

```java
BufferedReader reader = null;
try {
    reader = Files.newBufferedReader(path);
    return reader.readLine();
} finally {
    if (reader != null) {
        reader.close();     // if this throws, it hides the original exception
    }
}
```

  </Bad>
  <Good title="try-with-resources (Java 7)">

```java
try (BufferedReader reader = Files.newBufferedReader(path);
     BufferedWriter writer = Files.newBufferedWriter(out)) {
    writer.write(reader.readLine());
}   // writer closed, then reader
```

  </Good>
</Compare>

### Suppressed exceptions

If the body throws and then `close()` also throws, the body's exception is the one that propagates;
the close failure is attached to it rather than lost.

```java
catch (IOException e) {
    for (Throwable s : e.getSuppressed()) log.warn("Also failed while closing", s);
}
```

Since Java 9 you can also list an existing effectively-final variable: `try (reader) { … }`.

## Custom exceptions

```java
public class InsufficientFundsException extends RuntimeException {
    private final long accountId;

    public InsufficientFundsException(long accountId, Money requested, Money available) {
        super("Account %d cannot pay %s (balance %s)".formatted(accountId, requested, available));
        this.accountId = accountId;
    }

    public long accountId() { return accountId; }
}
```

- Extend `RuntimeException` unless you have a strong reason for a checked exception.
- Name the problem, not the location: `OrderNotFoundException`, not `ServiceException`.
- Put the useful facts in fields **and** in the message.
- Always offer a constructor that takes a `cause`.

## Rules that hold up

<Compare>
  <Bad title="Swallowing">

```java
try {
    charge(card);
} catch (Exception e) {
    // ignore
}
```

The payment failed and nobody will ever know.

  </Bad>
  <Good title="Handle, or let it go">

```java
try {
    charge(card);
} catch (CardDeclinedException e) {
    return PaymentResult.declined(e.reason());   // a real recovery
}
// anything else propagates to a handler that logs it once
```

  </Good>
</Compare>

<Compare>
  <Bad title="Losing the cause">

```java
catch (SQLException e) {
    throw new RepositoryException("Save failed");   // the stack trace of the real problem is gone
}
```

  </Bad>
  <Good title="Wrapping with the cause">

```java
catch (SQLException e) {
    throw new RepositoryException("Save failed for order " + id, e);
}
```

  </Good>
</Compare>

More rules:

- **Catch what you can handle**, where you can handle it. Otherwise let it propagate.
- **Log or rethrow, not both** — logging at every layer produces the same stack trace five times.
- **Do not catch `Exception` or `Throwable`** except at the outermost boundary (a request handler, a
  thread's run method), and never `Error`.
- **Do not use exceptions for normal control flow** — they are slow to create (stack trace capture)
  and hide the real logic.
- **Fail fast**: validate arguments at the start of public methods (`Objects.requireNonNull`,
  `IllegalArgumentException`).
- **Restore the interrupt flag** if you catch `InterruptedException` and cannot rethrow it:
  `Thread.currentThread().interrupt();`
