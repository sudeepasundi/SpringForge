## An "is-a" relationship

`class SavingsAccount extends Account` says a savings account **is an** account: it has everything an
account has, and may add or change behaviour. The subclass inherits every non-private field and method;
it can **add** new ones and **override** inherited ones.

Java has **single inheritance** of classes: a class extends exactly one parent (`Object` if you say
nothing). It may implement any number of interfaces — the next chapters cover why that difference exists.

## Constructors are not inherited

A subclass must build its parent part first. Its constructor calls `super(...)`, explicitly or
implicitly.

```java
public class CheckingAccount extends Account {
    private final Money overdraftLimit;

    public CheckingAccount(String name, Money opening, Money overdraftLimit) {
        super(name, opening);               // must be first
        this.overdraftLimit = overdraftLimit;
    }
}
```

If you leave out `super(...)`, the compiler inserts `super()` — which fails to compile when the parent
has no no-argument constructor. That error message ("constructor Account in class Account cannot be
applied to given types") is almost always this.

## Overriding

A subclass **overrides** a method by declaring one with the same name and parameter types.

```java
@Override
protected boolean canWithdraw(Money amount) {
    return !balance().minus(amount).plus(overdraftLimit).isNegative();
}
```

<Callout type="tip" title="Always write @Override">
It costs nothing and turns a silent mistake into a compile error. Without it, `public boolean
equals(Money other)` compiles happily — as a new *overload* that `HashSet` will never call.
</Callout>

### `super.method()`

Inside an override, `super.method()` calls the parent's version, so you can extend rather than
replace it:

```java
@Override
public String toString() {
    return super.toString() + " (overdraft " + overdraftLimit + ")";
}
```

## `final`

- A `final` **class** cannot be extended (`String`, `Money`).
- A `final` **method** cannot be overridden. `Account.withdraw` is final so no subclass can skip its checks.
- A `final` **variable** cannot be reassigned.

## What `protected` really means

`protected` members are visible to subclasses — and to *every class in the same package*. That makes
it wider than people expect. Use it for hooks a subclass is meant to implement or call, not as a
general "semi-private".

## Why deep hierarchies hurt

Inheritance couples a subclass to its parent's **implementation**, not just its interface. When the
parent changes how its methods call each other, subclasses can break without any of their own code
changing.

<Compare>
  <Bad title="The fragile base class">

```java
public class CountingSet<E> extends HashSet<E> {
    private int added;

    @Override public boolean add(E e) { added++; return super.add(e); }

    @Override public boolean addAll(Collection<? extends E> c) {
        added += c.size();
        return super.addAll(c);   // HashSet.addAll calls add() for each element...
    }
}

set.addAll(List.of("a", "b", "c"));
set.added;   // 6, not 3
```

The subclass depended on an undocumented detail of `HashSet`. A future JDK could change it again.

  </Bad>
  <Good title="Wrap it instead">

```java
public class CountingSet<E> {
    private final Set<E> inner = new HashSet<>();
    private int added;

    public boolean add(E e)  { added++; return inner.add(e); }
    public boolean addAll(Collection<? extends E> c) {
        added += c.size();
        return inner.addAll(c);   // inner's internals no longer matter
    }
}
```

This is composition, covered in the SOLID chapter.

  </Good>
</Compare>

Rules of thumb:

- Inherit only when the subclass truly **is a** parent everywhere the parent is used (the Liskov
  substitution principle).
- Design classes for inheritance deliberately — `abstract` with documented hooks, like `Account` — or
  make them `final`.
- Keep hierarchies shallow. Two levels is common; four is a warning sign.
