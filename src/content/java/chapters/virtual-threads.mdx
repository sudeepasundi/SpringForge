## The problem virtual threads solve

A classic web server handles each request on its own **platform thread** — a thin wrapper around an
operating-system thread. OS threads are expensive: each reserves around a megabyte of stack, and
switching between thousands of them is costly. So servers cap their pools (Tomcat defaults to 200),
and a request that waits 2 seconds on a slow database holds one of those 200 threads the whole time.

Before Java 21, the answer was **reactive programming** (WebFlux, `CompletableFuture` chains): never
block, return a promise instead. It scales, but it is harder to write, read, debug and profile.

**Virtual threads** (Java 21) keep the simple blocking style and make threads cheap.

## How they work

A virtual thread is a Java object managed by the JVM, not the OS. The JVM runs many virtual threads
on a small pool of platform threads called **carriers** (a `ForkJoinPool`, one per core by default).

<Steps>
  <Step title="Mount">

When a virtual thread is ready to run, the scheduler mounts it on a free carrier and runs its code.

  </Step>
  <Step title="Block and unmount">

When the code blocks — socket read, `Thread.sleep`, `BlockingQueue.take`, a JDBC call — the JDK
saves the virtual thread's stack to the heap and **unmounts** it. The carrier is immediately free to
run another virtual thread.

  </Step>
  <Step title="Resume">

When the I/O completes, the virtual thread is scheduled again, possibly on a different carrier, and
continues exactly where it stopped.

  </Step>
</Steps>

The code you write is ordinary blocking code. The JDK's networking, file and concurrency classes were
reworked to cooperate with this.

## Using them

```java
Thread.startVirtualThread(() -> handle(request));

Thread vt = Thread.ofVirtual().name("worker-", 0).start(task);

try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Quote>> quotes = suppliers.stream()
            .map(s -> executor.submit(() -> s.quote(item)))   // one virtual thread per call
            .toList();
    …
}
```

### In Spring Boot (3.2+)

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

With that one property, Tomcat handles each request on a virtual thread, and `@Async`, scheduled
tasks and several other executors use virtual threads too. The rest of your code does not change.

<Callout type="pitfall" title="Your database is still the bottleneck">
Ten thousand virtual threads can all try to use a connection pool of 20. They will wait politely
rather than crash, but throughput is set by the pool and the database. Protect downstream systems
with explicit limits — a `Semaphore`, the pool size, or a rate limiter.
</Callout>

## Pinning

In some situations a virtual thread cannot unmount while blocked; it stays **pinned** to its carrier,
blocking that carrier too. With few carriers, a handful of pinned threads can stall everything.

- **Native code** and foreign functions pin while they run.
- In **Java 21–23**, blocking inside a `synchronized` block or method pins. **Java 24** (JEP 491)
  removed this limitation for `synchronized`.

On Java 21, prefer `ReentrantLock` over `synchronized` around blocking calls in hot paths, and detect
pinning with `-Djdk.tracePinnedThreads=full` or the JFR event `jdk.VirtualThreadPinned`.

```java
// Java 21: may pin while waiting on the network
synchronized (this) {
    response = httpClient.send(request, handler);
}

// Java 21: does not pin
lock.lock();
try {
    response = httpClient.send(request, handler);
} finally {
    lock.unlock();
}
```

## When not to use them

- **CPU-bound work** gains nothing: there are still only as many cores as there are.
- **Pooling virtual threads** defeats their purpose.
- Libraries that pin heavily, or depend on large per-thread caches, may need updating first.

## Structured concurrency and scoped values

Two related APIs make concurrent code easier to reason about. `StructuredTaskScope` treats a group of
subtasks as one unit: if one fails the others are cancelled, and none outlives the block. **Scoped
values** are an immutable, bounded alternative to `ThreadLocal`. Scoped values are final in Java 25;
structured concurrency is still a **preview** API, so its shape may still change.

```java
// Preview API — shape shown as of recent JDKs
try (var scope = StructuredTaskScope.open()) {
    Subtask<Customer> customer = scope.fork(() -> customers.load(id));
    Subtask<List<Order>> orders = scope.fork(() -> this.orders.load(id));
    scope.join();                                   // waits for both; fails fast if one fails
    return new Summary(customer.get(), orders.get());
}
```

For most request–response services, virtual threads now give reactive-level scalability with
imperative code. Reactive remains a strong fit for streaming and event-driven pipelines.
