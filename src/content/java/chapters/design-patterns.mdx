## Why patterns

A design pattern is a **named, reusable solution** to a recurring design problem. The names matter as
much as the code: "this is a strategy" tells a reader a lot in three words. Spring is built from these
patterns, so recognising them makes the framework far less magical.

## Singleton

One instance for the whole application.

```java
public enum Clock implements Supplier<Instant> {   // the simplest correct singleton
    INSTANCE;
    public Instant get() { return Instant.now(); }
}

public final class Registry {                      // lazy, thread-safe, no locking
    private Registry() { }
    private static class Holder { static final Registry INSTANCE = new Registry(); }
    public static Registry getInstance() { return Holder.INSTANCE; }
}
```

<Callout type="pitfall" title="Hand-written singletons are global state">
They hide dependencies and are hard to replace in tests. In Spring, let the container manage one
instance (a singleton-scoped bean) and **inject** it. Spring singletons are shared across threads, so
keep them stateless.
</Callout>

## Factory

Put object creation behind a method, so callers do not depend on concrete classes.

```java
public interface Notifier { void send(Message m); }

public static Notifier forChannel(Channel channel) {       // a static factory
    return switch (channel) {
        case EMAIL -> new EmailNotifier();
        case SMS -> new SmsNotifier();
    };
}

List.of(…); Optional.of(…); Money.of(…);                   // static factories everywhere in the JDK
```

Static factory methods beat constructors when you want names (`Money.zero`), caching (`Integer.valueOf`),
or the freedom to return a subtype. In Spring, every `@Bean` method is a factory method, and the
container itself is a `BeanFactory`.

## Builder

Construct an object with many optional parameters, readably and validated in one place.

```java
HttpRequest request = HttpRequest.newBuilder(uri)
        .timeout(Duration.ofSeconds(5))
        .header("Accept", "application/json")
        .GET()
        .build();
```

It avoids **telescoping constructors** (`new Pizza(size, true, false, true, null)`) and lets the final
object be immutable. Lombok's `@Builder` and records with a static builder are common shortcuts.

## Strategy

Define a family of interchangeable algorithms behind one interface and choose one at run time.

```java
public interface ShippingCost { Money quote(Parcel p); }

class FlatRate implements ShippingCost { … }
class ByWeight implements ShippingCost { … }

class Checkout {
    private final ShippingCost shipping;       // which one is decided outside
    Checkout(ShippingCost shipping) { this.shipping = shipping; }
}

// With lambdas, a strategy is often just a function:
ShippingCost free = p -> Money.zero(EUR);
```

In Spring, injecting an interface *is* the strategy pattern; injecting `Map<String, PaymentGateway>`
gives you every implementation keyed by bean name, ready to pick from.

## Template method

A base class fixes the steps of an algorithm and lets subclasses (or callbacks) fill in some of them.

```java
abstract class DataImporter {
    public final void run() {           // the template: final so the order cannot change
        var rows = read();
        rows.forEach(this::validate);
        save(rows);
    }
    protected abstract List<Row> read();
    protected void validate(Row row) { }   // an optional hook
    protected abstract void save(List<Row> rows);
}
```

Spring's `JdbcTemplate` is the callback flavour: it owns connection handling, statement creation,
cleanup and exception translation, and you pass in only the variable part — the SQL and a `RowMapper`.

## Observer

Subjects notify subscribers of events without knowing who they are.

```java
// Spring's version
public record OrderPlaced(long orderId) { }

@Service
class OrderService {
    private final ApplicationEventPublisher events;
    void place(Order o) {
        …
        events.publishEvent(new OrderPlaced(o.id()));
    }
}

@Component
class Receipts {
    @EventListener
    void on(OrderPlaced e) { … }       // OrderService never references Receipts
}
```

`@TransactionalEventListener` delivers the event only after the transaction commits. Across services,
the same idea becomes messaging (Kafka), covered in the event-driven modules.

## Proxy

A stand-in object with the same interface that controls access to the real one — adding behaviour
before and after, or loading it lazily.

```java
class TimingPaymentGateway implements PaymentGateway {
    private final PaymentGateway target;
    TimingPaymentGateway(PaymentGateway target) { this.target = target; }

    public Receipt charge(Money amount) {
        long start = System.nanoTime();
        try {
            return target.charge(amount);
        } finally {
            metrics.record(System.nanoTime() - start);
        }
    }
}

// The JDK can generate such a class at run time for any interface:
PaymentGateway proxy = (PaymentGateway) Proxy.newProxyInstance(
        loader, new Class<?>[] { PaymentGateway.class },
        (p, method, args) -> { log(method); return method.invoke(real, args); });
```

Spring wraps beans in proxies — JDK dynamic proxies for interfaces, CGLIB subclasses otherwise — to
implement `@Transactional`, `@Async`, `@Cacheable` and method security. Because the proxy sits
*outside* the bean, a call from one method to another inside the same bean bypasses it: the famous
self-invocation problem.

## Decorator

Like a proxy in shape, but meant to **add responsibilities**, often stacked.

```java
InputStream in = new GZIPInputStream(
                     new BufferedInputStream(
                         new FileInputStream(file)));   // each layer adds one feature

Collections.unmodifiableList(list);                     // decorates a list with read-only behaviour
```

The difference from a proxy is intent: a proxy controls access to one object; decorators add behaviour
and are composed by the caller.

## Adapter and chain of responsibility, briefly

- **Adapter** converts one interface into another the client expects: `Arrays.asList` adapts an array
  to `List`; Spring's `HandlerAdapter` lets one `DispatcherServlet` call very different kinds of handler.
- **Chain of responsibility** passes a request along a chain of handlers, each of which may handle it,
  change it or pass it on: servlet filters, the Spring Security filter chain, and interceptors.

## Anti-patterns to recognise

- **God object** — one class that knows and does everything.
- **Service locator** — objects fetching their own dependencies from a registry, hiding them.
- **Singleton abuse** — global mutable state disguised as a pattern.
- **Anaemic model everywhere** — all logic in services, entities only getters and setters (sometimes
  fine, but a choice to make consciously).
- **Pattern-itis** — a factory for a class with one implementation that will never have another.
