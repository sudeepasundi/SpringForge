## `java.util.concurrent`

`synchronized` is simple but inflexible. The `java.util.concurrent` packages (Java 5, by Doug Lea)
provide explicit locks, lock-free atomics, thread-safe collections and coordination tools. In
application code, reach for these before `synchronized`, `wait` and `notify`.

## Explicit locks

### `ReentrantLock`

Does what `synchronized` does, plus:

- `tryLock()` — give up instead of waiting (or wait with a timeout), which avoids deadlocks.
- `lockInterruptibly()` — waiting can be interrupted.
- Optional **fairness** — longest-waiting thread first (slower).
- Several `Condition`s per lock (`await` / `signal`).

```java
private final ReentrantLock lock = new ReentrantLock();

void update() {
    lock.lock();
    try {
        // critical section
    } finally {
        lock.unlock();          // ALWAYS in finally: an exception must not leave the lock held
    }
}

if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {
    try { … } finally { lock.unlock(); }
} else {
    // could not get it in time — back off, retry, or report
}
```

### `ReadWriteLock`

Many readers **or** one writer. Useful when reads vastly outnumber writes and each read takes a while.

```java
private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();

Rate current(String currency) {
    rw.readLock().lock();
    try { return rates.get(currency); } finally { rw.readLock().unlock(); }
}

void refresh(Map<String, Rate> fresh) {
    rw.writeLock().lock();
    try { rates.clear(); rates.putAll(fresh); } finally { rw.writeLock().unlock(); }
}
```

`StampedLock` (Java 8) adds an **optimistic read** mode that takes no lock at all and validates
afterwards — faster still, but not reentrant and easy to misuse.

## Atomic variables

The `java.util.concurrent.atomic` classes update a single value **without locks**, using the CPU's
**compare-and-set** (CAS): "set to X only if the value is still Y", retried until it succeeds.

```java
AtomicLong counter = new AtomicLong();
counter.incrementAndGet();
counter.addAndGet(5);
counter.compareAndSet(10, 0);                   // true if it was 10
counter.updateAndGet(v -> v * 2);               // the function may run more than once: keep it pure
counter.accumulateAndGet(42, Math::max);        // a running maximum

AtomicReference<Config> config = new AtomicReference<>(initial);
config.set(reloaded);                           // swap an immutable object atomically

LongAdder hits = new LongAdder();               // many writers, occasional reads
hits.increment();
hits.sum();
```

`LongAdder` keeps several internal cells so that concurrent increments rarely collide. It outperforms
`AtomicLong` under heavy contention, at the cost of `sum()` not being an atomic snapshot.

<Callout type="pitfall" title="Two atomics are not one atomic operation">
`if (count.get() < limit) count.incrementAndGet();` is check-then-act again — two threads can both
pass the check. Use a single CAS loop (`updateAndGet(v -> v < limit ? v + 1 : v)`) or a lock.
</Callout>

### `ConcurrentHashMap` done right

<Compare>
  <Bad title="Check-then-act on a concurrent map">

```java
if (!cache.containsKey(key)) {
    cache.put(key, load(key));        // two threads can both load and both put
}

Integer n = counts.get(word);
counts.put(word, n == null ? 1 : n + 1);   // lost updates
```

Each call is thread-safe; the *combination* is not.

  </Bad>
  <Good title="Use the atomic methods">

```java
cache.computeIfAbsent(key, this::load);    // load runs at most once per key
counts.merge(word, 1, Integer::sum);       // atomic increment
counts.compute(word, (k, v) -> v == null ? 1 : v + 1);
```

Keep the functions short and never touch the same map from inside them.

  </Good>
</Compare>

### Blocking queues: producer–consumer

```java
BlockingQueue<Job> jobs = new ArrayBlockingQueue<>(1_000);

// producer
jobs.put(job);                        // waits while the queue is full — natural back-pressure
jobs.offer(job, 1, TimeUnit.SECONDS); // or give up after a while

// consumer
while (!Thread.currentThread().isInterrupted()) {
    Job next = jobs.take();           // waits while empty
    process(next);
}
```
