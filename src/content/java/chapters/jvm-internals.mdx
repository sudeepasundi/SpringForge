- **JDK** = development tools (`javac`, `jar`, `jcmd`…) + the runtime. **JRE** was the runtime alone;
  since Java 11 you use a JDK or build a trimmed runtime with `jlink`.
- **Bytecode** is platform-neutral, so the same `.class` file runs on any JVM — "write once, run anywhere".
- `javap -c Account.class` shows the bytecode.

## Class loading

Classes are loaded **lazily**, the first time they are used.

<Steps>
  <Step title="Loading">

A class loader finds the bytes (in a JAR, a module, or generated at run time) and creates a `Class`
object.

  </Step>
  <Step title="Linking">

**Verification** checks the bytecode is safe (no stack overflows, type-correct operations).
**Preparation** allocates static fields with default values. **Resolution** turns symbolic
references into real ones (often lazily).

  </Step>
  <Step title="Initialisation">

Static initialisers and static field assignments run — once, thread-safely, on first active use.

  </Step>
</Steps>

Loaders **delegate to their parent first**, so application code cannot replace `java.lang.String`.
A class's identity is its name **plus** its loader: the same class loaded by two loaders is two
different types — the source of the baffling `ClassCastException: Foo cannot be cast to Foo`.

Errors to recognise: `ClassNotFoundException` (a dynamic load failed), `NoClassDefFoundError` (a class
present at compile time is missing at run time, or its static initialiser failed earlier), and
`NoSuchMethodError` (two incompatible library versions on the classpath).

A local variable holding an object lives on the stack; the object it refers to lives on the heap.
(The JIT's **escape analysis** can sometimes avoid heap allocation for objects that never leave a
method.)

## Garbage collection

The garbage collector frees objects that are no longer **reachable** from GC roots — live thread
stacks, static fields, JNI references. Unreachable cycles are collected too; there is no reference
counting.

### The generational hypothesis

Most objects die young (request data, iterators, temporary strings). So the heap is split:

<Steps>
  <Step title="Allocate in Eden">

Allocation is a pointer bump in a thread-local buffer — very fast.

  </Step>
  <Step title="Minor GC">

When Eden fills, live objects are copied to a survivor space; everything left in Eden is garbage and
reclaimed in one go. Cost is proportional to **live** objects, not dead ones.

  </Step>
  <Step title="Promotion">

Objects that survive several minor collections are promoted to the old generation.

  </Step>
  <Step title="Old-generation collection">

Collected less often, usually concurrently with the application, with some compaction to fight
fragmentation.

  </Step>
</Steps>

```bash
java -XX:+UseZGC -jar app.jar                 # generational by default from Java 23
java -Xlog:gc*:file=gc.log -jar app.jar       # unified GC logging
```

### Memory leaks in a garbage-collected language

The GC frees only what is unreachable. A leak is something **still referenced but no longer needed**:

- static collections and caches that only grow (use size limits or Caffeine)
- listeners registered and never removed
- `ThreadLocal` values left on pooled threads
- inner-class instances holding their outer object
- class loader leaks on redeploy in application servers

## The JIT compiler

The JVM starts by **interpreting** bytecode. It counts how often methods and loops run, and compiles
hot ones to native code:

- **C1** compiles quickly with light optimisation.
- **C2** compiles hot code with aggressive optimisation — inlining, escape analysis, loop
  optimisations, and **speculative** optimisations based on observed types.
- **Tiered compilation** (the default) uses both.

If an assumption turns out wrong (a second implementation of an interface appears), the JIT
**deoptimises** and recompiles. This is why a JVM needs **warm-up**, why micro-benchmarks need JMH, and
why GraalVM native images (ahead-of-time compiled) start instantly but may peak lower.

Modern JVMs are **container-aware**: they read cgroup memory and CPU limits. Remember that the heap is
only part of the process's memory — metaspace, thread stacks, the code cache and direct buffers add
to it, so `MaxRAMPercentage` should leave headroom.

## Diagnosing a running JVM

```bash
jcmd                                  # list JVMs
jcmd <pid> VM.flags                   # effective flags
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print               # thread dump: deadlocks, stuck threads
jcmd <pid> GC.heap_dump /tmp/heap.hprof
jcmd <pid> JFR.start duration=60s filename=/tmp/app.jfr   # Java Flight Recorder: low-overhead profiling
jstat -gcutil <pid> 1000              # GC statistics every second
```

- **Heap dumps** are analysed with Eclipse MAT or VisualVM: look at the dominator tree and retained sizes.
- **Thread dumps** — take three a few seconds apart; threads stuck in the same place are the problem.
- **JFR + JDK Mission Control** show allocation, locking, I/O and GC with about 1% overhead.
- Spring Boot Actuator exposes `heapdump` and `threaddump` endpoints (secure them).

<Callout type="tip" title="Metrics first">
Before reaching for dumps, look at JVM metrics over time — heap after GC, GC pause time, thread count.
Micrometer publishes them from a Spring Boot app automatically; the observability lessons show how.
</Callout>
