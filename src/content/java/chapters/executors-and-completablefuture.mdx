## Why executors

Creating a platform thread per task is expensive, and unbounded thread creation can exhaust memory.
An **`ExecutorService`** separates *what* to run (tasks) from *how* it runs (a pool of reusable threads
and a queue).

<Mermaid
  caption="A thread pool: tasks wait in a queue; a fixed set of worker threads takes them one at a time."
  alt="Diagram: callers submit tasks into a queue inside the ExecutorService. Three worker threads take tasks from the queue and run them, each returning a Future to the caller."
  chart={`
flowchart LR
    C1[caller] -->|submit| Q[(task queue)]
    C2[caller] -->|submit| Q
    Q --> W1[worker 1]
    Q --> W2[worker 2]
    Q --> W3[worker 3]
    W1 -.->|result| F[Future]
`}
/>

```java
ExecutorService pool = Executors.newFixedThreadPool(4);

Future<Report> future = pool.submit(() -> buildReport(month));   // a Callable returns a value
pool.execute(() -> sendEmail(user));                              // a Runnable, fire and forget

Report report = future.get(5, TimeUnit.SECONDS);   // blocks; throws TimeoutException, ExecutionException

pool.shutdown();                                   // no new tasks; finish queued ones
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();                            // interrupt running tasks
}
```

Since Java 19 an `ExecutorService` is `AutoCloseable`: `close()` shuts it down and waits.

```java
try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
    pool.submit(task1);
    pool.submit(task2);
}   // waits here for both
```

<Callout type="pitfall" title="Unbounded queues hide overload">
`newFixedThreadPool` queues without limit: under sustained overload, memory fills with waiting tasks
and latency grows without bound. For production pools, build a `ThreadPoolExecutor` directly with a
**bounded** queue and a rejection policy.
</Callout>

```java
ExecutorService pool = new ThreadPoolExecutor(
        8, 16,                                     // core and maximum threads
        60, TimeUnit.SECONDS,                      // idle time before extra threads die
        new ArrayBlockingQueue<>(500),             // bounded queue
        Thread.ofPlatform().name("report-", 0).factory(),   // named threads help thread dumps
        new ThreadPoolExecutor.CallerRunsPolicy());         // when full, the caller runs the task (back-pressure)
```

The pool grows beyond the core size **only when the queue is full** — a frequent surprise.

### Sizing

- **CPU-bound** work: about the number of cores (`Runtime.getRuntime().availableProcessors()`).
- **I/O-bound** work: cores × (1 + wait time / compute time) — often much larger. For this, virtual
  threads are now usually the better answer.
- Always measure; the right size depends on what else runs on the machine.

## `Future` and its limits

A `Future` represents a result that will exist later. You can `get()` it (blocking), `cancel` it, or
check `isDone()`. You cannot say "when it finishes, do this" or combine two futures without blocking a
thread on each.

## `CompletableFuture`

`CompletableFuture` (Java 8) is a future you can **compose**.

```java
CompletableFuture<Customer> customer = CompletableFuture.supplyAsync(() -> customers.load(id), io);
CompletableFuture<List<Order>> orders = CompletableFuture.supplyAsync(() -> this.orders.load(id), io);

CompletableFuture<Summary> summary = customer
        .thenCombine(orders, Summary::new)                    // both finished → combine
        .thenApply(Summary::withTotals)                       // transform
        .orTimeout(2, TimeUnit.SECONDS)                       // Java 9: fail if too slow
        .exceptionally(ex -> Summary.unavailable(id));        // recover
```

### Which thread runs what

- `supplyAsync(task)` **without an executor** uses the **common ForkJoinPool** — shared with parallel
  streams and sized for CPU work. **Pass your own executor for blocking calls.**
- `thenApply` (no `Async`) runs on whichever thread completed the previous stage — or on the caller,
  if it was already complete.
- `thenApplyAsync(fn, executor)` always hands off to an executor.

### Errors

An exception inside a stage completes the future **exceptionally**; later `thenApply` stages are
skipped until an `exceptionally` or `handle`.

- `join()` throws an unchecked `CompletionException` wrapping the cause.
- `get()` throws a checked `ExecutionException` wrapping the cause.
- Lambdas cannot throw checked exceptions — wrap them (Tally uses `CompletionException`) and unwrap
  at the edge.

<Callout type="pitfall" title="A future nobody looks at">
`CompletableFuture.runAsync(this::sendEmail);` with no `exceptionally`, `join` or logging means a
failure disappears silently. Every chain should end somewhere that observes errors.
</Callout>

### `@Async` in Spring

`@Async` methods return `CompletableFuture<T>` and run on a Spring-managed executor. Because it works
through a proxy, calling an `@Async` method from the same class runs it synchronously — see the AOP
lesson.
