The container is a `Map<String, Object>` with opinions.

That is not a joke — it is close to literally true, and holding it in your head is what turns Spring
from a set of incantations into a system you can reason about. The container holds named objects,
it knows how to build them, it knows what order to build them in, and it can wrap them before
handing them out. Everything else is detail.

## Two phases, and the distinction that matters

The container's life divides into two phases, and almost every confusing Spring behaviour comes
from not knowing which phase something happens in.

A **`BeanDefinition`** is metadata: which class, which scope, which constructor arguments, whether
it is lazy, which other beans it depends on. It is a recipe. Nothing has been cooked.

A **bean** is the object that results. By the time one exists, the recipe is fixed.

This is why `@ConfigurationProperties` binding, conditional evaluation and property placeholder
resolution all happen in phase one: they change recipes, and recipes stop being changeable once
cooking starts.

<Callout type="tip" title="A test for which phase you are in">
Ask: "could this still change which class gets instantiated?" If yes, it is a
`BeanFactoryPostProcessor` concern (phase one). If it can only wrap or configure an object that
already exists, it is a `BeanPostProcessor` concern (phase two). AOP proxies are phase two — which
is exactly why they can only wrap, never replace.
</Callout>

## BeanFactory and ApplicationContext

You will see both names. They are not alternatives; one contains the other.

<DecisionTable
  columns={['What it is', 'Adds']}
  rows={[

      cells: [
        'The bare container: register definitions, get beans, resolve dependencies',
        '— (this is the floor)',
      ],
    },
    {
      label: 'ApplicationContext',
      verdict: 'good',
      cells: [
        'A BeanFactory plus the enterprise features',
        'Events, message sources, resource loading, automatic post-processor registration, eager singleton instantiation',
      ],
    },
  ]}
/>

In practice you always have an `ApplicationContext` — `SpringApplication.run` returns one. The
distinction matters for exactly one reason: **`ApplicationContext` instantiates non-lazy singletons
at startup, and a bare `BeanFactory` does not.** That eager instantiation is the reason a missing
dependency is a startup failure rather than a 3am `NullPointerException`, and it is one of the most
valuable properties Spring has.

Singleton is the default and should stay the default. It carries one obligation: **a singleton must
be stateless**, because every request touching your application shares the same instance. A mutable
field on a `@Service` is a data race, and it will corrupt data under load long before it shows up in
a test.

<Compare>
  <Bad title="A singleton with state">

One instance, many threads. Two concurrent requests will interleave and produce a total that
belongs to neither of them.

```java
@Service
public class InvoiceService {

    private BigDecimal runningTotal = BigDecimal.ZERO;   // shared by every request

    public BigDecimal addLine(BigDecimal amount) {
        runningTotal = runningTotal.add(amount);
        return runningTotal;
    }
}
```

  </Bad>
  <Good title="State on the stack">

The state lives in a local variable, which is per-invocation and therefore per-thread by
construction. The only fields are immutable collaborators.

```java
@Service
public class InvoiceService {

    private final TaxCalculator taxCalculator;   // stateless collaborator, safe to share

    public InvoiceService(TaxCalculator taxCalculator) {
        this.taxCalculator = taxCalculator;
    }

    public BigDecimal total(List<Line> lines) {
        BigDecimal total = BigDecimal.ZERO;      // local — one per call
        for (Line line : lines) {
            total = total.add(taxCalculator.withTax(line.amount()));
        }
        return total;
    }
}
```

  </Good>
</Compare>

## Look inside a running container

The most useful thing in this lesson is not a concept — it is that you can inspect the container at
runtime and stop guessing.

```java title="support/BeanReport.java" {8-14}
@Component
@Profile("dev")   // never ship this
class BeanReport implements ApplicationRunner {

    private final ApplicationContext context;

    BeanReport(ApplicationContext context) {
        this.context = context;
    }

    @Override
    public void run(ApplicationArguments args) {
        System.out.printf("%d beans registered%n", context.getBeanDefinitionCount());

        Arrays.stream(context.getBeanDefinitionNames())
                .filter(name -> name.startsWith("task"))
                .sorted()
                .forEach(name -> System.out.printf("  %-28s %s%n",
                        name, context.getType(name).getSimpleName()));
    }
}
```

<Terminal>
{`$ ./mvnw spring-boot:run
312 beans registered
  taskController               TaskController
  taskRepository               SimpleJpaRepository$$SpringCGLIB$$0
  taskService                  TaskService$$SpringCGLIB$$0`}
</Terminal>

Three things in that output are worth noticing.

**312 beans** for a small application. Most are auto-configuration infrastructure, and that number
is a good rough gauge of how much Boot is doing for you.

**Bean names are derived** from the class name with the first letter lower-cased, unless you set one
explicitly. That is the string in the `Map` — which is why `@Qualifier("taskRepository")` works.

**`$$SpringCGLIB$$` in the type names.** `taskService` is not a `TaskService`; it is a generated
subclass wrapping one. Something added transactional behaviour during phase two. That subclass is
the mechanism behind `@Transactional`, `@Cacheable`, `@Async` and method security — and it is the
subject of this module's final lesson, where it also explains a bug that catches everyone.

<Callout type="prod">
Actuator exposes the same information without writing code: `/actuator/beans` lists every bean with
its type, scope and dependencies. Keep it behind authentication — it is a precise map of your
application's internals — but reach for it before you reach for a debugger.
</Callout>
