"Orchestrator" is one of those words that has been attached to two different jobs. Getting them
confused produces a state machine where a switch statement would do, or — worse — a switch statement
where a state machine was needed.

## Two things called orchestration

ShopFlow's `OrderSaga` ([module 09](/learn/event-driven/saga-pattern)) exists because its steps can be
undone: release the stock, refund the payment. It persists a state machine because it has to know
which steps completed in order to reverse them.

Relay's orchestrator has none of that, because **nothing here can be undone.** There is no step two
to fail. The entire job is to choose correctly, once — and then never do it again for the same event.

<Callout type="pitfall" title="Reaching for a saga because the word fits">
If you find yourself persisting a state machine for a single irreversible action, stop. The state
exists to enable compensation; with nothing to compensate, it is a table you have to maintain, query
and clean up, protecting a rollback that cannot happen.

The test is one question: **if the last step fails, is there something to undo?** For a notification,
no. There is only something to *not do twice*, which is a dedup marker, not a saga.
</Callout>

## The decision, as a pure function

The rules that decide whether a person gets woken at 4am are the rules most worth testing and the
ones most often buried in a service class next to three network calls.

```java title="ChannelDecision.java"
public record ChannelDecision(List<Channel> channels, boolean suppressed, String reason) {

    public static ChannelDecision of(NotificationRequest request, RecipientPreferences prefs) { … }
}
```

No repository, no client, no clock field, no Spring. Every rule below is a test that runs in
microseconds — which matters, because these are the rules that get a company fined when they are
wrong.

### Opt-out, and what it does not cover

```java
if (request.type().isDeclinable() && prefs.hasOptedOut(request.type())) {
    return suppress("recipient opted out of " + request.type());
}
```

`isDeclinable()` is carrying real weight. Marketing and digests are declinable. A password reset, a
fraud alert or a receipt is not — those are transactional notices about the account itself, and
suppressing them because someone unsubscribed from a newsletter is its own kind of failure.

<Callout type="prod">
Put the declinable flag on the **type**, not in a config file and not in an `if` inside the sender.
Someone will add a notification type in a hurry, and the only question that stops them shipping a
compliance problem is the one the compiler asks: *is this declinable?*
</Callout>

### Quiet hours cross midnight

```java
return start.isBefore(end)
        ? !localNow.isBefore(start) && localNow.isBefore(end)
        : !localNow.isBefore(start) || localNow.isBefore(end);
```

Two bugs live in this three-line method, and both ship regularly.

The first is the window itself: quiet hours are usually 22:00–07:00, so `start` is *after* `end` and
the obvious `start < now < end` comparison is false all night — the check silently does nothing,
which is the worst possible outcome for a check of this kind.

The second is the zone.

<Compare>
  <Bad title="Evaluated in the server's zone">

Works perfectly in CI, which runs in UTC, and in your local tests, which run in your zone. Fails for
every recipient who is not in that zone — and fails invisibly, because nobody files a ticket saying
"I received this at a reasonable hour."

```java
LocalTime now = LocalTime.now();               // server zone
```

  </Bad>
  <Good title="Evaluated in the recipient's zone">

The only zone that means anything here is the one the phone is in.

```java
LocalTime localNow = ZonedDateTime.now(prefs.zone()).toLocalTime();
```

  </Good>
</Compare>

### Severity reorders rather than overrides

```java
if (request.severity() == Severity.CRITICAL) {
    chain = fastestFirst(chain);
}
```

A critical notice leads with the fastest channel the recipient has verified — but it still falls back
to their actual preference. It reorders the chain rather than replacing it, so a recipient who has
only ever verified email still gets the alert by email instead of nothing.

## Suppression is a decision, not a drop

```java
if (decision.suppressed()) {
    deliveries.recordSuppressed(request, decision.reason());
    return;
}
```

*"Why didn't I get that notification?"* is a support ticket, and the answer has to be queryable
rather than reconstructed from log files. Every suppression writes a row with a reason.

This is the difference between a system you can operate and one you can only apologise for.

## The fallback chain

```java title="DispatchOrchestrator.java"
for (Channel channel : chain) {
    try {
        deliveries.claim(request.eventId(), channel);
        DeliveryReceipt receipt = channels.send(channel, request, prefs);
        deliveries.recordSent(request, channel, receipt);
        return;
    } catch (ChannelUnavailableException e) {
        deliveries.release(request.eventId(), channel);   // try the next one
    }
}
throw new NoChannelAvailableException(request.eventId(), chain);
```

Three exits, each deliberate:

<Steps>
  <Step title="A channel accepts">

Record the receipt and stop. The chain is ordered by the recipient's preference, not by what is
cheapest for us — a detail worth defending in review, because the cheapest ordering is always
available and always tempting.

  </Step>
  <Step title="A channel is unavailable">

Release the claim and try the next. This is the case the chain exists for: the SMS provider is down
and the person still needs to know. Note that only `ChannelUnavailableException` reaches here — a
malformed request is not retryable on another channel either, so it propagates.

  </Step>
  <Step title="Every channel refused">

Throw. That is what sends the record to a retry topic, which is the next lesson. The recipient is
reachable in principle and not right now, so waiting is the correct response.

  </Step>
</Steps>

<Callout type="prod">
Notice what the orchestrator does *not* do: it does not queue, sleep, or schedule. A `Thread.sleep`
here would hold a Kafka partition; a scheduled retry table would be a second, worse copy of what the
broker already does.

Throwing and letting the retry topic own the waiting keeps this class synchronous and testable, and
puts the backoff somewhere it survives a restart.
</Callout>
