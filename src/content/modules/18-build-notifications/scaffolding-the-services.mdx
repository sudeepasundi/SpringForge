Every other module in this course explains something that already exists. This one starts with an
empty directory.

You are going to build **Relay**: a request arrives on a Kafka topic, something decides how to reach
the person, and an email or an SMS goes out. It is a small enough system to hold in your head and a
real enough one to get wrong in interesting ways.

<Callout type="pitfall" title="Five services is a teaching decision, not a recommendation">
[Module 07](/learn/microservices-fundamentals/why-microservices) makes the case that distribution is a
cost you buy deliberately. Relay is split finely because each seam teaches something — discovery,
declarative clients, routing, idempotent side effects.

A real notification platform this size is one service with three packages, and it should stay that
way until two teams need to deploy it on different days.
</Callout>

## Generating them

[Module 00](/learn/foundations/environment-setup) generated one service by hand. Five is where
that stops being reasonable — not because it is slow, but because the fifth one will quietly differ
from the first.

<Terminal title="one loop, five services">
{`$ mkdir relay && cd relay
$ for svc in discovery-server dispatch-orchestrator preference-service email-service sms-service; do
    curl -s https://start.spring.io/starter.tgz \\
      -d type=maven-project -d language=java -d javaVersion=21 \\
      -d bootVersion=3.4.1 \\
      -d groupId=dev.springforge.relay -d artifactId=$svc -d name=$svc \\
      -d packageName=dev.springforge.relay.\${svc//-/} \\
      -d dependencies=actuator \\
      | tar -xzf - -C . --one-top-level=$svc
  done
$ ls
discovery-server  dispatch-orchestrator  email-service  preference-service  sms-service`}
</Terminal>

Then add the dependencies each one actually needs, rather than a union of all of them:

<Terminal>
{`$ # discovery-server
$ ./mvnw -q -f discovery-server dependency:get -Dartifact=org.springframework.cloud:spring-cloud-starter-netflix-eureka-server:4.1.3
$ # every other service registers, so it needs the client instead
$ # dispatch-orchestrator also needs: kafka, openfeign, jdbc, flyway, postgresql, resilience4j`}
</Terminal>

<Callout type="tip" title="The rule from module 00 still applies, and matters more here">
*Add what you know you need now. Do not add what you might need later.* With one service an unused
starter is a slightly slower startup. With five it is five slightly different sets of transitive
versions, and the day they disagree is the day you are debugging something else.
</Callout>

  ]}
/>

One repository, five Maven modules under a parent. That is the boring answer and it is correct for a
system one team owns.

```xml title="relay/pom.xml"
<project>
    <groupId>dev.springforge.relay</groupId>
    <artifactId>relay-parent</artifactId>
    <packaging>pom</packaging>

    <modules>
        <module>discovery-server</module>
        <module>dispatch-orchestrator</module>
        <module>preference-service</module>
        <module>email-service</module>
        <module>sms-service</module>
    </modules>

    <dependencyManagement>
        <dependencies>
            <!-- Versions in one place. Without this, two services end up on two
                 Spring Cloud releases and the Feign they share behaves differently. -->
            <dependency>
                <groupId>org.springframework.cloud</groupId>
                <artifactId>spring-cloud-dependencies</artifactId>
                <version>2024.0.0</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>
</project>
```

## The shared-code trap

Five services that exchange JSON will tempt you into a `relay-common` module holding the DTOs. It
feels obviously right and it is the most reliable way to turn five services back into one.

<Compare>
  <Bad title="A shared module with everything in it">

Every service depends on `relay-common`, so every change to it rebuilds and redeploys all five. You
now have a distributed monolith: the deployment cost of microservices and the coupling of a monolith.

```xml
<dependency>
    <groupId>dev.springforge.relay</groupId>
    <artifactId>relay-common</artifactId>   <!-- DTOs, entities, enums, utils, config -->
</dependency>
```

The failure is gradual. Someone puts a shared `@Entity` in it, then a `RestTemplate` bean, then a
base class every controller extends. By then removing it is a quarter of work.

  </Bad>
  <Good title="Duplicate the shapes, share nothing that can change independently">

Each service declares the fields it actually reads. `email-service` does not need to know that a
`NotificationRequest` has an `smsBody`, so it does not have a field for it.

```java title="dispatch-orchestrator — what the orchestrator sends"
public record EmailRequest(
        UUID idempotencyKey, EmailAddress to,
        String template, Locale locale, Map<String, Object> model) {}
```

```java title="email-service — what the email service accepts"
public record EmailRequest(
        UUID idempotencyKey, EmailAddress to,
        String template, Locale locale, Map<String, Object> model) {}
```

Two identical files, deliberately. They are identical *today*; the point is that either can change
without a coordinated release, and a consumer that ignores an added field keeps working.

  </Good>
</Compare>

<Callout type="prod">
If duplication genuinely hurts — and past about three services it can — share the **contract**, not
the code: publish an OpenAPI document or an Avro schema and generate the client. That is a versioned
artifact with compatibility rules
([module 14](/learn/kafka-ops/schemas-and-evolution)), not a jar that silently couples deploys.

What must never be shared is anything with behaviour: entities, base classes, a configuration class,
a utility that reaches into a database.
</Callout>

## Kafka and Postgres, locally

Nothing above runs without a broker. One compose file brings up the infrastructure and the services
together.

```yaml title="platform/docker-compose.yml"
services:
  kafka:
    image: confluentinc/cp-kafka:7.7.1
    environment:
      KAFKA_PROCESS_ROLES: broker,controller     # KRaft: no ZooKeeper
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1  # one broker, so one replica
    healthcheck:
      test: ['CMD', 'kafka-broker-api-versions', '--bootstrap-server', 'localhost:9092']
      interval: 10s
      retries: 12

  dispatch-orchestrator:
    build: ../dispatch-orchestrator
    depends_on:
      kafka: { condition: service_healthy }      # not just 'started'
```

<Callout type="pitfall" title="depends_on without a condition waits for the process, not the service">
Plain `depends_on: [kafka]` means "start the container first". Kafka takes several seconds to accept
connections after that, so the orchestrator starts, fails to connect, and — depending on your
configuration — either retries quietly or exits.

`condition: service_healthy` with a real healthcheck is what you want. Your services should retry
anyway, because this problem exists in production too and compose is not there to solve it.
</Callout>

## Proving the loop works

Before writing a line of business logic, make a request go all the way through. A system you cannot
run is a system you will debug by reading.

<Steps>
  <Step title="Bring it up">

```bash
docker compose -f platform/docker-compose.yml up -d --build
./platform/create-topics.sh
```

  </Step>
  <Step title="Check every service registered">

The registry is the fastest way to see whether five services started. Four should be listed —
everything except the registry itself.

<Terminal>
{`$ curl -s -H "Accept: application/json" http://localhost:8761/eureka/apps \\
    | jq -r '.applications.application[].name'
DISPATCH-ORCHESTRATOR
EMAIL-SERVICE
PREFERENCE-SERVICE
SMS-SERVICE`}
</Terminal>

  </Step>
  <Step title="Put one request on the topic">

<Terminal>
{`$ docker exec -i relay-kafka kafka-console-producer \\
    --bootstrap-server localhost:9092 --topic notifications.requested.v1 <<'EOF'
{"eventId":"6b1c9f22-0000-4000-8000-000000000001","recipientId":"88af0000-0000-4000-8000-000000000001","type":"ORDER_SHIPPED","severity":"INFO"}
EOF`}
</Terminal>

  </Step>
  <Step title="Watch it come out the other end">

```bash
docker compose -f platform/docker-compose.yml logs -f dispatch-orchestrator email-service
```

You are looking for one line from the orchestrator saying which channel it chose, and one from the
email service saying it sent. If you see the first without the second, the problem is discovery —
which is the next lesson.

  </Step>
</Steps>

<Callout type="prod">
Make this a script and run it in CI. A `smoke.sh` that publishes one event and asserts a row in
`delivery_log` catches the class of failure that unit tests never do: a service that starts, passes
its health check, and cannot reach anything.

It is also the first thing you will run at 3am, so it should already work.
</Callout>
