Everything so far decided *what* to send. This lesson is about the two guarantees that decide whether
the system is trustworthy: a notification that should arrive does, and one that already arrived never
arrives again.

The second is the hard one, because Kafka gives you at-least-once delivery and an email cannot be
recalled.

## Blocking retry stalls the partition

[Module 09](/learn/event-driven/messaging-foundations) configured retries with a
`DefaultErrorHandler` and an exponential backoff. That is the right default for most consumers and
the wrong one here.

```java title="NotificationRequestConsumer.java"
@RetryableTopic(
        attempts = "4",
        backoff = @Backoff(delay = 2_000, multiplier = 4.0, maxDelay = 60_000),
        exclude = {UnknownRecipientException.class, MalformedRequestException.class},
        dltTopicSuffix = "-dlt")
@KafkaListener(topics = "notifications.requested.v1", groupId = "dispatch-orchestrator")
public void onRequest(NotificationRequest request, ...) { … }
```

Spring creates the retry topics and the dead-letter topic for you, and runs a listener on each. A
failed record is republished to `…-retry-0` and the original is committed, so the partition keeps
moving.

<Callout type="pitfall" title="Retry topics are the wrong choice when ordering is the point">
If your consumer applies state transitions for a key — stock levels, account balances, a saga's steps
— reordering is a correctness bug, not a latency trade. ShopFlow's consumers keep blocking retry for
exactly that reason.

Relay can afford it because two notifications to one person are independent of each other. Check that
assumption before copying this annotation, because nothing will fail loudly if it is wrong.
</Callout>

### Excluding what cannot succeed

```java
exclude = {UnknownRecipientException.class, MalformedRequestException.class}
```

This is where the error decoder from the previous lesson pays off. A malformed request will still be
malformed in a minute — retrying it four times delays the dead-letter by 42 seconds, burns provider
quota, and adds nothing. It goes straight to the DLT.

## At most once, for something irreversible

Kafka gives you at-least-once. Your users expect at-most-once. The gap between those two sentences is
where the duplicate emails live.

<Compare>
  <Bad title="Mark it sent afterwards">

The obvious order, and it has a window. The provider accepted the message, then the process died
before the marker was written. The redelivery finds no marker and sends a second copy.

```java
DeliveryReceipt receipt = channels.send(channel, request, prefs);
deliveries.recordSent(request, channel, receipt);   // ← crash here = duplicate
```

  </Bad>
  <Good title="Claim it first">

Inverting the order inverts the failure. A crash now means a notification that was sent but is
recorded as merely claimed — unrecorded rather than duplicated.

```java
deliveries.claim(request.eventId(), channel);       // ← crash here = never sent
DeliveryReceipt receipt = channels.send(channel, request, prefs);
deliveries.recordSent(request, channel, receipt);
```

  </Good>
</Compare>

Neither order is perfectly safe — that is not available with a remote side effect. The choice is
which failure you prefer, and for notifications it is obvious: an unrecorded send is a reporting
problem, a duplicate send is a user-facing one.

```java title="DeliveryLog.java"
try {
    db.sql("insert into delivery_log (event_id, channel, status, claimed_at) values (…)")
      .update();
} catch (DataIntegrityViolationException duplicate) {
    throw new AlreadyClaimedException(eventId, channel);
}
```

<Callout type="prod">
Insert first and let the unique constraint arbitrate. A `select` followed by an `insert` has a race
between the two statements, and with four consumer threads it will lose that race — rarely enough to
pass review and often enough to matter.

This is the same argument [module 09](/learn/event-driven/idempotency) makes for dedup tables. What
changes here is the ordering relative to the side effect.
</Callout>

### REQUIRES_NEW, and why

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void claim(UUID eventId, Channel channel) { … }
```

The claim has to commit on its own. If it joined the caller's transaction, a later rollback would
release a claim for a message that had already reached the provider — reintroducing the duplicate the
claim exists to prevent.

<Callout type="pitfall" title="Two layers of dedup, doing different jobs">
`alreadyHandled` at the top of the consumer and `claim` inside the send loop look redundant. They are
not.

The first is a cheap read that stops a redelivered event from re-running the decision — no preference
lookup, no routing. The second is the correctness guarantee, and it is the one that holds under
concurrency because it is a write.

Deleting the first costs performance. Deleting the second costs a duplicate email.
</Callout>

## The dead-letter path

A DLT nobody reads is a queue where notifications go to be forgotten.

```java
@DltHandler
public void onDeadLetter(NotificationRequest request,
                         @Header(KafkaHeaders.EXCEPTION_MESSAGE) String reason) {
    deliveries.recordUndeliverable(request, reason);
    log.error("Undeliverable notification {} for {}: {}", …);
}
```

Writing a row rather than only logging is what makes the next three things possible.

<Steps>
  <Step title="Alert on depth, not on arrival">

One dead letter is a bad phone number. Fifty in ten minutes is a provider outage that survived the
retry ladder — a different problem with a different response.

```yaml
- alert: NotificationsUndeliverable
  expr: increase(relay_undeliverable_total[10m]) > 20
  for: 5m
  labels: { severity: warning }
```

  </Step>
  <Step title="Triage by reason, because the two kinds are not alike">

<Terminal>
{`$ psql relay -c "select reason, count(*) from delivery_log
                  where status = 'UNDELIVERABLE'
                    and claimed_at > now() - interval '1 day'
                  group by reason order by 2 desc;"
              reason               | count
-----------------------------------+-------
 provider error                    |   214   ← retry these
 not in E.164 format               |    31   ← fix the data
 rate limited                      |     9   ← retry, more slowly`}
</Terminal>

  </Step>
  <Step title="Replay deliberately, never automatically">

A DLT that drains itself back onto the main topic is an infinite loop with extra steps. Replay is a
command someone runs, scoped to a reason and a window, after the cause is fixed.

<Terminal>
{`$ ./platform/replay-dlt.sh --reason "provider error" --since 2026-09-16T08:00Z --dry-run
would replay 214 records to notifications.requested.v1
$ ./platform/replay-dlt.sh --reason "provider error" --since 2026-09-16T08:00Z --confirm`}
</Terminal>

The claim rows are still there, so anything that actually got sent before failing is skipped on
replay. That is the property that makes replaying 214 records safe rather than terrifying.

  </Step>
</Steps>

<Callout type="prod">
Put a retention on the DLT that is long enough to act on — 30 days, not the default 7. The whole
point of the topic is that a person will look at it, and people take longer than brokers.

Give it the same partition count as the source topic, or a replay reorders everything relative to its
original partitioning for no benefit.
</Callout>

## What is left un-guaranteed

Worth saying out loud, because a system that claims more than it delivers is worse than one that is
honest.

<DecisionTable
  columns={['Guaranteed?', 'Why']}
  rows={[
    { label: 'Never sent twice', verdict: 'good', cells: ['Effectively', 'Claim-before-send plus a unique constraint'] },
    { label: 'Always sent at least once', verdict: 'bad', cells: ['No', 'A crash after claiming loses it — deliberately'] },
    { label: 'Sent in order', verdict: 'bad', cells: ['No', 'A retried record arrives after later ones'] },
    { label: 'Actually delivered', verdict: 'bad', cells: ['No', 'The provider accepted it; the handset is not our system'] },
    { label: 'Recorded accurately', verdict: 'mixed', cells: ['Mostly', 'A crash mid-send leaves a CLAIMED row of unknown outcome'] },
  ]}
/>

Those `CLAIMED` rows are the honest residue of the design. The sweeper reports them and deliberately
does **not** retry them: nobody knows whether the provider got the message, and re-sending on a maybe
is exactly the failure the whole lesson has been avoiding.
