The orchestrator needs to call three services and does not know where any of them are. The registry
from the previous lesson knows. This lesson is about the code in between — and about the fact that
Spring now offers two ways to write it, one of which is the future and one of which is what you will
find in the codebase you join.

## The same client, twice

<Compare>
  <Bad title="OpenFeign — what most Spring Cloud codebases use">

One annotation, one interface, no implementation. `name` is a **registry key**, not a hostname:
Spring Cloud LoadBalancer resolves it to the live instances and round-robins across them.

```java
@FeignClient(name = "email-service", configuration = ChannelClientConfig.class)
public interface EmailClient {

    @PostMapping("/api/emails")
    DeliveryReceipt send(@RequestBody EmailRequest request);
}
```

It is labelled "Bad" here only relative to the alternative. It works, it is everywhere, and it is
still maintained — but OpenFeign has been feature-complete since Spring Cloud 2022.0.0, and the
Spring team's own recommended migration path is the block on the right.

  </Bad>
  <Good title="Spring HTTP interfaces — what to reach for in new code">

The same shape with core Spring annotations and no extra dependency. `@LoadBalanced` on the builder
is what makes `http://email-service` resolve through the registry, exactly as `name` does above.

```java
@HttpExchange("/api/emails")
public interface EmailApi {

    @PostExchange
    DeliveryReceipt send(@RequestBody EmailRequest request);
}
```

```java
@Bean
EmailApi emailApi(RestClient.Builder builder) {          // the @LoadBalanced builder
    RestClient client = builder.clone().baseUrl("http://email-service").build();
    return HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(client))
            .build()
            .createClient(EmailApi.class);
}
```

  </Good>
</Compare>

Relay ships both, side by side, because the interesting part is not which is better — it is what
actually differs.

**The honest summary:** Feign gives you configuration by property and wiring by annotation. HTTP
interfaces give you configuration by code and wiring by bean. Feign is less to write; HTTP interfaces
are less to know. For a new service, take the one with fewer moving parts you did not choose.

<Callout type="prod">
What actually matters is not the choice — it is having made **one**. A codebase with `RestTemplate`
in three services, `WebClient` in two and Feign in one has three sets of timeout configuration, three
retry stories and three places to wire observability, which is how a service ends up with no timeout
at all.

Pick one, configure it properly, and put that configuration in a shared starter.
</Callout>

## The timeouts nobody sets

Feign's defaults are **10 seconds to connect and 60 seconds to read**. That is a reasonable default
for a batch job and a disaster for a caller that is holding a Kafka partition.

```yaml title="dispatch-orchestrator/application.yml"
spring.cloud.openfeign.client.config:
  default:
    connect-timeout: 2000
    read-timeout: 5000
  preference-service:
    read-timeout: 1000      # a primary-key read behind a cache
```

<Callout type="pitfall" title="Raising max.poll.interval.ms to fix this makes it worse">
The instinct when a consumer keeps getting evicted is to give it longer. That buys time for the
symptom and extends the window in which a genuinely dead consumer keeps its partitions — so failover
gets slower in exchange for hiding a slow dependency.

Set the client timeout below the work budget, so a hung provider fails fast and the record goes to a
retry topic. `max.poll.interval.ms` should be sized for the *legitimate* worst case, not the
pathological one.
</Callout>

## Making failures mean something

By default every non-2xx becomes a `FeignException`, which tells the orchestrator nothing. It cannot
distinguish a provider that is briefly down from a phone number that is not a phone number — and
those want opposite responses.

```java title="ChannelClientConfig.java"
return (methodKey, response) -> switch (response.status()) {
    case 400, 422 -> new MalformedRequestException(methodKey, body(response));
    case 404      -> new UnknownRecipientException(methodKey);
    case 429      -> new ChannelUnavailableException(methodKey, "rate limited");
    case 500, 502, 503, 504 -> new ChannelUnavailableException(methodKey, "provider error");
    default       -> new ChannelUnavailableException(methodKey, "unexpected " + response.status());
};
```

That distinction is what the next two lessons are built on: `ChannelUnavailableException` means try
another channel, `MalformedRequestException` means stop and involve a person.

<Callout type="pitfall" title="A Feign configuration class must not be a @Configuration">
`ChannelClientConfig` is deliberately a plain class. If it carried `@Configuration` and sat in a
scanned package, its `ErrorDecoder` bean would apply to **every** Feign client in the application
rather than the ones that named it.

The symptom is that a client you never touched starts throwing your domain exceptions, and nothing in
its own file explains why.
</Callout>

## Where the resilience goes

Neither interface above carries `@Retry` or `@CircuitBreaker`. That is deliberate and it is the rule
from [module 08](/learn/resilience/http-clients): the interface describes the remote API, and the
policy for calling it is a separate decision.

```java title="ChannelGateway.java" {1-2}
@CircuitBreaker(name = "preference-service", fallbackMethod = "conservativeDefaults")
@Retry(name = "preference-service")
public RecipientPreferences preferencesFor(UUID recipientId) {
    return preferences.byRecipient(recipientId);
}
```

Keeping them separate has a concrete payoff here: switching Relay from Feign to HTTP interfaces
changes the interface files and **nothing else**. The retry, the breaker, the fallback and every
decision built on them are untouched.

<Callout type="prod">
Note which methods have a `fallbackMethod` and which do not. `preferencesFor` falls back to
conservative defaults, because emailing someone who preferred SMS beats not sending a password reset.

`send` has no fallback, because there is nothing safe to return. A fabricated receipt would record a
delivery that never happened — and the failure has to propagate for the orchestrator to try the next
channel at all.
</Callout>
