[Module 07](/learn/microservices-fundamentals/service-discovery) showed you Eureka from the outside —
the client configuration, and a strong argument that you probably do not need it. This lesson runs
the other half: the registry itself, which that lesson never shows.

Start with the argument, because it decides whether the rest is relevant to you.

<Callout type="pitfall" title="On Kubernetes, do not build this">
A Kubernetes `Service` already gives you a stable name, health-based endpoint management and load
balancing. Adding Eureka on top means two systems that both believe they know which instances are
alive, and during a rollout they will disagree.

Relay runs on docker-compose precisely so that Eureka is the right answer rather than a redundant
one. That is the condition module 07 names: **VMs, ECS without service discovery, a hybrid estate, or
a genuine need for client-side load balancing.** If you are on Kubernetes, read this lesson for the
mechanism and then do not deploy it.
</Callout>

## A registry is a cache, not a database

This is the fact everything else follows from. Eureka holds its registry **in memory**, and it is
designed to lose it.

Three consequences worth stating plainly:

1. **A restarted registry comes back empty.** For one lease interval it will tell callers that
   nothing exists. This is why you run more than one.
2. **Clients cache the registry.** A client that has a stale copy keeps working when the registry is
   down — which is a feature, and the reason Eureka survives its own outage better than DNS does.
3. **Eviction is a sweep, not an event.** The instance is not removed when the lease expires; it is
   removed the next time the sweeper runs.

<Callout type="prod">
Module 07 does the arithmetic on the client side and reaches roughly a 90-second window in which a
dead instance is still being handed out. **Do not respond by tightening the heartbeat.** Faster
heartbeats multiply registry traffic by every instance you run, and they do not fix the real problem,
which is that callers must tolerate a dead address.

Retries with a circuit breaker — the [module 08](/learn/resilience/circuit-breakers) toolkit —
handle it. Discovery is best-effort routing, not a guarantee of liveness.
</Callout>

## The server

```java title="discovery-server/DiscoveryServerApplication.java" {2}
@SpringBootApplication
@EnableEurekaServer
public class DiscoveryServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(DiscoveryServerApplication.class, args);
    }
}
```

That is genuinely the whole server. Everything that matters is configuration.

```yaml title="discovery-server/application.yml"
eureka:
  client:
    # A registry is a client of its PEERS, not of itself.
    register-with-eureka: false
    fetch-registry: false
  server:
    enable-self-preservation: true
    renewal-percent-threshold: 0.85
    eviction-interval-timer-in-ms: 15000
```

## Self-preservation

The setting everybody turns off, and the one they should not.

Eureka counts the renewals it expects per minute. When actual renewals fall below
`renewal-percent-threshold` of that, it **stops evicting anything**.

<Compare>
  <Bad title="Self-preservation off">

The registry is now a liveness detector that trusts the network absolutely. A switch blip that
interrupts heartbeats for 90 seconds looks identical to every service dying simultaneously — so
Eureka evicts all of them, and every caller finds an empty registry.

```yaml
eureka:
  server:
    enable-self-preservation: false   # "stale entries in dev annoy me"
```

The entries were annoying. The outage is worse.

  </Bad>
  <Good title="On, with a threshold you chose">

Below 85% of expected renewals, Eureka concludes it has lost the network rather than the fleet, and
holds what it has. Callers get some stale addresses and retry past them, which is survivable.

```yaml
eureka:
  server:
    enable-self-preservation: true
    renewal-percent-threshold: 0.85
```

  </Good>
</Compare>

<Callout type="pitfall" title="Self-preservation misfires when your fleet is small or elastic">
The expected-renewal count is recalculated on a timer, not instantly. Scale from twenty instances to
four deliberately and Eureka may briefly believe sixteen are missing, trip self-preservation, and
keep serving sixteen dead addresses.

It resolves itself. It also means the honest position is: self-preservation is protection against a
**network** failure and a nuisance during a **deliberate** scale-down. On a small fleet, lower the
threshold rather than disabling it.
</Callout>

## Two registries, not one

A single registry is a single point of failure — but an unusual one, because it fails *open*: callers
keep using their cached copy. It becomes an outage only when a client restarts with no cache.

```yaml title="peer 1"
eureka:
  instance:
    hostname: eureka-1
  client:
    register-with-eureka: true       # each peer registers with the other
    fetch-registry: true
    service-url:
      defaultZone: http://eureka-2:8761/eureka/
```

Peers replicate registrations to each other, so either can serve the whole registry. The replication
is asynchronous and last-write-wins, so the peers can briefly disagree — acceptable, because the
data is a cache of heartbeats that will be re-sent within 30 seconds anyway.

<Callout type="tip" title="Point clients at both, and never at a load balancer">
`defaultZone` takes a comma-separated list, and the client tries them in order. Putting a load
balancer in front of the peers instead is a common instinct and it is worse: the client loses the
ability to fail over on its own, and you have added a component whose failure takes out discovery.
</Callout>

## Watching it work

<Steps>
  <Step title="See the registry">

The dashboard at `http://localhost:8761` lists every registered instance. Useful once; the JSON is
what you will actually script against.

<Terminal>
{`$ curl -s -H "Accept: application/json" http://localhost:8761/eureka/apps \\
    | jq -r '.applications.application[] | "\\(.name) \\(.instance | length) instance(s)"'
DISPATCH-ORCHESTRATOR 1 instance(s)
EMAIL-SERVICE 2 instance(s)
PREFERENCE-SERVICE 1 instance(s)
SMS-SERVICE 1 instance(s)`}
</Terminal>

  </Step>
  <Step title="Kill an instance and watch the window">

Stop one email-service replica and poll. The instance stays listed for well over a minute — this is
the staleness the lesson has been describing, and seeing it is more convincing than reading it.

<Terminal>
{`$ docker compose -f platform/docker-compose.yml stop relay-email-service-2
$ while true; do
    printf '%s ' "$(date +%T)"
    curl -s -H "Accept: application/json" http://localhost:8761/eureka/apps/EMAIL-SERVICE \\
      | jq '[.application.instance[] | select(.status=="UP")] | length'
    sleep 5
  done
14:02:10 2
14:02:15 2
...
14:03:25 1`}
</Terminal>

  </Step>
  <Step title="Confirm the caller survived it">

During that window the orchestrator is still being handed the dead address. Its logs should show
failed attempts that retried onto the surviving instance — not failed notifications.

If a notification failed, the problem is not discovery. It is that nothing downstream was configured
to tolerate a stale address, which is the next lesson.

  </Step>
</Steps>
