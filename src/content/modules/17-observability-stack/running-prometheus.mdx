Prometheus is a single binary with a local time-series database that scrapes HTTP endpoints on a
timer. Almost everything surprising about operating it follows from three facts: **it pulls, it
stores locally, and it is not clustered.**

## The storage engine

Samples arrive into a head block in memory and are periodically compacted onto disk in two-hour
blocks, which are later merged into larger ones.

The arithmetic is worth doing before you deploy, not after:

<Terminal>
{`# 1,000,000 active series, 15s scrape interval, 15 days retention
memory ≈ 1,000,000 × 3 KB              ≈ 3 GB just for the head
samples/s = 1,000,000 / 15             ≈ 66,700
disk ≈ 66,700 × 2 bytes × 86,400 × 15  ≈ 173 GB`}
</Terminal>

**Active series is the only number that matters.** Not requests, not scrape targets, not query
volume — series. And series count is a product of label cardinality, which is why a single careless
label is a capacity incident.

```yaml title="prometheus.yml"
global:
  scrape_interval: 15s
  scrape_timeout: 10s        # must be < scrape_interval
  external_labels:
    cluster: shopflow-prod   # essential once you have more than one Prometheus
    replica: A

scrape_configs:
  - job_name: spring-services
    metrics_path: /actuator/prometheus
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      # Only scrape pods that opt in with an annotation.
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: "true"
      # Promote useful pod metadata to labels.
      - source_labels: [__meta_kubernetes_pod_label_app]
        target_label: app
      - source_labels: [__meta_kubernetes_namespace]
        target_label: namespace
      - source_labels: [__meta_kubernetes_pod_name]
        target_label: pod
```

<Callout type="pitfall" title="Cardinality is the failure mode, and it arrives from application code">
A histogram with 12 buckets, labelled by `endpoint` (50), `method` (4) and `status` (6), is
14,400 series from one metric. Add `user_id` and it is unbounded — Prometheus consumes memory until
the kernel kills it, and the person who added the label sees nothing wrong in their own service.

Defend at the scrape, not only by asking nicely:

```yaml
    metric_relabel_configs:
      # Drop a known-bad metric entirely.
      - source_labels: [__name__]
        regex: 'http_server_requests_seconds_bucket'
        action: drop
      # Or strip a high-cardinality label before ingestion.
      - regex: 'user_id|request_id|session_id'
        action: labeldrop

    # And cap the blast radius per target.
    sample_limit: 20000
    label_limit: 30
```

`sample_limit` fails the scrape rather than ingesting the flood. A failed scrape for one service is a
much better outcome than an out-of-memory kill for the monitoring system that would have told you
about it.
</Callout>

## Pull, and its consequences

Prometheus scrapes targets. That is unusual, and it has real advantages: the monitoring system knows
whether a target is up (`up == 0` is free), there is no push endpoint to secure or overwhelm, and you
can point a browser at `/actuator/prometheus` and see exactly what Prometheus sees.

It also has one hard limit: **short-lived jobs die before they are scraped.**

The Pushgateway is widely misused. It does not expire what it holds, so a decommissioned job keeps
reporting its last value forever, and `up` no longer means anything for those series. Use it for
batch jobs and delete the group when the job is retired.

## Retention, remote write and long-term storage

Local retention is deliberately short — 15 to 30 days is typical, because the local TSDB is not
designed to be your data warehouse.

```bash
--storage.tsdb.retention.time=15d
--storage.tsdb.retention.size=200GB     # whichever triggers first
```

For anything longer, `remote_write` streams samples to a system built for it:

```yaml title="prometheus.yml — remote write with the queue tuned"
remote_write:
  - url: https://mimir.observability.svc/api/v1/push
    queue_config:
      capacity: 10000
      max_shards: 50
      min_shards: 4
      max_samples_per_send: 2000
      batch_send_deadline: 5s
    write_relabel_configs:
      # Do not pay to store what you will never query at 90 days.
      - source_labels: [__name__]
        regex: 'go_gc_.*|process_.*'
        action: drop
```

<Callout type="prod">
Federation is often reached for and is the wrong tool for raw series. Federating a million series
through one scrape endpoint moves the capacity problem rather than solving it, and adds a scrape
interval of staleness.

Federate **recording-rule aggregates** — a few hundred series per cluster — and use Thanos or Mimir
when you need the raw data centrally.
</Callout>

## High availability

Prometheus is not clustered. HA means running **two identical instances scraping the same targets**,
with different `replica` external labels, and deduplicating at query time.

```yaml
global:
  external_labels:
    cluster: shopflow-prod
    replica: A          # the other instance says B
```

They will not agree exactly — scrapes happen at different instants — so the deduplication layer
(Thanos Querier, or Alertmanager's own grouping for alerts) picks one. Alertmanager deduplicates
identical alerts from both replicas automatically, which is why alerting works correctly with this
setup without any extra configuration.

<Callout type="pitfall" title="Recording rules are not optional at scale">
A dashboard panel computing `histogram_quantile` over a `rate` across every pod re-evaluates the
whole expression on every refresh, for every viewer. During an incident, when everyone opens the
dashboard at once, the queries can take Prometheus down.

Precompute them:

```yaml title="rules/aggregates.yml"
groups:
  - name: shopflow-aggregates
    interval: 30s
    rules:
      - record: job:http_request_duration_seconds:p99
        expr: |
          histogram_quantile(0.99,
            sum by (job, le) (rate(http_server_requests_seconds_bucket[5m])))
      - record: job:http_requests:rate5m
        expr: sum by (job) (rate(http_server_requests_seconds_count[5m]))
```

The naming convention — `level:metric:operation` — is a Prometheus convention worth following, since
it makes it obvious at a glance which series are precomputed.
</Callout>
