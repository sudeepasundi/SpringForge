[Module 10](/learn/observability/structured-logging) covered what to put in a log line and why it
should be JSON. This lesson is about everything that happens after your application writes it: how it
leaves the container, what carries it, where it lands, and why the bill is what it is.

## The pipeline

  caption="Four stages. Each is a place logs are lost, delayed or made expensive — and the application only participates in the first one."

<Callout type="prod">
The application's only job is **write JSON to stdout and stop caring.** Logging to a file inside a
container means the file dies with the pod and nothing collects it. Shipping directly from the
application over the network means your service now fails when the log backend is slow — you have
coupled request handling to an observability system, which is the wrong direction entirely.

Stdout is decoupled by construction: the runtime writes it to disk, and the agent's problems stay the
agent's problems.
</Callout>

```yaml title="fluent-bit.conf — the shape of a Kubernetes DaemonSet collector"
[SERVICE]
    Flush         5
    Log_Level     warn
    storage.path  /var/log/flb-storage/     # disk buffering, not memory
    storage.sync  normal
    storage.backlog.mem_limit 64M

[INPUT]
    Name              tail
    Path              /var/log/containers/*.log
    Parser            cri
    Tag               kube.*
    Mem_Buf_Limit     32MB                  # per input — see the pitfall
    Skip_Long_Lines   On
    Refresh_Interval  10
    DB                /var/log/flb_kube.db  # remembers file offsets across restarts

[FILTER]
    Name                kubernetes
    Match               kube.*
    Merge_Log           On                  # parse the JSON your app emitted
    Keep_Log            Off                 # drop the raw duplicate — halves the volume
    Labels              On
    Annotations         Off

[OUTPUT]
    Name    loki
    Match   kube.*
    host    loki.observability.svc
    labels  job=fluent-bit, namespace=$kubernetes['namespace_name'], app=$kubernetes['labels']['app']
    Retry_Limit 5
```

<Callout type="pitfall" title="Mem_Buf_Limit with memory buffering drops logs silently">
When the backend is slow and the buffer fills, Fluent Bit **pauses the input** — and while it is
paused, the container runtime keeps rotating files. Rotated-away data is gone. The logs you most want
are the ones from the incident that also overloaded the log backend.

Two mitigations, both required: **`storage.type filesystem`** so the buffer spills to disk instead of
stalling, and an alert on the agent's own `fluentbit_output_retries_failed_total`. A log pipeline that
does not monitor itself will fail invisibly, and you will discover it while looking for logs that do
not exist.
</Callout>

## Loki against Elasticsearch

The architectural difference is what gets indexed.

<Compare>
  <Bad title="Elasticsearch indexes the content">

Every field in every log line is inverted-indexed. Queries on any field are fast, and the index is
often larger than the data. Storage and memory cost scale with volume and with cardinality, and a
mapping explosion from a high-cardinality field is a classic outage.

```text
# Full-text search across message bodies — fast, and paid for up front.
message:"payment declined" AND service:"payment-service"
```

  </Bad>
  <Good title="Loki indexes only labels">

Labels are indexed; the log body is compressed and stored in object storage. Queries filter by label
first, then brute-force scan the matching chunks — which is slower on broad searches and dramatically
cheaper to run.

```logql
{namespace="shopflow", app="payment-service"}
  |= "payment declined"
  | json
  | duration > 500ms
```

  </Good>
</Compare>

For a Kubernetes estate where you almost always start from "this service, this hour", Loki is
usually the better trade. Elasticsearch earns its cost when log content is a primary search surface —
security investigation, or product analytics built on logs.

<Callout type="pitfall" title="High-cardinality labels destroy Loki">
Every distinct combination of label values creates a **stream**, and each stream is a separate set of
chunks. Putting a request id, a user id or a trace id in a label produces millions of streams and
Loki falls over.

```text
BAD   {app="payment", trace_id="4bf92f...", user_id="88af"}
GOOD  {app="payment", namespace="shopflow", level="error"}
```

The identifiers belong **in the log body**, where they are searchable with a filter expression and
cost nothing to store. This is the same cardinality lesson as
[module 10](/learn/observability/metrics-micrometer) taught for Prometheus labels, and it bites the
same way.
</Callout>

## Retention, and the bill

Log volume is the observability cost that surprises people, because it grows with traffic *and* with
every well-meaning `log.info` someone adds.

<Steps>
  <Step title="Sample the routine, keep all the exceptional">

Access logs for successful requests are the bulk of the volume and the least of the value. Sample
them at 1–10%; keep every 4xx and 5xx.

  </Step>
  <Step title="Tier retention by usefulness">

7 days hot for interactive debugging, 30 days warm, a year in cheap object storage for compliance.
Almost nobody queries a 90-day-old `INFO` line, and everybody pays to keep it.

  </Step>
  <Step title="Drop noise at the collector, not the source">

The application should not know about retention policy. Dropping in the agent means one place to
change and no redeploy.

```yaml title="Vector — drop health-check noise before it costs anything"
transforms:
  drop_probes:
    type: filter
    inputs: [kubernetes_logs]
    condition: '!contains(string!(.message), "/actuator/health")'
```

  </Step>
  <Step title="Alert on your own log volume">

A per-service bytes-per-second metric catches a debug logger left on in production before the invoice
does. This is the single highest-return alert in the whole stack.

  </Step>
</Steps>

<Callout type="prod">
Put the **trace id in every log line** — [module 10](/learn/observability/distributed-tracing) shows
the MDC wiring. It costs one field and it turns log search from "grep and hope" into "show me
everything that happened during this request, across every service".

That single field is worth more than any amount of log-platform sophistication, and it is the thing
most often missing.
</Callout>
