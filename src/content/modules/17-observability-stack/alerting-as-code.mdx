The failure mode of alerting is not missing an alert. It is having so many that nobody reads them —
at which point you have all the cost of monitoring and none of the benefit, and the outage you built
it for goes unnoticed among the noise.

Everything in this lesson is aimed at that.

## The split

Prometheus evaluates rules and decides an alert is **firing**. Alertmanager decides who hears about
it, when, and whether it is worth waking someone.

This division is why HA works without effort: two Prometheus replicas send identical alerts and
Alertmanager deduplicates them, because the alert's identity is its label set and both replicas
produce the same one.

## Writing a rule worth waking up for

```yaml title="rules/slo.yml"
groups:
  - name: shopflow-slo
    interval: 30s
    rules:
      - alert: HighErrorRate
        expr: |
          sum by (job) (rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          /
          sum by (job) (rate(http_server_requests_seconds_count[5m]))
          > 0.05
        for: 5m                      # must hold for 5m — kills the flapping
        labels:
          severity: critical
          team: payments
        annotations:
          summary: "{{ $labels.job }} error rate is {{ $value | humanizePercentage }}"
          description: >
            More than 5% of requests to {{ $labels.job }} have failed for 5 minutes.
          runbook_url: https://wiki.shopflow.dev/runbooks/high-error-rate
          dashboard_url: https://grafana.shopflow.dev/d/shopflow-overview
```

<Callout type="prod">
`for: 5m` is the single most important field. Without it, one bad scrape or a 30-second blip pages
someone — and after the third false page, people stop reading the channel. The duration is what
distinguishes a condition from a moment.

`runbook_url` is the second. An alert that arrives at 3 a.m. with no instructions is a puzzle handed
to whoever is least equipped to solve it. If you cannot write the runbook, the alert probably should
not page.
</Callout>

## Alert on symptoms, not causes

<Compare>
  <Bad title="Cause-based alerts">

Each of these fires when something is *unusual*, not when anything is *wrong*. High CPU on a service
that is comfortably meeting its SLO is not an incident, and paging on it teaches people that pages
are ignorable.

```yaml
- alert: HighCPU
  expr: rate(process_cpu_seconds_total[5m]) > 0.8
- alert: PodRestarted
  expr: increase(kube_pod_container_status_restarts_total[1h]) > 0
- alert: HighMemory
  expr: jvm_memory_used_bytes / jvm_memory_max_bytes > 0.85
```

  </Bad>
  <Good title="Symptom-based alerts">

Each of these means a user is having a bad time, whatever the cause. There are far fewer of them, and
every one of them is worth a human's attention.

```yaml
- alert: HighErrorRate          # users are getting errors
- alert: HighLatency            # users are waiting
- alert: QueueGrowing           # work is not being done
- alert: ErrorBudgetBurnFast    # you will miss the SLO
```

  </Good>
</Compare>

The cause metrics are not useless — they are exactly what you want on a **dashboard**, for the person
diagnosing the symptom. The distinction is: symptoms page, causes inform.

## Burn-rate alerting

A fixed threshold has to choose between catching a fast outage and catching a slow leak. Multi-window
burn rate does both.

```yaml
      # Fast burn: 14.4× the budget rate over 1h means the entire
      # 30-day budget is gone in ~2 days. Page immediately.
      - alert: ErrorBudgetBurnFast
        expr: |
          job:slo_error_ratio:rate1h  > (14.4 * 0.001)
          and
          job:slo_error_ratio:rate5m  > (14.4 * 0.001)
        for: 2m
        labels: { severity: critical }

      # Slow burn: 6× over 6h. A ticket, not a page.
      - alert: ErrorBudgetBurnSlow
        expr: |
          job:slo_error_ratio:rate6h > (6 * 0.001)
          and
          job:slo_error_ratio:rate30m > (6 * 0.001)
        for: 15m
        labels: { severity: warning }
```

The short second window is what makes this respond quickly *and* recover quickly: the alert clears as
soon as the burn stops, rather than staying lit for the length of the long window. This connects
directly to the SLO material in [module 10](/learn/observability/slos-and-alerting) — the rules here
are how that arithmetic becomes something that actually wakes a person.

## Routing, grouping and inhibition

```yaml title="alertmanager.yml"
route:
  receiver: slack-default
  group_by: [alertname, cluster, namespace]
  group_wait: 30s          # collect related alerts before the first notification
  group_interval: 5m       # then batch new members of the group
  repeat_interval: 4h      # re-notify an unresolved alert this often

  routes:
    - matchers: [severity="critical"]
      receiver: pagerduty
      group_wait: 10s
      repeat_interval: 1h
    - matchers: [team="payments"]
      receiver: slack-payments
      continue: true       # keep evaluating later routes too
    - matchers: [severity="info"]
      receiver: "null"     # deliberately dropped

inhibit_rules:
  # If the whole cluster is down, do not also page about every service in it.
  - source_matchers: [alertname="ClusterDown"]
    target_matchers: [severity=~"warning|critical"]
    equal: [cluster]

  # A critical alert suppresses the warning version of the same thing.
  - source_matchers: [severity="critical"]
    target_matchers: [severity="warning"]
    equal: [alertname, cluster, namespace]

receivers:
  - name: pagerduty
    pagerduty_configs:
      - service_key: ${PAGERDUTY_KEY}
        description: "{{ .CommonAnnotations.summary }}"
  - name: "null"
```

<Callout type="pitfall" title="group_by: [...] with too many labels defeats grouping entirely">
Grouping by a label that differs per instance — `pod`, `instance`, `endpoint` — creates one group per
value, so a node failure sends forty separate notifications instead of one.

Group by the labels that describe **the problem**, not the labels that describe *where it is*. The
individual instances belong in the notification body, which is what `.Alerts` gives you in the
template.
</Callout>

<Callout type="prod">
Inhibition is the highest-leverage feature in Alertmanager and the least used. During a real incident
the symptom alerts cascade — one database failure lights up every service that depends on it — and
the on-call engineer is handed thirty pages describing one problem.

Two or three inhibit rules turn that into one. Write them the first time you experience the cascade,
while you still remember which alert was the cause.
</Callout>

## Everything in git

```text
observability/
  rules/            # Prometheus alerting and recording rules
  alertmanager/     # routing, receivers, inhibitions
  dashboards/       # exported Grafana JSON
  provisioning/     # Grafana datasource and dashboard providers
```

```yaml title="Grafana provisioning — dashboards loaded from disk, not clicked"
apiVersion: 1
providers:
  - name: shopflow
    folder: ShopFlow
    type: file
    disableDeletion: true
    allowUiUpdates: false      # the UI becomes read-only; git is the source
    options:
      path: /etc/grafana/dashboards
```

`allowUiUpdates: false` is the line that makes this real. Without it, someone fixes a panel in the UI,
the next deploy silently reverts it, and after that happens twice nobody trusts the provisioning.

<Callout type="prod">
Validate rules in CI, so a broken expression is a failed build rather than an alert that silently
never fires:

```bash
promtool check rules observability/rules/*.yml
promtool test rules observability/rules/tests/*.yml
amtool check-config observability/alertmanager/alertmanager.yml
```

`promtool test rules` is unit testing for alerts — you provide a series of samples and assert which
alerts fire and when. An alert that has never been observed to fire is an untested code path in the
system you depend on most during an incident, and this is how you test it without an outage.
</Callout>

## Reviewing what you have

Alert quality decays. New alerts get added during incidents; nothing removes them afterwards.

<Steps>
  <Step title="Count pages per week per person">

More than roughly two is unsustainable, and the response will be to stop reading them rather than to
fix the cause.

  </Step>
  <Step title="Measure the actionable rate">

For every page: did a human do something? An alert with a low actionable rate should be demoted to a
ticket or deleted. `ALERTS` is itself a metric, so this is a query, not a survey.

  </Step>
  <Step title="Delete alerts nobody acts on">

An alert that has fired twenty times and been acknowledged twenty times without action is worse than
no alert — it consumes attention and trains people to dismiss the channel.

  </Step>
  <Step title="Check for silences that never expire">

`amtool silence query` will show you the ones somebody added during an incident eight months ago and
forgot. Every permanent silence is a monitoring gap nobody knows about.

  </Step>
</Steps>
