Your services can export straight to a tracing backend. Almost nobody should: it hardcodes the
backend into every service, puts sampling decisions in application configuration, and means changing
vendor is a fleet-wide redeploy.

The OpenTelemetry Collector is the indirection that fixes all three. Services export to it; it
decides everything else.

## The pipeline model

Three stages, composed per signal type.

```yaml title="otel-collector.yaml"
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }

processors:
  # ALWAYS first. Rejects data rather than letting the collector OOM.
  memory_limiter:
    check_interval: 1s
    limit_percentage: 80
    spike_limit_percentage: 15

  k8sattributes:
    auth_type: serviceAccount
    extract:
      metadata: [k8s.namespace.name, k8s.pod.name, k8s.deployment.name, k8s.node.name]

  resource:
    attributes:
      - { key: deployment.environment, value: production, action: upsert }

  # ALWAYS last before the exporter. Batching is the single biggest
  # efficiency win in the whole pipeline.
  batch:
    timeout: 5s
    send_batch_size: 8192
    send_batch_max_size: 10000

exporters:
  otlp/tempo:
    endpoint: tempo.observability.svc:4317
    tls: { insecure: true }
    sending_queue:
      enabled: true
      num_consumers: 10
      queue_size: 5000
    retry_on_failure:
      enabled: true
      initial_interval: 5s
      max_elapsed_time: 300s

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, k8sattributes, resource, batch]
      exporters: [otlp/tempo]
  telemetry:
    metrics:
      level: detailed      # the collector's own metrics — scrape these
```

<Callout type="pitfall" title="Processor order is not cosmetic">
`memory_limiter` **first** — it can only protect the collector if it sees data before anything else
allocates on it. `batch` **last** — batching before a processor that drops data means you batched
work you then threw away.

Getting this wrong produces a collector that OOMs under exactly the load spike it was deployed to
survive, and the configuration looks perfectly reasonable in review.
</Callout>

## Agent and gateway

One collector per node, and a pool behind it. The split exists because of tail sampling.

    },

/>

The application always exports to `localhost` or a node-local service. It never knows a backend
exists.

```yaml title="Spring — the app config is this small, and stays this small"
otel:
  exporter:
    otlp:
      endpoint: http://otel-collector.observability.svc:4318
      protocol: http/protobuf
  resource:
    attributes:
      service.name: order-service
      service.version: ${BUILD_VERSION:dev}
```

Changing tracing backend, adjusting sampling, adding a second destination — none of that touches this
file or redeploys a service.

## Where tail sampling actually runs

Head sampling decides at the first span, before anything is known. Tail sampling decides after the
whole trace has arrived, so it can keep the interesting ones.

<Compare>
  <Bad title="Head sampling — the decision is made blind">

Sample 1% at the root and the decision propagates. It is cheap and it discards 99% of your errors,
because at the moment of the decision nobody knows the request will fail.

```yaml
# In the application — decided before the request is handled.
otel.traces.sampler: parentbased_traceidratio
otel.traces.sampler.arg: 0.01
```

  </Bad>
  <Good title="Tail sampling — decide once you know what happened">

Keep every error, keep everything slow, sample the boring remainder. You pay to buffer traces for the
decision window and you keep the traces that are worth having.

```yaml
processors:
  tail_sampling:
    decision_wait: 10s          # must exceed your slowest trace
    num_traces: 100000
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 1000 }
      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 5 }
```

  </Good>
</Compare>

<Callout type="pitfall" title="Tail sampling requires every span of a trace to reach the same collector">
The decision needs the complete trace. If spans from one request land on three different gateway
replicas, each sees a fragment and decides independently — producing broken, partial traces that are
worse than no trace at all.

The fix is a **load-balancing exporter** on the agents, which routes by trace id:

```yaml
exporters:
  loadbalancing:
    routing_key: traceID
    protocol:
      otlp: { tls: { insecure: true } }
    resolver:
      dns:
        hostname: otel-gateway-headless.observability.svc
```

Agents load-balance by trace id to the gateway pool; only the gateway does `tail_sampling`. Skip this
and tail sampling appears to work in a single-replica test environment and produces fragments in
production.
</Callout>

`decision_wait` is the other trap: it must be longer than your slowest trace, or long traces are
decided on incomplete data. Memory is `num_traces` × average trace size held for `decision_wait` —
budget for it.

## Tempo against Jaeger

<DecisionTable
  columns={['Storage', 'Search', 'Best for']}
  rows={[

    },
    {
      label: 'Jaeger',

      cells: ['Cassandra or Elasticsearch', 'Rich attribute search', 'Exploratory search when you have no trace id'],
    },
  ]}
/>

Tempo's bet is the same as Loki's: **you almost always arrive with a trace id** — from a log line, an
exemplar on a Prometheus graph, or an error report. Given that, an index is expensive infrastructure
for a workflow you rarely use, and dropping it makes trace storage nearly free.

<Callout type="prod">
Exemplars are the connective tissue and are widely unknown. Micrometer attaches trace ids to
histogram buckets, so a spike on a latency graph in Grafana becomes clickable — straight to a trace
of a request that was actually slow.

```yaml
management:
  tracing:
    sampling:
      probability: 1.0        # sample everything in-app; let the collector decide
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
```

Sampling at 100% in the application and tail-sampling in the collector is the right division: the
application should not be making retention decisions, and cannot make good ones.
</Callout>
