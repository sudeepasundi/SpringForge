The same image runs in development, staging and production. Everything that differs between them
comes from the environment — that is the twelve-factor rule, and it is what makes "promote the
artifact you tested" possible at all.

## Config is what varies between deploys

The test is not "does it look like configuration?" but **"does this differ between environments?"**

end up as untested, unreviewed, unversioned logic that someone changes in a console at 2am — with no
pull request and no way to test it beforehand.

## The precedence that makes this work

From [module 02](/learn/boot-essentials/configuration-properties): environment variables outrank every
packaged file. That single fact is what lets one image behave correctly everywhere.

```yaml title="application.yml — shipped in the jar"
spring:
  datasource:
    url: ${DB_URL}                  # no default: startup fails if unset
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: ${DB_POOL_SIZE:10}   # a default that can be overridden
  jpa:
    open-in-view: false
logging:
  level:
    dev.springforge: ${LOG_LEVEL:INFO}
```

Two placeholder styles, used deliberately. `${DB_PASSWORD}` with **no default** fails startup rather
than connecting with an empty credential. `${DB_POOL_SIZE:10}` has a sensible default that production
can raise.

<Callout type="tip" title="Make the packaged defaults production-shaped">
The unprofiled `application.yml` should describe production behaviour, and development should loosen
it. Get that backwards and a forgotten profile means production runs with debug logging, SQL tracing
and an embedded database — a configuration mistake becoming an incident.
</Callout>

## Where secrets come from

<DecisionTable
  columns={['Rotation', 'Audit', 'Verdict']}
  rows={[
    { label: 'Committed to git', verdict: 'bad', cells: ['Impossible', 'None', 'Compromised the moment it is pushed'] },
    { label: 'Kubernetes Secret', verdict: 'mixed', cells: ['Manual', 'Via the API server', 'Base64, not encryption — acceptable with RBAC and etcd encryption'] },
    { label: 'External Secrets Operator', verdict: 'good', cells: ['Automatic sync', 'In the source store', 'A good default — the platform store, surfaced as a K8s Secret'] },
    { label: 'Vault Agent injection', verdict: 'good', cells: ['Automatic, with leases', 'Full', 'Strongest; also the most machinery'] },
    { label: 'Cloud IAM (no secret)', verdict: 'good', cells: ['N/A', 'Full', 'Best of all — a credential that does not exist cannot leak'] },
  ]}
/>

The last row deserves emphasis. IRSA on EKS, Workload Identity on GKE and Managed Identity on Azure
let a pod authenticate to a cloud service using its own identity, with **no credential anywhere**.
Where the platform supports it, that beats every form of secret storage, because the safest secret is
the one that does not exist.

```yaml title="External Secrets Operator: the source of truth stays in the platform store"
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: order-service-secrets
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: order-service-secrets     # the K8s Secret it creates
  data:
    - secretKey: DB_PASSWORD
      remoteRef:
        key: prod/order-service/db
        property: password
```

```yaml title="deployment.yaml"
envFrom:
  - configMapRef: { name: order-service-config }
  - secretRef: { name: order-service-secrets }
```

The application sees ordinary environment variables and knows nothing about Vault or AWS. That is the
point: no SDK, no startup dependency on a secret store, and the same image runs anywhere.

<Callout type="pitfall" title="Rotation is not a property of your secret store">
A store that rotates a credential every 30 days achieves nothing if your application read it into a
field at startup and never looks again. **Rotation only works if the application can pick up the new
value**, which usually means it must tolerate two valid credentials during the changeover.

The practical test: rotate a credential in staging and see whether anything breaks. If nobody has
ever done that, you do not have rotation — you have a store that changes a value your services
ignore.
</Callout>

## Where secrets leak without being committed

Repeating the list from [module 05](/learn/security/security-hardening) because this is the lesson
where it becomes operational:

- **`/actuator/heapdump`** — every secret in memory, in plain text, over HTTP.
- **Debug logging of request bodies** — credentials on the login endpoint.
- **Exception messages returned to clients** — a JDBC exception carrying the connection URL.
- **Docker image layers** — a file added in one layer and deleted in a later one is still extractable.
- **CI logs** — an unmasked variable in a build step, readable by anyone with repository access.
- **`kubectl describe pod`** — environment variables are shown in plain text to anyone with read
  access to the namespace.

That last one surprises people and is worth designing around: `envFrom` a Secret puts the value in
the pod spec's resolved environment, visible to anyone who can `describe`. Mounting as a file avoids
it, at the cost of your application needing to read the file.

## Environment parity

The gap between environments is where surprises live.

<Compare>
  <Bad title="Environments that differ in kind">

Every difference is a class of bug that only production can produce: H2 accepts SQL Postgres
rejects, one instance hides every concurrency problem, and an in-memory broker has no partitions, no
consumer groups and no rebalancing.

```text
development:  H2, in-memory Kafka, one instance
staging:      PostgreSQL 14, real Kafka, one instance
production:   PostgreSQL 16, Kafka cluster, twelve instances
```

  </Bad>
  <Good title="Same kind, different scale">

Every environment runs the same technologies at the same versions. Differences are in capacity, which
does not change behaviour — and Testcontainers makes the development row free.

```text
development:  PostgreSQL 16 (Testcontainers), Kafka (Testcontainers), 1 instance
staging:      PostgreSQL 16, Kafka (3 brokers), 2 instances
production:   PostgreSQL 16, Kafka (3 brokers), 12 instances
```

  </Good>
</Compare>

The "one instance" difference is worth its own mention. A service that only ever runs single-instance
in development hides every concurrency bug: a `@Scheduled` job with no lock, an in-memory rate
limiter, a local cache that assumes it is the only one. Run two instances locally with
`docker compose up --scale order-service=2` and those surface immediately.

<Callout type="prod">
Validate configuration at startup with `@Validated @ConfigurationProperties`, as in
[module 02](/learn/boot-essentials/typed-config). Centralised configuration means a typo in a shared
value can break every service that reads it — and failing fast in the first instance to roll is
enormously cheaper than discovering it from behaviour.
</Callout>

## A configuration checklist

Worth running against a service before it first goes to production:

```text
□ No secrets in the repository, and a scanner in CI enforcing that
□ Every secret injected from the environment, with no default placeholder
□ Packaged defaults describe production; profiles loosen for development
□ Config bound to @Validated types, so a bad value fails at startup
□ Pool sizes, timeouts and thread counts overridable per environment
□ Log level changeable without a redeploy
□ Same database and broker versions in every environment
□ At least two instances in every environment above development
□ A credential has actually been rotated at least once, in staging
```
