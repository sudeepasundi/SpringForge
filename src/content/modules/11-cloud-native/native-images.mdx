A GraalVM native image starts in about 50 milliseconds and uses a fraction of the memory. The demo is
genuinely impressive.

The demo does not mention that the build takes six minutes, that reflection needs declaring, that
peak throughput is often lower, and that your profiler no longer works.

## What ahead-of-time compilation changes

The throughput row surprises people. The JIT compiles from *observed* behaviour — it inlines the
branch your production traffic actually takes and deoptimises when that assumption breaks. AOT
compiles once, without ever seeing a request, so it cannot make those choices.

Native wins on startup and memory. It generally loses on sustained throughput.

## The closed-world assumption

Everything follows from this: the compiler must know, at build time, every class that will ever be
loaded and every method that will ever be reflected on. It walks reachable code from `main` and
discards the rest.

Anything discovered at runtime is invisible to that analysis:

```java
// The analyser cannot know which class this is. If nothing else references
// PaymentProcessor, it was not compiled into the image at all.
Class<?> type = Class.forName(config.getProcessorClass());

// A dynamic proxy over an interface that must exist in the image.
Object proxy = Proxy.newProxyInstance(loader, new Class[]{ handlerType }, handler);

// A resource that must have been explicitly included.
InputStream in = getClass().getResourceAsStream("/templates/" + name + ".ftl");
```

Each fails at **runtime**, in the image, with `ClassNotFoundException` or a null resource — having
worked perfectly on the JVM.

<Callout type="tip" title="Spring does most of this for you">
Spring Boot's AOT processing runs at build time, evaluates your configuration, and generates the
reflection, proxy and resource hints for everything the framework knows about — your beans, your
`@ConfigurationProperties`, your JPA entities, your Jackson DTOs.

The gap is code Spring cannot see: your own reflection, and libraries without native support. That
is a much smaller surface than it used to be, and it is where the remaining work is.
</Callout>

## Declaring hints

```java title="support/NativeHints.java" {5-9,14-18}
@Configuration
@ImportRuntimeHints(NativeHints.Registrar.class)
public class NativeHints {

    static class Registrar implements RuntimeHintsRegistrar {

        @Override
        public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
            // Reflection: this type is instantiated by name from configuration.
            hints.reflection().registerType(StripeProcessor.class,
                    MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS,
                    MemberCategory.INVOKE_PUBLIC_METHODS);

            // Resources: a pattern, because the filenames come from config.
            hints.resources().registerPattern("templates/*.ftl");

            // Serialization: needed for anything Java-serialised, such as
            // session state or a cache that has not moved to JSON yet.
            hints.serialization().registerType(SessionState.class);

            // Proxies: the interface list must match exactly.
            hints.proxies().registerJdkProxy(PaymentGateway.class, Auditable.class);
        }
    }
}
```

For a whole package of types serialised by Jackson, `@RegisterReflectionForBinding` is far less
tedious:

```java
@RegisterReflectionForBinding({ OrderPlaced.class, StockReserved.class, PaymentCaptured.class })
@Configuration
class EventSerializationHints { }
```

## Finding what you missed

Guessing at hints is miserable. The tracing agent generates them from a real run:

<Terminal>
{`$ java -agentlib:native-image-agent=config-output-dir=src/main/resources/META-INF/native-image \\
       -jar target/order-service-1.0.0.jar

# Now exercise the application — run the full integration test suite against it,
# not just the happy path. The agent only records what actually executes.

$ ./mvnw verify -Dtest.target=http://localhost:8080

$ ls src/main/resources/META-INF/native-image/
reflect-config.json  resource-config.json  proxy-config.json  serialization-config.json`}
</Terminal>

<Callout type="pitfall" title="The agent only sees code paths that ran">
A reflective call on an error-handling branch that your test suite never triggers produces no hint,
and the image fails at exactly that moment in production — the worst possible time for a new failure
mode.

The agent is a starting point, not a guarantee. **Run your full integration suite against the native
image itself**, not just against the JVM build, or you have tested a different artifact than the one
you deploy.
</Callout>

<Callout type="prod">
The cost nobody mentions in the demo is **debugging**. JFR support is limited, async-profiler does
not attach, heap dumps are not what you know, and JMX is largely absent.

When a native service misbehaves in production, the tooling you would normally reach for is not
there. That is a serious consideration for a service you are on call for, and it should weigh at
least as heavily as the startup number in the decision.
</Callout>

## AOT without going native

Spring's AOT processing works on the JVM too, and it is the option most teams should actually take:

```bash
./mvnw spring-boot:process-aot
java -Dspring.aot.enabled=true -jar target/order-service-1.0.0.jar
```

It pre-computes the bean definitions, cutting roughly 30% off startup while keeping the JIT, the
tooling and every debugging option. That is a large fraction of the benefit for none of the cost, and
it is worth trying before committing to native.
