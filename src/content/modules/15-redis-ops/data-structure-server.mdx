[Module 04](/learn/data/caching-redis) used Redis as a cache: `GET`, `SET`, a TTL. That is a small
fraction of what it does, and treating it as a key-value store means solving in application code
problems Redis solves in one command.

It also means missing the property that governs everything: **Redis executes commands one at a
time.**

## Single-threaded, and why that matters

Command execution is single-threaded. Not I/O — Redis 6+ uses threads for reading and writing
sockets — but the actual execution of every command, in order, one after another.

The trade is worth understanding rather than resenting. Single-threaded execution is why **every
Redis command is atomic for free** — no locks, no isolation levels, no lost updates. `INCR` cannot
interleave with another `INCR`. That simplicity is bought by making every command block every other
one.

<Callout type="pitfall" title="The commands to ban outright">
Each of these is O(n) over the whole keyspace or a whole collection, and each will freeze the server
for as long as it runs:

```bash
KEYS *                  # scans every key. Use SCAN, which is cursor-based.
FLUSHALL                # synchronous by default. FLUSHALL ASYNC if you must.
SMEMBERS huge-set       # returns everything. Use SSCAN.
HGETALL huge-hash       # same. Use HSCAN.
DEL huge-key            # frees every element inline. Use UNLINK (async).
```

`KEYS` in production is the classic. It looks harmless in a console, runs in 3ms on a development
dataset, and takes the better part of a second against eight million keys — during which nothing
else is served.

Disable them in `redis.conf` so nobody can:

```conf
rename-command KEYS ""
rename-command FLUSHALL ""
rename-command CONFIG ""
```
</Callout>

## Sorted sets solve more than you expect

<Compare>
  <Bad title="Rebuilding it in the application">

Fetch everything, sort in the JVM, take a page. It transfers the whole set over the network on every
request and gets slower as the set grows.

```java
Set<String> all = redis.opsForSet().members("leaderboard");   // blocks Redis
List<Score> sorted = all.stream()
        .map(this::lookupScore)                               // N more round trips
        .sorted(comparing(Score::value).reversed())
        .limit(10)
        .toList();
```

  </Bad>
  <Good title="Letting Redis do it">

One command, O(log n + 10), no transfer of anything you did not ask for. The set stays sorted as it
is written.

```java
// Update a score — the ordering is maintained by Redis.
redis.opsForZSet().incrementScore("leaderboard", playerId, points);

// Top 10, with scores.
Set<TypedTuple<String>> top =
        redis.opsForZSet().reverseRangeWithScores("leaderboard", 0, 9);

// One player's rank, without fetching anything else.
Long rank = redis.opsForZSet().reverseRank("leaderboard", playerId);
```

  </Good>
</Compare>

A sorted set also gives you a **sliding-window rate limiter** in three commands, which is the
mechanism behind the edge rate limiting in
[module 07](/learn/microservices-fundamentals/api-gateway):

```lua
-- Score is the timestamp, so a range query is a time window.
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])  -- drop expired
local count = redis.call('ZCARD', KEYS[1])
if count < tonumber(ARGV[3]) then
    redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])              -- record this request
    redis.call('EXPIRE', KEYS[1], ARGV[2] / 1000)
    return 1
end
return 0
```

## Scripts and transactions

Redis has two ways to make several commands atomic, and they are not equivalent.

<DecisionTable
  columns={['Atomic?', 'Can branch on a value?', 'Use when']}
  rows={[
    {
      label: 'MULTI/EXEC',
      verdict: 'mixed',
      cells: ['Yes — queued and executed together', 'No — commands are queued before any result is seen', 'A fixed batch with no conditional logic'],
    },
    {
      label: 'Lua script (EVAL)',
      verdict: 'good',
      cells: ['Yes — the script is one command', 'Yes — you have the results as you go', 'Read-then-decide-then-write, which is most real cases'],
    },
  ]}
/>

The distinction matters because `MULTI/EXEC` cannot express "read this, and write only if". That is
exactly what a rate limiter, a lock, or a conditional decrement needs — so Lua is the usual answer,
and the script runs as a single atomic command.

<Callout type="prod">
A Lua script blocks the server for its whole duration, like any other command. Keep scripts short and
bounded — no loops over an unbounded collection, no `KEYS` — and be aware that
`lua-time-limit` does **not** kill a running script; it only starts returning `BUSY` to other
clients, and the script keeps going until it finishes or you `SCRIPT KILL` it.

A slow script is therefore a full outage, not a slow query.
</Callout>

## Streams, and how they differ from Kafka

Redis Streams look like Kafka and are not a replacement for it.

<DecisionTable
  columns={['Redis Streams', 'Kafka']}
  rows={[
    { label: 'Consumer groups', cells: ['Yes, with per-message acknowledgement', 'Yes, with positional offsets'] },
    { label: 'Stuck message', verdict: 'good', cells: ['Stays pending; claim it with XCLAIM. Does not block others', 'Blocks its partition'] },
    { label: 'Durability', verdict: 'bad', cells: ['Whatever your persistence config gives you', 'Replicated to disk on multiple brokers'] },
    { label: 'Retention', cells: ['Trim by length or time; it is all in memory', 'Disk-bound; days or forever'] },
    { label: 'Scale', cells: ['One key on one node', 'Partitioned across a cluster'] },
  ]}
/>

The per-message acknowledgement is a genuine advantage — it is the thing Kafka does not give you, and
the reason a Redis Stream can be a better work queue. The disadvantage is that the data lives in
memory on one node, with whatever durability your persistence settings actually provide — which the
next lesson is about.

**Use Streams for a work queue that needs acknowledgement and where losing the tail on a hard crash
is tolerable.** Use Kafka when the log itself must survive.

## Naming keys

Redis has no schema, so key naming is the schema.

```text
shopflow:order:6b1c9f22            # service : type : id
shopflow:cart:user:88af:items      # nested, colon-delimited
shopflow:ratelimit:ip:10.2.0.4     # scoped by concern
```

Two habits worth adopting from the start: a **prefix per service**, so a shared Redis can be reasoned
about and scanned selectively, and **no unbounded key spaces without a TTL** — a key pattern
generated from user input with no expiry is an unbounded memory leak, and Redis responds to running
out of memory by evicting or refusing writes.
