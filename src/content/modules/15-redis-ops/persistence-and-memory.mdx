Redis holds its dataset in memory. Two questions follow immediately, and the defaults answer both in
ways people find surprising: **what survives a restart**, and **what happens when memory runs out.**

## Persistence

Two mechanisms, which can be combined.

```conf title="redis.conf — durable-ish, which is what most people actually want"
# RDB: snapshot after 1 change in 900s, 100 in 300s, 10000 in 60s.
save 900 1
save 300 100
save 60 10000
dbfilename dump.rdb

# AOF: the tail RDB cannot cover.
appendonly yes
appendfsync everysec        # see below — this is the important line
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# Do not keep serving happily while snapshots are silently failing.
stop-writes-on-bgsave-error yes
```

<Callout type="pitfall" title="appendfsync everysec means you can lose a second of writes">
The default is `everysec`: Redis fsyncs the append-only file once a second. A power loss or an OOM
kill therefore discards up to a second of acknowledged writes — writes your application was told had
succeeded.

`appendfsync always` fsyncs every write and is genuinely durable, at a very large throughput cost —
often an order of magnitude. Almost nobody runs it.

The honest position: **Redis is not a system of record.** If losing a second of writes is
unacceptable, that data belongs in a database, and Redis holds a derived copy. Choosing Redis and
then trying to configure your way to Postgres durability is fighting the tool.
</Callout>

## What a fork costs

Both RDB snapshots and AOF rewrites work by forking. The child writes the dataset to disk while the
parent keeps serving.

<Mermaid

This is the most common cause of an unexplained Redis OOM kill: the instance sits comfortably at
8 GB, a background save starts, copy-on-write duplicates a few gigabytes of pages, and the container
limit is 10 GB.

```conf
# Lets the kernel overcommit so fork() succeeds rather than failing outright.
# Set the sysctl too: vm.overcommit_memory = 1
```

The real mitigation is capacity: **plan for `maxmemory` plus the write rate during a save**, and
disable transparent huge pages (`never`), which makes copy-on-write duplicate 2 MB pages instead of
4 KB ones.

## maxmemory and eviction

Without `maxmemory`, Redis grows until the kernel kills it. With it, Redis applies a policy when the
limit is reached.

  columns={['Evicts', 'Use for']}
  rows={[

      verdict: 'mixed',
      cells: ['Nothing — writes fail with OOM', 'Anything where losing a key silently is worse than an error'],
    },
    {

      verdict: 'good',
      cells: ['Least recently used, any key', 'A pure cache'],
    },
    {
      label: 'allkeys-lfu',
      verdict: 'good',
      cells: ['Least frequently used, any key', 'A cache with a stable hot set — usually better than LRU'],
    },
    {
      label: 'volatile-lru / -lfu / -ttl',
      verdict: 'mixed',
      cells: ['Only keys that have a TTL', 'Mixed workloads — but see the warning'],
    },
  ]}
/>

```conf
maxmemory 6gb                    # leave room for COW and overhead
maxmemory-policy allkeys-lfu
```

<Callout type="pitfall" title="volatile-* fails when nothing has a TTL">
The `volatile-*` policies only consider keys with an expiry set. If memory fills and **no** key has a
TTL, there is nothing eligible — so Redis behaves as `noeviction` and starts rejecting writes.

This is a nasty failure because it appears only under memory pressure, on an instance that looked
correctly configured. If you use a `volatile-*` policy, something must guarantee that TTLs are
actually being set.
</Callout>

The default is `noeviction`, and that default is deliberate: silently discarding data is a terrible
default for a data store. For a cache it is the wrong default, so set the policy explicitly rather
than inheriting it.

## Memory that is used but is not your data

`INFO memory` reports several numbers and people read the wrong one.

<Terminal>
{`$ redis-cli INFO memory
used_memory_human:6.21G           # what the dataset costs, as Redis sees it
used_memory_rss_human:8.94G       # what the OS has actually given the process
mem_fragmentation_ratio:1.44      # rss / used — 1.44 means 44% overhead
mem_allocator:jemalloc-5.3.0`}
</Terminal>

**`used_memory_rss` is what the container limit applies to**, and it is the one that gets you
OOM-killed. A fragmentation ratio above roughly 1.5 means a lot of memory is held by the allocator
but not holding data — typically after a workload that deleted many keys of varying sizes.

```conf
# Let jemalloc return freed pages gradually, without blocking.
activedefrag yes
active-defrag-ignore-bytes 100mb
active-defrag-threshold-lower 10
active-defrag-cycle-min 5
active-defrag-cycle-max 25
```

A ratio **below 1** is different and worth recognising: it means part of the dataset has been swapped
to disk. On a database that keeps everything in memory, swapping turns microsecond operations into
millisecond ones and looks exactly like Redis having become inexplicably slow. Disable swap on Redis
hosts.

## Where the memory actually goes

Small collections use compact encodings; past a threshold they switch to a general one, and memory
per element jumps.

```conf
hash-max-listpack-entries 128
hash-max-listpack-value 64
zset-max-listpack-entries 128
set-max-intset-entries 512
```

A hash with 128 fields may use a fraction of the memory of one with 129, because it crossed the
threshold. That produces a genuinely confusing capacity surprise, and it is also an optimisation: a
few thousand small hashes cost far less than one large one holding the same data.

```bash
# What a specific key actually costs, including overhead.
redis-cli MEMORY USAGE shopflow:cart:88af

# Find the biggest keys without blocking the server — SCAN-based.
redis-cli --bigkeys
redis-cli --memkeys
```

<Callout type="prod">
Set `maxmemory` to roughly 60–70% of the container limit, not 90%. The remaining headroom is for
copy-on-write during saves, allocator fragmentation, client output buffers and replication buffers —
none of which count towards `used_memory` and all of which count towards the container limit.

An instance configured with `maxmemory` at 95% of its limit will be OOM-killed during a background
save, and the eviction policy will never get a chance to help.
</Callout>
