## The problem that created Spring

In 2002, building a Java server application meant writing to a container. Your business logic
extended framework classes, implemented framework interfaces, and could not be instantiated
outside an application server. Testing a pricing rule meant starting a J2EE container.

Rod Johnson's argument was simple: **that dependency points the wrong way**. Your code should not
know about the framework. The framework should know about your code.

That inversion — the framework calling you rather than you calling the framework — is the whole
idea. Everything else in Spring is a consequence of it.

<Callout type="note" title="One sentence to keep">
Spring's job is to build your objects, wire them together, and wrap them in behaviour you did not
write by hand — transactions, security, caching, retries — without your classes knowing any of it
is happening.
</Callout>

## Framework, Boot, Cloud: three different things

These three names get used interchangeably in job adverts, and they are not the same layer.

The dependency runs one way: Cloud needs Boot, Boot needs the Framework. You can use the Framework
without Boot (few people do now), and Boot without Cloud (most people should).

## What inversion of control actually looks like

Here is the same requirement written both ways. The difference is not style — it changes what you
can test, and what you can swap.

<Compare>
  <Bad title="The object builds its own world">

`OrderService` decides which repository and which gateway it uses. To test it you need a real
database and a real payment provider.

```java
public class OrderService {
    private final OrderRepository repository =
            new JdbcOrderRepository(DataSourceFactory.get());
    private final PaymentGateway payments =
            new StripeGateway(System.getenv("STRIPE_KEY"));

    public Order place(Cart cart) { /* ... */ }
}
```

  </Bad>
  <Good title="The object is handed its world">

The dependencies arrive through the constructor. In production Spring supplies the real ones; in a
test you supply fakes. The class never changes.

```java
@Service
public class OrderService {
    private final OrderRepository repository;
    private final PaymentGateway payments;

    public OrderService(OrderRepository repository, PaymentGateway payments) {
        this.repository = repository;
        this.payments = payments;
    }

    public Order place(Cart cart) { /* ... */ }
}
```

  </Good>
</Compare>

Nothing in the second version imports Spring except the `@Service` annotation, and even that is
only a marker telling the container "this one is yours to build". The class is a plain Java object
with a constructor. That is the point.

## What Boot changed

The Framework solved coupling. It did not solve **configuration**. A 2012 Spring application
carried hundreds of lines of XML — or later, Java config — describing a `DataSource`, an
`EntityManagerFactory`, a `TransactionManager`, a `DispatcherServlet`, a view resolver, and so on.
Every project rewrote the same file.

Boot's insight was that this configuration is almost entirely predictable from what is on the
classpath. If `spring-boot-starter-data-jpa` and a Postgres driver are present, and a JDBC URL is
set, then you want a `DataSource`, a `JpaTransactionManager`, and an `EntityManagerFactory`
configured in the obvious way.

```java title="What Boot registers for you, conditionally"
@AutoConfiguration
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })
@ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {
    // …registers a DataSource only if you have not defined one yourself.
}
```

Read `@ConditionalOnMissingBean` carefully, because it is the contract that makes Boot tolerable:
**every default steps aside the moment you declare your own bean.** Boot is not magic you have to
fight. It is a large pile of defaults with an explicit override rule.

<Callout type="prod">
Teams get into trouble when they treat auto-configuration as unknowable. It is ordinary code in an
ordinary jar, and `--debug` prints a report of every condition that matched and every one that did
not. Module 02 walks through reading that report.
</Callout>

<Callout type="tip" title="A useful reading habit">
When you meet an unfamiliar Spring annotation, look at its source. Almost all of them are
meta-annotations — `@RestController` is just `@Controller` plus `@ResponseBody` — and reading the
composition tells you more than any blog post.
</Callout>
