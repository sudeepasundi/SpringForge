A JWT is a signed JSON document. That is genuinely all it is — and both halves of that sentence carry
consequences people routinely miss: *signed* means you can trust it if you check the signature
properly, and *JSON document* means anyone can read it.

## What a token actually contains

```text title="A JWT is three base64url segments, dot-separated"
eyJhbGciOiJSUzI1NiIsImtpZCI6ImE0ZjIifQ            ← header
.eyJpc3MiOiJodHRwczovL2F1dGguYWNtZS5jb20iLC…     ← payload (claims)
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c      ← signature
```

```json title="Decoded header and payload"
{ "alg": "RS256", "kid": "a4f2" }

{
  "iss": "https://auth.acme.com",        // who issued it
  "sub": "6b1c9f22-...",                 // who it is about
  "aud": "taskly-api",                   // who it is for
  "exp": 1773148800,                     // when it stops being valid
  "iat": 1773145200,
  "scope": "tasks.read tasks.write",
  "tenant_id": "acme"
}
```

<Callout type="pitfall" title="Base64 is not encryption">
Anyone holding the token can read every claim — paste it into any decoder. The signature prevents
*modification*, not *reading*. Never put anything in a JWT you would not put in a URL: no PII beyond
an identifier, no internal hostnames, no secrets.
</Callout>

## Validation is five checks, not one

Checking the signature is necessary and nowhere near sufficient. A valid signature only proves *some*
issuer signed *something*.

The **audience** check is the one teams skip. Without it, a token your identity provider issued for
*any* client is accepted by your API — so a low-privilege third-party integration's token works
against your admin service. The signature is perfectly valid; it was simply never meant for you.

## Configuring a resource server

The good news: Spring Security does all five checks, and the configuration is short.

```yaml title="application.yml"
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          # Spring discovers the JWKS endpoint from /.well-known/openid-configuration
          issuer-uri: https://auth.acme.com/realms/taskly
          audiences: taskly-api          # do not omit this
```

```java title="support/SecurityConfig.java" {10-12,17}
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
            .securityMatcher("/api/**")
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers(HttpMethod.GET, "/api/tasks/**").hasAuthority("SCOPE_tasks.read")
                    .requestMatchers("/api/tasks/**").hasAuthority("SCOPE_tasks.write")
                    .anyRequest().authenticated())
            .oauth2ResourceServer(oauth -> oauth
                    .jwt(jwt -> jwt.jwtAuthenticationConverter(authoritiesConverter())))
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .csrf(CsrfConfigurer::disable)     // safe: no cookies, so no CSRF surface
            .build();
}

@Bean
JwtAuthenticationConverter authoritiesConverter() {
    JwtGrantedAuthoritiesConverter scopes = new JwtGrantedAuthoritiesConverter();
    scopes.setAuthorityPrefix("SCOPE_");       // the default; stated for clarity
    scopes.setAuthoritiesClaimName("scope");

    JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(jwt -> {
        Collection<GrantedAuthority> authorities = new ArrayList<>(scopes.convert(jwt));
        // Merge a provider-specific claim — Keycloak puts roles under realm_access.
        Map<String, Object> realm = jwt.getClaim("realm_access");
        if (realm != null && realm.get("roles") instanceof Collection<?> roles) {
            roles.forEach(r -> authorities.add(new SimpleGrantedAuthority("ROLE_" + r)));
        }
        return authorities;
    });
    return converter;
}
```

<Callout type="tip" title="Never parse a JWT yourself">
Hand-rolled JWT parsing has produced a long list of CVEs: accepting `alg: none`, confusing HMAC with
RSA so the public key becomes the HMAC secret, failing to check `exp`, comparing signatures with
`String.equals` and leaking timing. Spring Security's implementation handles all of them. There is
no situation in which writing your own is the right call.
</Callout>

## Key rotation happens without you

The `kid` in the header names which key signed the token. Spring fetches the issuer's JWKS, caches
it, and refetches when it sees an unknown `kid`. That is what makes key rotation invisible: the
issuer publishes the new key alongside the old, starts signing with the new one, and your service
picks it up on the first token it cannot match.

Two operational consequences:

- **Your service must reach the issuer's JWKS endpoint.** In a locked-down network this is a
  firewall rule people forget, and the symptom is every token failing with no obvious cause.
- **Do not cache the JWKS forever.** The defaults are sensible; overriding them with a very long TTL
  means a revoked key stays trusted.

## Revocation, honestly

**You cannot revoke a JWT.** It is valid until it expires, because validation is a local computation
with no callback to the issuer. Any claim otherwise is a workaround with a cost.

**Short expiry plus revocable refresh tokens** is the standard answer, and it is the right one. If
you genuinely need instant revocation on every request, you need sessions, and you should use them.

<Callout type="prod">
Set `spring.security.oauth2.resourceserver.jwt.clock-skew` if your tokens are short-lived. Servers
drift by a few seconds, and with a five-minute expiry a two-second skew rejects tokens that were
issued moments ago. Thirty seconds is a reasonable allowance; more than a minute starts undermining
the point of a short expiry.
</Callout>

## Propagating identity between services

When service A calls service B on a user's behalf, B still needs to know who the user is.

<Compare>
  <Bad title="A trusted header">

Any service that can reach B can claim to be any user. This is only safe if the network is perfectly
segmented and the gateway is the sole ingress — an assumption that is true right up until it is not.

```java
restClient.get()
        .uri("/api/accounts/{id}", accountId)
        .header("X-User-Id", currentUserId())     // unverifiable by the receiver
        .retrieve();
```

  </Bad>
  <Good title="Forward the token">

B validates the token exactly as it validates a token from the browser: signature, issuer, audience,
expiry. There is nothing to trust, because everything is verified.

```java
@Bean
RestClient accountsClient(RestClient.Builder builder) {
    return builder
            .baseUrl("http://accounts")
            .requestInterceptor((request, body, execution) -> {
                Authentication auth = SecurityContextHolder.getContext().getAuthentication();
                if (auth instanceof JwtAuthenticationToken jwt) {
                    request.getHeaders().setBearerAuth(jwt.getToken().getTokenValue());
                }
                return execution.execute(request, body);
            })
            .build();
}
```

  </Good>
</Compare>

Two caveats on forwarding. The token's `aud` must include the downstream service, or B rejects it —
which usually means an audience list, or the token exchange flow. And forwarding a *user's* token
gives B the user's full privileges; for a background job with no user, use the client credentials
grant and give the service its own identity.
