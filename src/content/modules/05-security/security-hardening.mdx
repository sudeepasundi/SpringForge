The previous four lessons covered who you are and what you may do. This one covers everything else —
the settings and habits that decide whether a mistake elsewhere becomes an incident.

## CSRF: when you need it and when you do not

Cross-site request forgery works because **browsers attach cookies automatically**. A malicious page
can make your browser POST to your bank, and the session cookie goes along.

That mechanism is the whole story, and it tells you exactly when the protection is needed:

```java
// Stateless API with bearer tokens: nothing is sent automatically, so there is
// nothing to forge. Disabling CSRF here is correct, not a shortcut.
.csrf(CsrfConfigurer::disable)

// Cookie-authenticated app with a JavaScript front end: the token goes in a
// readable cookie so the SPA can echo it back in a header.
.csrf(csrf -> csrf
        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
        .csrfTokenRequestHandler(new SpaCsrfTokenRequestHandler()))
```

<Callout type="pitfall" title="Disabling CSRF because POSTs return 403">
This is the most common security regression in Spring applications. The 403 is CSRF protection
working. If your credential is a cookie, disabling it opens a real hole — send the token instead.

The tell is whether authentication survives a request your JavaScript did not make. If a plain HTML
form on another site would be authenticated, you need CSRF protection.
</Callout>

## CORS: a browser rule, not a security boundary

CORS decides whether a *browser* lets page JavaScript read your response. It stops nothing else —
curl, a server, a mobile app all ignore it entirely. It is not access control.

```java title="support/CorsConfig.java" {7-9,14}
@Bean
CorsConfigurationSource corsConfigurationSource(AppProperties properties) {
    CorsConfiguration config = new CorsConfiguration();

    // Never "*" with credentials — the browser rejects that combination, and
    // "*" without credentials is still an invitation to probe your API.
    config.setAllowedOrigins(properties.allowedOrigins());   // from configuration
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type", "Idempotency-Key"));
    config.setAllowCredentials(true);
    config.setMaxAge(Duration.ofHours(1));                   // cache preflights

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", config);
    return source;
}
```

`setAllowedOriginPatterns("*")` with credentials is the dangerous variant — it reflects whatever
origin asked, which means every origin is allowed. List your origins, and put them in configuration
so each environment has its own.

## Security headers

Spring Security writes several by default. Two are worth configuring explicitly.

```java title="support/SecurityConfig.java" {5-9,12-14}
.headers(headers -> headers
        .frameOptions(FrameOptionsConfig::deny)              // clickjacking
        .contentTypeOptions(withDefaults())                  // nosniff
        .httpStrictTransportSecurity(hsts -> hsts
                .includeSubDomains(true)
                .maxAgeInSeconds(31_536_000))                // one year
        .referrerPolicy(r -> r.policy(STRICT_ORIGIN_WHEN_CROSS_ORIGIN))
        .contentSecurityPolicy(csp -> csp.policyDirectives(
                "default-src 'self'; "
              + "script-src 'self'; "                        // no 'unsafe-inline'
              + "object-src 'none'; "
              + "frame-ancestors 'none'; "
              + "base-uri 'self'")))
```

<Callout type="prod">
Roll out CSP in report-only mode first. `Content-Security-Policy-Report-Only` sends violation reports
without blocking anything, so you find the inline script you forgot before it breaks the checkout
page. Run it for a week, fix what reports, then enforce.
</Callout>

## Secrets

Three rules, in order of how much they cost when broken.

<Steps>
  <Step title="Never commit one">

A secret pushed to a repository is compromised — including after a force-push, because it is in
clones, forks, CI caches and mirrors. Rotate it; do not try to erase it.

Add a scanner to CI so this is caught at the pull request:

```yaml title=".github/workflows/security.yml"
- name: Scan for secrets
  uses: gitleaks/gitleaks-action@v2
```

  </Step>
  <Step title="Inject from the environment, with no default">

A placeholder with no fallback fails startup rather than connecting with an empty credential.

```yaml
spring:
  datasource:
    password: ${DB_PASSWORD}       # unresolvable → startup failure. Good.
```

  </Step>
  <Step title="Make rotation routine">

A secret you cannot rotate without downtime will not be rotated, and a breach then means an outage
on top of an incident. Rotation should be a routine operation you have performed recently enough to
trust — which means the application must tolerate two valid credentials during the changeover.

  </Step>
</Steps>

<Callout type="pitfall" title="Where secrets leak without anyone committing one">
- **`/actuator/heapdump`** — every secret in memory, in plain text, over HTTP.
- **Debug logging of request bodies** — `spring.mvc.log-request-details` logs credentials on the
  login endpoint.
- **Exception messages returned to clients** — a JDBC exception can carry the connection URL.
- **Docker image layers** — a secret in an intermediate layer stays in the image even if a later
  layer deletes the file.
- **CI logs** — an unmasked variable in a build step is readable by anyone with repository access.
</Callout>

## Dependency vulnerabilities

The most likely source of a serious vulnerability in your service is code you did not write. Log4Shell
was not a bug anyone's team introduced.

```xml title="pom.xml — fail the build on a known CVE"
<plugin>
  <groupId>org.owasp</groupId>
  <artifactId>dependency-check-maven</artifactId>
  <version>11.1.0</version>
  <configuration>
    <failBuildOnCVSS>7</failBuildOnCVSS>     <!-- high and critical -->
    <nvdApiKey>${env.NVD_API_KEY}</nvdApiKey>
  </configuration>
</plugin>
```

Three habits matter more than the specific tool:

- **Upgrade Spring Boot promptly.** A patch release moves hundreds of transitive versions in a
  combination that has been tested. Staying current is the cheapest security work available.
- **Fail the build on high and critical**, not on everything. A gate that fires constantly gets
  ignored, and then it protects nothing.
- **Have a triage path.** Not every CVE is exploitable in your usage. Suppress with a written reason
  and an expiry date, not silently.

## Input handling

Two rules that cover most injection risks.

**Never build a query by concatenation.** JPQL and native queries both take parameters:

```java
// Injectable. There is no safe way to do this.
@Query(value = "select * from tasks where title like '%" + title + "%'", nativeQuery = true)

// Bound as a parameter by the driver.
@Query("select t from Task t where lower(t.title) like lower(concat('%', :title, '%'))")
List<Task> search(@Param("title") String title);
```

**Escape on output, not on input.** Storing HTML-escaped text corrupts the data — a name is
`O'Brien`, not `O&#39;Brien` — and it does not help when the same value is later rendered into a
different context. Store what the user typed and escape at the boundary that renders it, which
knows whether it is producing HTML, a URL, or SQL.
