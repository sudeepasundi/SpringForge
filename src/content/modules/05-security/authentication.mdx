Authentication answers one question — *who is making this request* — and Spring Security answers it
with four collaborating pieces. Knowing which piece does what turns "authentication is failing" into
a specific, answerable question.

The distinction that matters: **`UserDetailsService` loads, it does not verify.** It has no access to
the submitted password and must not check anything. Its only job is to return the stored user or
throw `UsernameNotFoundException`. `DaoAuthenticationProvider` does the comparison.

## Password storage

This is the part where a mistake is unrecoverable, so the rules are short and absolute.

```java title="support/SecurityConfig.java"
@Bean
PasswordEncoder passwordEncoder() {
    // Produces {bcrypt}$2a$10$… — the prefix records which algorithm made the hash,
    // so you can change the default later without invalidating existing passwords.
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}
```

<Callout type="prod">
The delegating encoder is what makes an algorithm upgrade possible without a password reset. Because
each hash is prefixed with the algorithm that produced it, old hashes keep verifying while new ones
use the new default — and you can re-encode a user's password during a successful login, so the
migration completes as people sign in.
</Callout>

## A UserDetailsService

```java title="user/DatabaseUserDetailsService.java" {14-16,20-24}
@Service
public class DatabaseUserDetailsService implements UserDetailsService {

    private final UserRepository repository;

    public DatabaseUserDetailsService(UserRepository repository) {
        this.repository = repository;
    }

    @Override
    @Transactional(readOnly = true)
    public UserDetails loadUserByUsername(String username) {
        AppUser user = repository.findByUsernameWithRoles(username)
                // The message is deliberately identical for a missing user and a
                // wrong password — see the note below.
                .orElseThrow(() -> new UsernameNotFoundException("Bad credentials"));

        return User.withUsername(user.getUsername())
                .password(user.getPasswordHash())
                .authorities(user.getRoles().stream()
                        .map(role -> new SimpleGrantedAuthority("ROLE_" + role.name()))
                        .toList())
                .accountLocked(user.isLocked())
                .disabled(!user.isEnabled())
                .build();
    }
}
```

<Callout type="pitfall" title="Do not tell an attacker which half was wrong">
"No account with that email" and "Incorrect password" together let anyone enumerate your user base.
Return the same message for both.

Timing leaks the same information more subtly: a missing user returns immediately, while a real user
costs ~100 ms of bcrypt. `DaoAuthenticationProvider` mitigates this by hashing a dummy password when
the user is not found — do not disable that behaviour, and do not reimplement it carelessly in a
custom provider.
</Callout>

## Login attempt throttling

Nothing in Spring Security limits attempts by default. Without it, a valid username plus a password
list is only a matter of time.

```java title="user/LoginAttemptListener.java" {8,15}
@Component
public class LoginAttemptListener {

    private static final int MAX_ATTEMPTS = 5;
    private static final Duration WINDOW = Duration.ofMinutes(15);

    private final Cache<String, Integer> attempts = Caffeine.newBuilder()
            .expireAfterWrite(WINDOW)
            .maximumSize(100_000)          // bounded: this is attacker-controlled input
            .build();

    @EventListener
    public void onFailure(AuthenticationFailureBadCredentialsException event) {
        String key = key(event);
        attempts.asMap().merge(key, 1, Integer::sum);
    }

    @EventListener
    public void onSuccess(AuthenticationSuccessEvent event) {
        attempts.invalidate(key(event));
    }

    public boolean isBlocked(String username) {
        return attempts.getIfPresent(username) != null
                && attempts.getIfPresent(username) >= MAX_ATTEMPTS;
    }
}
```

Two design points worth copying. **Bound the cache** — the key is derived from user input, so an
unbounded map is a memory-exhaustion vector. And **key on the username, not only the IP**: a
distributed attack rotates IPs, and rate-limiting by IP alone punishes everyone behind a corporate
NAT. Track both.

<Callout type="prod">
An in-memory counter is per-instance. With four replicas an attacker gets four times the attempts,
and a restart clears the count. Move the counter to Redis for anything with real exposure — this is
one of the few places where the distributed version is genuinely required rather than merely tidier.
</Callout>

## A custom AuthenticationProvider

When the credential is not a password — an API key, a signed webhook, a hardware token — implement a
provider rather than bending the password flow.

```java title="support/ApiKeyAuthenticationProvider.java" {14,19-22}
@Component
public class ApiKeyAuthenticationProvider implements AuthenticationProvider {

    private final ApiKeyRepository repository;
    private final PasswordEncoder encoder;

    @Override
    public Authentication authenticate(Authentication authentication) {
        String presented = (String) authentication.getCredentials();
        String keyId = (String) authentication.getPrincipal();

        ApiKey key = repository.findActiveById(keyId)
                .orElseThrow(() -> new BadCredentialsException("Invalid API key"));

        // Store API keys hashed, exactly like passwords. A leaked database
        // should not hand over working credentials.
        if (!encoder.matches(presented, key.getHash())) {
            throw new BadCredentialsException("Invalid API key");
        }
        if (key.isExpired()) {
            throw new CredentialsExpiredException("API key expired");
        }

        return new ApiKeyAuthenticationToken(key.getClientId(), key.getAuthorities());
    }

    @Override
    public boolean supports(Class<?> authentication) {
        return ApiKeyAuthenticationToken.class.isAssignableFrom(authentication);
    }
}
```

`supports()` is what lets several providers coexist: `ProviderManager` asks each in turn and uses the
first that claims the token type.

<Callout type="tip" title="Hash API keys, and show them once">
Treat an API key exactly like a password: generate it with a `SecureRandom`, show the plaintext to
the user once at creation, store only the hash. "We can email you your API key" means you stored it
in plaintext, and that is a breach waiting for a database dump.
</Callout>

## Sessions or tokens

The trade-off is revocation against statelessness, and it is not close for browser applications: a
session cookie with `HttpOnly`, `Secure` and `SameSite` is simpler, revocable, and not readable by
JavaScript. Storing a JWT in `localStorage` — the usual reason people choose it — makes any XSS a
full account takeover.

Choose JWTs when statelessness genuinely buys you something, keep their lifetime short, and pair
them with refresh tokens you *can* revoke. The next lesson covers that properly.
