Spring Security has a reputation for being impenetrable. It is not — it is a list of servlet filters
that run in a fixed order, and every behaviour you find confusing is one of them doing its job.

Once you can name the filters, debugging security stops being guesswork.

## Where it plugs in

Spring Security registers exactly one filter with the servlet container: `springSecurityFilterChain`,
wrapped in a `DelegatingFilterProxy`. Everything else happens inside it.

**Only the first matching chain runs.** This is the single most important structural fact, and it is
the cause of most "my rule is being ignored" reports: an earlier chain with a broader matcher
swallowed the request, and the chain containing your rule was never consulted.

<Callout type="tip" title="Print the actual chain">
Stop guessing which filters are active:

```yaml
logging:
  level:
    org.springframework.security.web.FilterChainProxy: DEBUG
```

At startup Spring Security logs every chain with its matcher and its filters, in order. At request
time it logs which chain matched and which filter rejected. That output answers most security
questions in under a minute.
</Callout>

## 401 or 403

`ExceptionTranslationFilter` makes this decision, and the rule is worth memorising because the two
mean very different things to a client.

<DecisionTable
  columns={['Means', 'Thrown when', 'Client should']}
  rows={[
    {
      label: '401 Unauthorized',
      verdict: 'mixed',
      cells: ['We do not know who you are', 'AuthenticationException — no credentials, or invalid ones', 'Authenticate and retry'],
    },
    {
      label: '403 Forbidden',
      verdict: 'bad',
      cells: ['We know who you are, and you may not', 'AccessDeniedException from an authenticated user', 'Not retry — nothing will change'],
    },
  ]}
/>

The subtlety: an **anonymous** user who hits a protected endpoint throws `AccessDeniedException`, not
an authentication exception — but `ExceptionTranslationFilter` checks whether the principal is
anonymous and converts it to a 401. That is why an unauthenticated request gets 401 rather than 403,
even though the exception type suggests otherwise.

## Configuring chains

Modern Spring Security is configured with `SecurityFilterChain` beans. Multiple chains are ordered,
and the first matcher to accept wins.

```java title="support/SecurityConfig.java" {6,8,23,25}
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    @Order(1)
    SecurityFilterChain actuator(HttpSecurity http) throws Exception {
        return http
                .securityMatcher(EndpointRequest.toAnyEndpoint())   // scope this chain
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers(EndpointRequest.to(HealthEndpoint.class)).permitAll()
                        .anyRequest().hasRole("ACTUATOR"))
                .httpBasic(withDefaults())
                .csrf(CsrfConfigurer::disable)                      // no browser sessions here
                .build();
    }

    @Bean
    @Order(2)
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http
                .securityMatcher("/api/**")
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers(HttpMethod.GET, "/api/tasks/**").hasAuthority("SCOPE_tasks.read")
                        .requestMatchers("/api/tasks/**").hasAuthority("SCOPE_tasks.write")
                        .anyRequest().authenticated())              // ← always end with this
                .oauth2ResourceServer(oauth -> oauth.jwt(withDefaults()))
                .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
                .csrf(CsrfConfigurer::disable)                      // stateless bearer tokens
                .build();
    }
}
```

Two rules that prevent the most common misconfigurations:

**Rules are evaluated top to bottom, first match wins.** A broad rule above a specific one makes the
specific one dead code. Order from most specific to least.

**Always end with `.anyRequest().authenticated()`.** Without it, a path you forgot to list is
unprotected — and the failure is silent. With it, a forgotten path returns 401 and someone tells you.

<Compare>
  <Bad title="Broad rule first, and no catch-all">

The first rule matches everything under `/api/`, so the admin rule below it never runs — any
authenticated user reaches the admin endpoints. And any path outside `/api/` is not mentioned at
all, so it is wide open.

```java
.authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/**").authenticated()
        .requestMatchers("/api/admin/**").hasRole("ADMIN"))   // unreachable
```

  </Bad>
  <Good title="Specific first, catch-all last">

The admin rule is evaluated first, so it applies. The final rule means nothing is reachable by
accident.

```java
.authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/admin/**").hasRole("ADMIN")
        .requestMatchers("/api/**").authenticated()
        .anyRequest().denyAll())
```

  </Good>
</Compare>

<Callout type="pitfall" title="Never use WebSecurityCustomizer to ignore a path you care about">
`web.ignoring().requestMatchers("/api/public/**")` removes the path from the filter chain entirely.
No headers are written, no CORS handling, no CSRF, and — importantly — **no security context**, so
downstream code that reads the authentication sees nothing even when a valid token was sent.

Use `permitAll()` inside the chain instead. It skips authorisation while keeping every other filter,
which is nearly always what you actually meant. Reserve `ignoring()` for genuinely static assets.
</Callout>

## Reading the current user

The `SecurityContext` is held in a `ThreadLocal`, which has one consequence worth knowing before you
need it.

```java
// Anywhere — but only on the request thread.
Authentication auth = SecurityContextHolder.getContext().getAuthentication();

// In a controller, prefer an argument. It is testable and explicit.
@GetMapping("/me")
public UserResponse me(@AuthenticationPrincipal Jwt jwt) {
    return service.byId(UUID.fromString(jwt.getSubject()));
}
```

<Callout type="prod">
Because the context is thread-bound, it does not exist on a thread you spawn — `@Async`, a
`CompletableFuture`, a scheduled job, a message consumer. `SecurityContextHolder.getContext()`
returns an empty context there, so `@PreAuthorize` on a method called from an async thread denies
access, and code reading the principal gets null.

`DelegatingSecurityContextExecutor` propagates it where that is genuinely required. The better
default is to pass the user id as a parameter — which also works in the message consumer where there
was never a request.
</Callout>
