Authentication asked who you are. Authorization asks what you may do — and it is where most real
security bugs live, because the failure is silent. A broken login is obvious to everyone. A missing
tenant check returns 200 and the wrong customer's data.

## Roles and authorities

They are the same mechanism. A role is an authority that starts with `ROLE_`, and Spring Security
adds the prefix for you in some places and not others. That inconsistency is the source of a
persistent bug.

```java
// hasRole("ADMIN") checks for the authority "ROLE_ADMIN" — it adds the prefix.
.requestMatchers("/api/admin/**").hasRole("ADMIN")

// hasAuthority does not add anything. This checks for the literal string.
.requestMatchers("/api/admin/**").hasAuthority("ROLE_ADMIN")

// So this never matches, and the endpoint is unreachable rather than unprotected —
// which is at least the safe direction, but it will waste an afternoon.
.requestMatchers("/api/admin/**").hasAuthority("ADMIN")
```

<Callout type="tip" title="Pick one and never mix">
Use `hasAuthority` everywhere and store authorities with their full name, or use `hasRole`
everywhere and store roles without the prefix. Mixing the two in one codebase guarantees that
someone eventually writes the third line above.
</Callout>

The more useful distinction is conceptual:

**Check permissions, not roles.** `hasAuthority("tasks.delete")` survives the arrival of a new role;
`hasRole("ADMIN") or hasRole("MANAGER") or hasRole("TEAM_LEAD")` needs editing every time the
organisation changes, and someone will miss one of the twelve places it appears. Roles then become a
grouping of permissions, assigned at the user level and expanded into authorities at login.

Use all three. HTTP rules keep obvious things out cheaply, method security expresses domain rules
once for every entry point, and the data layer is what saves you when the other two have a gap.

## Method security

```java title="task/TaskService.java" {1,6,12,18}
@Service
@EnableMethodSecurity        // on a @Configuration class; shown here for context
public class TaskService {

    @PreAuthorize("hasAuthority('tasks.read')")
    public TaskResponse get(UUID id) { … }

    // Rules can reference method arguments by name.
    @PreAuthorize("hasAuthority('tasks.write') and #request.assigneeId() == authentication.name")
    public TaskResponse assignToSelf(AssignRequest request) { … }

    // @PostAuthorize inspects the return value — after the method has run.
    @PostAuthorize("returnObject.ownerId() == authentication.name")
    public TaskResponse getPrivate(UUID id) { … }

    // A named bean keeps complex logic out of a string.
    @PreAuthorize("@taskPermissions.canDelete(#id, authentication)")
    public void delete(UUID id) { … }
}
```

Four things to be careful about.

**`@PostAuthorize` runs after the method.** Any side effect has already happened, and the data has
already been loaded. It is fine on a read, wrong on anything that writes.

**Expressions are strings.** A typo in `hasAuthority('taks.read')` compiles and fails at runtime —
denying access, which is the safe direction, but only discovered by a test. Test your security rules
like any other logic.

**Method security is proxy-based.** A self-invoked call skips the check entirely — the
[self-invocation problem](/learn/spring-core/aop-proxies) again. Here it means an internal call path
silently bypasses authorisation.

**Prefer a bean over a long expression.** `@taskPermissions.canDelete(#id, authentication)` is
testable, debuggable and refactorable. A twelve-term SpEL expression is none of those.

```java title="task/TaskPermissions.java"
@Component("taskPermissions")
public class TaskPermissions {

    private final TaskRepository repository;

    public boolean canDelete(UUID taskId, Authentication authentication) {
        if (authentication.getAuthorities().stream()
                .anyMatch(a -> a.getAuthority().equals("tasks.admin"))) {
            return true;
        }
        return repository.findOwnerId(taskId)
                .map(ownerId -> ownerId.toString().equals(authentication.getName()))
                .orElse(false);
    }
}
```

## Multi-tenancy: enforce it at the data layer

This is the highest-consequence authorisation problem in a SaaS application, and the only reliable
place to solve it is where the query is built.

<Compare>
  <Bad title="Checking the tenant in the service">

Correct — until someone adds a second query path. The batch job, the admin endpoint, the new report,
the repository method somebody called directly. Every one of them is a data leak, and each looks
fine in isolation.

```java
@Transactional(readOnly = true)
public TaskResponse get(UUID id) {
    Task task = repository.findById(id).orElseThrow();
    if (!task.getTenantId().equals(currentTenant())) {
        throw new AccessDeniedException("Wrong tenant");
    }
    return TaskResponse.from(task);
}
```

  </Bad>
  <Good title="A filter the ORM applies to every query">

Hibernate adds `tenant_id = ?` to every query against the entity. A developer who forgets the check
cannot leak data, because there is no query path that skips it.

```java
@Entity
@FilterDef(name = "tenantFilter",
           parameters = @ParamDef(name = "tenantId", type = UUID.class))
@Filter(name = "tenantFilter", condition = "tenant_id = :tenantId")
public class Task { … }

@Component
class TenantFilterActivator {

    @PersistenceContext
    private EntityManager entityManager;

    // Runs once per request, before any repository call.
    public void activate(UUID tenantId) {
        entityManager.unwrap(Session.class)
                .enableFilter("tenantFilter")
                .setParameter("tenantId", tenantId);
    }
}
```

  </Good>
</Compare>

<Callout type="prod">
Hibernate filters do not apply to `find()` by primary key, to native queries, or to JDBC. Cover the
gaps: use row-level security in PostgreSQL if you can, and add an integration test that authenticates
as tenant A, requests a resource belonging to tenant B by id, and asserts a 404. Run it against every
endpoint. That test catches the class of bug that a code review will not.
</Callout>

## Return 404, not 403

For a resource the caller may not see, 403 confirms it exists. Over an id space that is enumerable —
sequential ids, or a leaked list — that is a data disclosure in itself.

```java
@ExceptionHandler(AccessDeniedException.class)
ProblemDetail onAccessDenied(AccessDeniedException ex, HttpServletRequest request) {
    // A tenant-scoped resource the caller cannot see should be indistinguishable
    // from one that does not exist.
    if (request.getRequestURI().startsWith("/api/tasks/")) {
        return ProblemDetail.forStatusAndDetail(NOT_FOUND, "Task not found");
    }
    return ProblemDetail.forStatusAndDetail(FORBIDDEN, "Access denied");
}
```

Use 403 only where the caller is already entitled to know the resource exists — for example, a team
member who can see a task listed but may not delete it.

## Test the rules

Security rules are logic, and untested logic is wrong.

```java title="task/TaskSecurityTest.java" {8,15,22}
@WebMvcTest(TaskController.class)
@Import(SecurityConfig.class)
class TaskSecurityTest {

    @Autowired MockMvc mockMvc;
    @MockitoBean TaskService service;

    @Test
    void anonymous_requests_are_rejected() throws Exception {
        mockMvc.perform(get("/api/tasks"))
                .andExpect(status().isUnauthorized());
    }

    @Test
    @WithMockUser(authorities = "tasks.read")
    void read_authority_cannot_delete() throws Exception {
        mockMvc.perform(delete("/api/tasks/{id}", UUID.randomUUID()).with(csrf()))
                .andExpect(status().isForbidden());
    }

    @Test
    @WithMockUser(authorities = { "tasks.read", "tasks.delete" })
    void delete_authority_can_delete() throws Exception {
        mockMvc.perform(delete("/api/tasks/{id}", UUID.randomUUID()).with(csrf()))
                .andExpect(status().isNoContent());
    }
}
```

The middle test is the valuable one. Anyone can verify that the happy path works; the test that
proves a *narrower* authority is genuinely insufficient is the one that catches an over-broad rule.
