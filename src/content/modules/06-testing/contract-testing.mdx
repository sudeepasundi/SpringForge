Two services. One provides an API, the other consumes it. Both have green test suites. The provider
renames a field, deploys, and the consumer breaks in production.

This happens because each side tested against its own idea of the other. Contract testing removes
the assumption.

## The gap that unit and integration tests leave

The consumer's stub is a *belief* about the provider. Contract testing turns that belief into an
artifact the provider must satisfy.

## How it works

<Steps>
  <Step title="The consumer writes the contract as a test">

The consumer states what it needs — not everything the provider returns, just the fields it actually
uses. Running the test produces a **pact file**: a machine-readable description of the interactions.

  </Step>
  <Step title="The pact is published to a broker">

A shared service that both teams can reach. It knows which consumer versions expect which contracts,
and which provider versions have satisfied them.

  </Step>
  <Step title="The provider verifies against it in its own CI">

The provider replays every published interaction against a real instance of itself and asserts the
responses match. **A change that breaks a consumer fails the provider's build** — before it is
deployed, in the pipeline of the team that made the change.

  </Step>
</Steps>

That last point is the whole value: the feedback arrives in the right pipeline, at the right time,
belonging to the right team.

## The consumer side

```java title="order/CatalogClientContractTest.java" {1-2,11-23,28}
@ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "catalog-service", pactVersion = PactSpecVersion.V4)
class CatalogClientContractTest {

    @Pact(consumer = "order-service")
    V4Pact productExists(PactDslWithProvider builder) {
        return builder
                .given("a product with id 42 exists")        // provider state
                .uponReceiving("a request for product 42")
                    .path("/api/products/42")
                    .method("GET")
                .willRespondWith()
                    .status(200)
                    .body(newJsonBody(body -> {
                        // Match types and shapes, not exact values — the provider
                        // must not have to return literally "Widget" forever.
                        body.uuid("id");
                        body.stringType("name", "Widget");
                        body.numberType("priceMinor", 1299);
                        body.stringMatcher("currency", "[A-Z]{3}", "GBP");
                    }).build())
                .toPact(V4Pact.class);
    }

    @Test
    @PactTestFor(pactMethod = "productExists")
    void reads_the_fields_it_needs(MockServer mockServer) {
        CatalogClient client = new CatalogClient(RestClient.create(mockServer.getUrl()));

        Product product = client.byId(UUID.fromString("..."));

        assertThat(product.priceMinor()).isEqualTo(1299);
        assertThat(product.currency()).isEqualTo("GBP");
    }
}
```

Two decisions in there matter more than the syntax.

**Match on types, not values.** `stringType("name", "Widget")` says "a string, and here is an
example". `stringValue("Widget")` would require the provider to return that exact string forever,
which turns the contract into a straitjacket and makes provider tests brittle for no benefit.

**Only specify what you consume.** If the order service never reads `description`, it does not belong
in the contract. Over-specifying makes the provider unable to change fields nobody depends on — the
exact coupling contract testing exists to prevent.

## The provider side

```java title="catalog/CatalogProviderContractTest.java" {1-3,8,15-19}
@Provider("catalog-service")
@PactBroker(url = "https://pacts.acme.internal")
@SpringBootTest(webEnvironment = RANDOM_PORT)
class CatalogProviderContractTest {

    @LocalServerPort int port;

    @MockitoBean ProductRepository repository;

    @BeforeEach
    void setTarget(PactVerificationContext context) {
        context.setTarget(new HttpTestTarget("localhost", port));
    }

    // Each @State matches a `.given(...)` from a consumer contract.
    @State("a product with id 42 exists")
    void productExists() {
        given(repository.findById(PRODUCT_42))
                .willReturn(Optional.of(new Product(PRODUCT_42, "Widget", 1299, "GBP")));
    }

    @TestTemplate
    @ExtendWith(PactVerificationInvocationContextProvider.class)
    void verify(PactVerificationContext context) {
        context.verifyInteraction();
    }
}
```

`@State` is the mechanism that keeps the two sides independent. The consumer says "given a product
with id 42 exists"; the provider decides how to make that true — a mock, a seeded database, a test
fixture. Neither side needs to know the other's implementation.

## Deploying safely

The broker's `can-i-deploy` check is what turns contract testing from documentation into a gate:

<Terminal>
{`$ pact-broker can-i-deploy \\
    --pacticipant catalog-service \\
    --version "$GIT_SHA" \\
    --to-environment production

Computer says no ¯\\_(ツ)_/¯

CONSUMER      | C.VERSION | PROVIDER        | P.VERSION | SUCCESS?
--------------|-----------|-----------------|-----------|---------
order-service | 4f2a1c    | catalog-service | 9b3e7d    | false

The verification for the pact between order-service and catalog-service failed:
  Expected a Number at $.priceMinor but got an Object`}
</Terminal>

That runs in the provider's pipeline, before the deploy, and names the consumer that would break.
Compare it to the alternative: a 500 in the order service at 2am and thirty minutes of tracing to
find which deploy caused it.

## What contract testing is and is not

<DecisionTable
  columns={['Catches', 'Does not catch']}
  rows={[
    {
      label: 'Contract test',
      verdict: 'good',
      cells: ['Shape and type changes that break a real consumer', 'Whether the business logic is correct'],
    },
    {
      label: 'Integration test',
      verdict: 'good',
      cells: ['That your service works with its own dependencies', 'Whether another team’s service still matches your stub'],
    },
    {
      label: 'End-to-end test',
      verdict: 'mixed',
      cells: ['That a whole flow works, once', 'Anything reliably — they are slow, flaky, and own nobody’s pipeline'],
    },
  ]}
/>

Contract testing is specifically **not** a functional test of the provider. It verifies the shape of
the exchange, not that the price is correct. Both are needed, and conflating them produces contracts
that are impossible to satisfy.

<Callout type="pitfall" title="Contract testing needs both teams">
This is an organisational tool, not a library. If the provider team does not run verification in
their pipeline, you have a consumer test with extra steps and a false sense of safety.

Before adopting it, get agreement on three things: the provider runs verification on every build,
a failed verification blocks their deploy, and there is a broker both teams can reach. Without all
three, WireMock stubs are more honest about what you are actually getting.
</Callout>

## When it is worth it

<DecisionTable
  columns={['Worth it?', 'Why']}
  rows={[
    {
      label: 'Several teams, independent deploys',
      verdict: 'good',
      cells: ['Yes', 'This is exactly the problem it solves'],
    },
    {
      label: 'One team, several services',
      verdict: 'mixed',
      cells: ['Maybe', 'A shared client library or a monorepo compile check may be simpler'],
    },
    {
      label: 'A public API with unknown consumers',
      verdict: 'bad',
      cells: ['No', 'There is nobody to write the consumer side — use OpenAPI diffing instead'],
    },
    {
      label: 'A provider that will not cooperate',
      verdict: 'bad',
      cells: ['No', 'Verification in the provider’s pipeline is the whole mechanism'],
    },
  ]}
/>

For a public API, the equivalent is diffing the generated OpenAPI document in CI — the technique from
[module 03](/learn/web-rest/api-design). It cannot know who depends on what, but it does make every
breaking change visible in review.
