Auto-configuration is the single feature that made Spring Boot worth adopting, and the single thing
people most often describe as magic. It is neither magical nor complicated: it is a list of
configuration classes in a text file, each guarded by conditions, evaluated at startup.

This lesson follows one of them from the jar to the bean it registers. After that you can read any
of the others.

## Where the list comes from

`@EnableAutoConfiguration` — inside `@SpringBootApplication` — reads a plain text file from every
jar on the classpath:

<Terminal>
{`$ unzip -p ~/.m2/repository/.../spring-boot-autoconfigure-3.4.1.jar \\
    META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports | head -6
org.springframework.boot.autoconfigure.admin.SpringApplicationAdminJmxAutoConfiguration
org.springframework.boot.autoconfigure.aop.AopAutoConfiguration
org.springframework.boot.autoconfigure.amqp.RabbitAutoConfiguration
org.springframework.boot.autoconfigure.batch.BatchAutoConfiguration
org.springframework.boot.autoconfigure.cache.CacheAutoConfiguration
org.springframework.boot.autoconfigure.context.ConfigurationPropertiesAutoConfiguration`}
</Terminal>

That is the whole discovery mechanism. One file, one fully-qualified class name per line, about 150
of them in `spring-boot-autoconfigure` alone. Every one is a candidate; almost none survive.

The filter step matters for startup time. Boot ships a precomputed index of the classes each
auto-configuration needs, so a candidate whose classes are absent is eliminated without loading
anything. That is why 150 candidates cost milliseconds rather than seconds.

## One auto-configuration, read in full

`DataSourceAutoConfiguration`, reduced to its structure:

```java title="DataSourceAutoConfiguration.java (abridged)" {1-4,12-14,19-21}
@AutoConfiguration(before = SqlInitializationAutoConfiguration.class)
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })
@ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {

    @Configuration(proxyBeanMethods = false)
    @Conditional(PooledDataSourceCondition.class)
    @ConditionalOnMissingBean({ DataSource.class, XADataSource.class })
    @Import({ DataSourceConfiguration.Hikari.class,
              DataSourceConfiguration.Tomcat.class,
              DataSourceConfiguration.Dbcp2.class,
              DataSourceConfiguration.Generic.class })
    protected static class PooledDataSourceConfiguration {
    }
}
```

Read it as a series of questions, each of which can end the whole thing:

1. **`@ConditionalOnClass({DataSource, EmbeddedDatabaseType})`** — is JDBC even on the classpath? No
   JDBC driver, no further consideration.
2. **`@ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")`** — are you using reactive
   R2DBC instead? Then back off entirely.
3. **`@ConditionalOnMissingBean({DataSource, XADataSource})`** — **have you defined your own
   `DataSource`?** If so, do nothing.
4. **`@Import({Hikari, Tomcat, Dbcp2, Generic})`** — pick a pool implementation, in that order, by
   what is on the classpath. Hikari is first because `spring-boot-starter-jdbc` brings it.

Point 3 is the contract that makes the whole system tolerable, and it is worth stating plainly:
**every Boot default steps aside the moment you declare your own bean of that type.** You never
have to fight auto-configuration. You define a bean and it yields.

<Callout type="note" title="Why proxyBeanMethods = false">
You will see this on nearly every auto-configuration class. It puts the class in lite mode,
skipping CGLIB subclass generation — which saves startup time across 150 candidates and works in
native images. It is safe there because auto-configuration classes take dependencies as method
parameters rather than calling each other's `@Bean` methods, exactly as
[the previous module recommended](/learn/spring-core/configuration-classes).
</Callout>

## The condition evaluation report

This is the tool that ends guessing. Start with `--debug` and Boot prints exactly what matched, what
did not, and why:

<Terminal>
{`$ ./mvnw spring-boot:run -Dspring-boot.run.arguments=--debug

============================
CONDITIONS EVALUATION REPORT
============================

Positive matches:
-----------------
   DataSourceAutoConfiguration matched:
      - @ConditionalOnClass found required classes 'javax.sql.DataSource',
        'org.springframework.jdbc.datasource.embedded.EmbeddedDatabaseType'
      - @ConditionalOnMissingBean did not find any beans of type ConnectionFactory

Negative matches:
-----------------
   RedisAutoConfiguration:
      Did not match:
         - @ConditionalOnClass did not find required class
           'org.springframework.data.redis.core.RedisOperations'

   DataSourceTransactionManagerAutoConfiguration#transactionManager:
      Did not match:
         - @ConditionalOnMissingBean found beans of type
           'PlatformTransactionManager' jpaTransactionManager`}
</Terminal>

Three questions this answers immediately, each of which otherwise costs an hour:

- **"Why is this bean missing?"** Find it under *Negative matches* — the reason is printed.
- **"Why is there a bean I did not ask for?"** Find it under *Positive matches*.
- **"Which of my two candidates won?"** The last block above is the answer: JPA's transaction
  manager was registered first, so the JDBC one backed off. That is not a bug; it is the
  `@ConditionalOnMissingBean` contract working.

<Callout type="prod">
Actuator exposes the same report at `/actuator/conditions` on a running application, which means you
can answer these questions in staging without restarting anything with `--debug`. Keep it behind
authentication.
</Callout>

## Overriding, in order of preference

<Steps>
  <Step title="Set a property">

The overwhelming majority of what you want to change is already a property. Auto-configurations bind
`@ConfigurationProperties`, so `spring.datasource.hikari.maximum-pool-size=20` needs no code.

  </Step>
  <Step title="Define your own bean">

`@ConditionalOnMissingBean` means yours wins, with no exclusion and no ceremony.

```java
@Bean
DataSource dataSource(DataSourceProperties properties) {
    HikariDataSource ds = properties.initializeDataSourceBuilder()
            .type(HikariDataSource.class).build();
    ds.setPoolName("taskly-primary");
    ds.setLeakDetectionThreshold(20_000);   // log a stack trace for leaked connections
    return ds;
}
```

Note that it still takes `DataSourceProperties`, so all the standard configuration still applies —
you are customising, not replacing the whole mechanism.

  </Step>
  <Step title="Exclude the auto-configuration">

The blunt instrument, for when you want none of it.

```java
@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
```

Or `spring.autoconfigure.exclude` in properties, which has the advantage of being profile-specific.
Reach for this last: excluding a class removes everything it registers, including parts you wanted.

  </Step>
</Steps>

## Writing your own

Once the mechanism is clear, writing one is mechanical — and it is how a platform team ships shared
defaults that every service gets for free but any service can override.

```java title="TasklyObservabilityAutoConfiguration.java" {1-3,7}
@AutoConfiguration
@ConditionalOnClass(MeterRegistry.class)
@ConditionalOnProperty(prefix = "taskly.observability", name = "enabled",
                       havingValue = "true", matchIfMissing = true)
public class TasklyObservabilityAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean          // ← always include this, so consumers can override
    MeterFilter commonTags(@Value("${spring.application.name:unknown}") String app) {
        return MeterFilter.commonTags(Tags.of("application", app, "team", "platform"));
    }
}
```

Then register it, in the consuming jar's own imports file:

```text title="src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports"
dev.springforge.starter.TasklyObservabilityAutoConfiguration
```

<Callout type="pitfall" title="Never component-scan your starter's package">
An auto-configuration class must be discovered through the imports file, never through
`@ComponentScan`. Scanning would register it unconditionally, before conditions are ordered — and it
would drag the consumer's scanning into your package tree. This is the most common mistake in
hand-rolled starters.
</Callout>
