A health check that returns 200 whenever the process is alive is worse than no health check. It
tells your orchestrator everything is fine while the database connection pool is exhausted and every
request is failing.

This lesson is about making the operational surface of your application tell the truth.

## Liveness and readiness are different questions

They are routinely conflated, and conflating them causes outages in both directions.

<DecisionTable

The failure mode from getting this wrong is specific and severe: **put a database check in liveness,
and a database blip restarts every instance simultaneously.** They come back, fail the check again,
and restart again. You have converted a recoverable dependency problem into a crash loop across the
whole fleet.

```yaml title="application.yml"
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus     # an explicit allowlist, never "*"
  endpoint:
    health:
      probes:
        enabled: true                               # adds /health/liveness and /health/readiness
      show-details: when-authorized
      group:
        readiness:
          include: db, redis                        # the things we cannot serve without
        liveness:
          include: livenessState                    # deliberately nothing else
```

```yaml title="deployment.yaml"
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  failureThreshold: 3
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  failureThreshold: 2
  periodSeconds: 5
startupProbe:                     # gives a slow JVM start time without loosening liveness
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  failureThreshold: 30
  periodSeconds: 2
```

The startup probe is the piece people miss. Without it you must set `initialDelaySeconds` high
enough for the slowest possible start, which also delays detection of a genuinely stuck process for
the rest of the pod's life.

## A health indicator that means something

`@Component` implementing `HealthIndicator`, named by convention — `ImportQueueHealthIndicator`
becomes the `importQueue` key:

```java title="support/ImportQueueHealthIndicator.java" {12-14,18}
@Component
public class ImportQueueHealthIndicator implements HealthIndicator {

    private final ImportQueue queue;
    private final ImportProperties properties;

    ImportQueueHealthIndicator(ImportQueue queue, ImportProperties properties) {
        this.queue = queue;
        this.properties = properties;
    }

    @Override
    public Health health() {
        int depth = queue.depth();
        // Degraded, not down: we are still serving, but somebody should look.
        Status status = depth > properties.queueDepthLimit() ? Status.OUT_OF_SERVICE : Status.UP;

        return Health.status(status)
                .withDetail("depth", depth)
                .withDetail("limit", properties.queueDepthLimit())
                .withDetail("oldestMessageAge", queue.oldestMessageAge().toString())
                .build();
    }
}
```

<Callout type="pitfall" title="A health check must be cheap and must not hang">
Kubernetes will call this every few seconds, forever. A health check that runs a query, calls a
downstream service, or has no timeout can itself become the reason a pod fails — under load the
health endpoint queues behind real traffic and times out, and the pod is removed exactly when you
needed it. Read cached state; never do real work.
</Callout>

## Exposing endpoints without leaking

The default is deliberately conservative: only `/health` over HTTP. Widening it to `*` exposes
`/actuator/env`, `/actuator/beans`, `/actuator/configprops` and `/actuator/heapdump` — a precise map
of your internals and, in the last case, a file containing every secret in memory.

Three rules:

- **Allowlist explicitly.** Name the endpoints you want. Never `include: "*"`.
- **Move actuator to a separate port**, so it is reachable from your cluster network and not from
  the internet.
- **Require authentication** for anything beyond `/health` and `/info`.

```yaml title="application.yml"
management:
  server:
    port: 8081                    # not the traffic port; do not expose it at the ingress
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus,conditions
```

```java title="support/ActuatorSecurityConfig.java"
@Bean
@Order(1)
SecurityFilterChain actuatorSecurity(HttpSecurity http) throws Exception {
    return http
            .securityMatcher(EndpointRequest.toAnyEndpoint())
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers(EndpointRequest.to(HealthEndpoint.class, InfoEndpoint.class))
                        .permitAll()
                    .anyRequest().hasRole("ACTUATOR"))
            .httpBasic(withDefaults())
            .csrf(CsrfConfigurer::disable)
            .build();
}
```

<Callout type="prod">
`/actuator/heapdump` writes the entire JVM heap to a file. That heap contains database passwords,
API keys, session tokens and user data in plain text. It is not in the default exposure list, and it
should not be in yours. If you need heap dumps in production, take them out of band with `jcmd` on a
host you control.
</Callout>

## Logs a machine can read

The default console format is designed for a human watching a terminal. In production nothing
watches a terminal — logs go to a collector that needs to parse and index them, and a multi-line
stack trace becomes fourteen unrelated "log entries".

Boot 3.4 ships structured logging with no extra dependency:

```yaml title="application-prod.yml"
logging:
  structured:
    format:
      console: ecs          # or gelf, logstash
  level:
    root: INFO
    dev.springforge: INFO
    org.hibernate.SQL: WARN
```

## Correlation, and why you should not build it yourself

The `trace.id` in that line is what lets you pull every log entry for one request across every
service. You get it for free — `spring-boot-starter-actuator` plus Micrometer Tracing populates MDC
automatically, and the structured format includes it.

Resist the urge to hand-roll a correlation filter. The built-in one propagates across HTTP clients,
`@Async` boundaries and Kafka; yours will not, and you will discover the gap during an incident.
Module 10 covers the full picture.

What is worth adding is **business context**, which no framework can guess:

```java title="Structured arguments, not string concatenation" {6-8}
import static net.logstash.logback.argument.StructuredArguments.kv;

log.warn("Import batch rejected: {} rows exceeded the size limit",
        rejected.size(),
        kv("taskId", task.getId()),
        kv("rowCount", rejected.size()),
        kv("reason", "size_limit"));
```

Those become indexed fields rather than text inside a message. `reason: "size_limit"` is
queryable; `"rejected because of the size limit"` is a substring search.

<Callout type="tip" title="Two logging rules worth enforcing in review">
**Never log a secret, a token, or a full request body.** Logs are replicated, retained and widely
readable — they are the least-controlled copy of your data.

**Log at the level that matches the action required.** `ERROR` means a human must do something.
If your dashboard shows a steady rate of errors nobody acts on, they are not errors, and the noise
is training everyone to ignore the ones that matter.
</Callout>
