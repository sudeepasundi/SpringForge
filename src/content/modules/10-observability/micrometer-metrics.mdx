Micrometer is SLF4J for metrics: one API, many backends. You instrument against `MeterRegistry` and
the exporter decides whether that becomes Prometheus, Datadog or CloudWatch.

Most of what you need is already instrumented. The skill is knowing which meter type to use, and how
to read what comes out.

## The meter types

`LongTaskTimer` is the one people miss. A `Timer` records nothing until the operation finishes, so an
import that has been stuck for two hours contributes nothing to your metrics and looks exactly like
an import that never started.

Three of those are worth a dashboard panel each on day one:

- **`hikaricp.connections.pending`** — threads waiting for a database connection. Above zero for any
  sustained period means the pool is the bottleneck, and it is the metric that distinguishes "slow
  queries" from "not enough connections".
- **`kafka.consumer.fetch.manager.records.lag`** — how far behind each consumer is. Steadily rising
  lag is a consumer that cannot keep up, and it is invisible in request metrics.
- **`jvm.gc.pause`** — pause times. A p99 latency spike with no corresponding change in downstream
  latency is usually here.

## Writing a Timer

The `@Timed` annotation is the cheap option; the programmatic API is what you need when the tags
depend on the outcome.

```java title="order/OrderService.java" {6,15-19,26}
@Service
public class OrderService {

    private final MeterRegistry registry;

    @Timed(value = "shopflow.order.place", percentiles = {0.5, 0.95, 0.99})
    public OrderResponse place(PlaceOrderCommand command) { … }

    /**
     * When the tags depend on the result, record it yourself. A sample started
     * before the work and stopped after captures the duration regardless of
     * which path the method took.
     */
    public PaymentResult charge(UUID orderId, Money amount) {
        Timer.Sample sample = Timer.start(registry);
        String outcome = "success";
        try {
            return gateway.charge(orderId, amount);
        } catch (PaymentDeclinedException e) {
            outcome = "declined";
            throw e;
        } catch (Exception e) {
            outcome = "error";
            throw e;
        } finally {
            // Tagging by outcome is what lets you chart declines separately from
            // errors — two very different problems with very different responses.
            sample.stop(Timer.builder("shopflow.payment.charge")
                    .tag("outcome", outcome)
                    .publishPercentileHistogram()
                    .register(registry));
        }
    }
}
```

<Callout type="pitfall" title="Gauges hold a weak reference">
`Gauge` does not store a value — it stores a reference and samples it when scraped. Micrometer holds
that reference **weakly**, so if nothing else keeps the object alive it is garbage collected and the
gauge reports `NaN` forever.

```java
// Broken: the list is unreachable after the constructor returns.
Gauge.builder("queue.depth", new ArrayList<>(), List::size).register(registry);

// Correct: the field keeps it alive.
this.pending = new ConcurrentLinkedQueue<>();
Gauge.builder("queue.depth", pending, Collection::size).register(registry);
```

A gauge that reads `NaN` in production and worked in a test is almost always this.
</Callout>

## Percentiles, and where they are computed

This is the detail that produces wrong dashboards, and it is worth being precise about.

<DecisionTable
  columns={['Computed where', 'Aggregatable across instances?']}
  rows={[
    {
      label: 'percentiles',
      verdict: 'bad',
      cells: ['In the application, per instance', 'No — you cannot average percentiles'],
    },
    {
      label: 'publishPercentileHistogram',
      verdict: 'good',
      cells: ['Buckets exported; percentile computed by Prometheus', 'Yes — histogram_quantile over the fleet'],
    },
  ]}
/>

```java
// Wrong for a fleet: each instance publishes its own p99, and the "average p99"
// across ten instances is a number with no meaning.
Timer.builder("http.server.requests").percentiles(0.99)

// Right: export buckets, let the query engine compute the percentile across all
// instances at once.
Timer.builder("http.server.requests").publishPercentileHistogram()
```

```promql
# The p99 across every instance, correctly computed from bucket counts.
histogram_quantile(0.99,
  sum by (le, uri) (rate(http_server_requests_seconds_bucket[5m])))
```

<Callout type="prod">
**Never alert on a mean latency.** A service where 99% of requests take 10ms and 1% take 10 seconds
has a mean of about 110ms, which looks perfectly healthy while one request in a hundred is
unusable.

Alert on p99, and look at p50 alongside it: p50 normal with p99 spiking is a tail problem — GC, a
lock, one slow shard. Both rising together is a capacity problem.
</Callout>

## Common tags

Set the tags every metric should carry once, at the registry level:

```java title="support/MetricsConfig.java"
@Bean
MeterRegistryCustomizer<MeterRegistry> commonTags(
        @Value("${spring.application.name}") String application,
        @Value("${DEPLOY_ENV:local}") String environment) {

    return registry -> registry.config()
            .commonTags("application", application, "environment", environment)
            // Bound cardinality centrally: a metric that slips through with an
            // unbounded tag is capped rather than unbounded.
            .meterFilter(MeterFilter.maximumAllowableTags(
                    "http.server.requests", "uri", 100, MeterFilter.deny()))
            // Percentile histograms are expensive; enable them where you need them.
            .meterFilter(MeterFilter.acceptNameStartsWith("shopflow"))
            .meterFilter(MeterFilter.denyNameStartsWith("jvm.threads.states"));
}
```

`maximumAllowableTags` is a genuinely useful safety net. It caps a metric at a fixed number of tag
values and denies the rest, so a mistake becomes a capped metric rather than a cardinality explosion
and a very large bill.

## Dashboards worth building

Two dashboards cover most needs, and building more before you need them is wasted effort.

**A service dashboard**, per service, showing RED plus the resource metrics:

```promql
# Rate, by endpoint
sum by (uri) (rate(http_server_requests_seconds_count[5m]))

# Error ratio — the ratio, not the count. A count alert fires on traffic growth.
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count[5m]))

# p99 duration across the fleet
histogram_quantile(0.99,
  sum by (le) (rate(http_server_requests_seconds_bucket[5m])))

# Saturation: threads waiting for a database connection
hikaricp_connections_pending
```

**A business dashboard**, showing the handful of metrics that describe whether the product works:
orders placed, checkout conversion, saga failures, dead-letter depth. This is the one that catches
outages your technical dashboard calls healthy.

<Callout type="tip" title="Exemplars link a metric to a trace">
Prometheus exemplars attach a trace id to a histogram bucket, so clicking a latency spike in Grafana
jumps straight to a trace that produced it.

```yaml
management:
  prometheus:
    metrics:
      export:
        properties:
          # Requires OpenMetrics scraping on the Prometheus side.
          io.prometheus.exemplars.enabled: "true"
```

It removes the manual step of finding a representative slow request, which is otherwise the slowest
part of the workflow from the previous lesson.
</Callout>
