A request served from the edge cache never reaches your service, never opens a database connection and
never allocates a JVM object. A request rejected at the edge does the same. Both are the cheapest
possible outcomes, and both are configuration rather than code.

The judgement is knowing which controls belong out here and which belong in the application.

## The proxy cache

```nginx title="Declared in http, used in a location"
proxy_cache_path /var/cache/nginx
                 levels=1:2
                 keys_zone=api_cache:100m      # ~800,000 keys of metadata
                 max_size=10g                  # on-disk ceiling
                 inactive=60m                  # evicted if unread for this long
                 use_temp_path=off;

server {
    location /api/catalog/ {
        proxy_cache api_cache;
        proxy_cache_key "$scheme$request_method$host$request_uri";

        proxy_cache_valid 200 301 5m;
        proxy_cache_valid 404 30s;             # cache negatives briefly too

        # Serve stale rather than fail — the most valuable line here.
        proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
        proxy_cache_background_update on;
        proxy_cache_lock on;                   # see the stampede note below

        add_header X-Cache-Status $upstream_cache_status;   # HIT / MISS / STALE / UPDATING
        proxy_pass http://catalog_service;
    }
}
```

<Callout type="prod">
`proxy_cache_use_stale ... error timeout http_5xx` turns an upstream outage into slightly old data
instead of a 502. For a catalogue, a product page or any read-mostly endpoint, that is almost always
what users would choose.

Paired with `proxy_cache_background_update on`, the stale response is served immediately while the
refresh happens behind it, so the latency cost of a refresh never lands on a user.
</Callout>

## The cache key is the whole design

The default key ignores everything except scheme, method, host and URI. That is wrong the moment a
response varies by anything else.

<Compare>
  <Bad title="A key that ignores what the response depends on">

Two users with different roles get the same cached response — the first one to ask populates the
cache for everybody. This is **cache poisoning by omission**, and it is a data leak, not a
performance bug.

```nginx
proxy_cache_key "$scheme$request_method$host$request_uri";
# Response body differs by Authorization. The key does not.
```

  </Bad>
  <Good title="Do not cache what varies per user">

Personalised responses do not belong in a shared cache. Cache the parts that are the same for
everyone and let the personalised call through.

```nginx
# Never cache an authenticated response in a shared cache.
proxy_cache_bypass $http_authorization;
proxy_no_cache     $http_authorization;

# Where a response genuinely varies by a small, bounded dimension,
# put that dimension in the key explicitly.
proxy_cache_key "$scheme$request_method$host$request_uri$http_accept_language";
```

  </Good>
</Compare>

<Callout type="pitfall" title="Vary: * and Set-Cookie are silent cache disablers">
Nginx will not cache a response carrying `Set-Cookie`, and it honours `Vary`. A Spring Security
default that issues a session cookie on every response therefore makes your entire cache a no-op —
with no error, no warning, and a hit ratio of zero.

Check `$upstream_cache_status` before believing a cache works. If it is `MISS` on every request for a
resource that should be cacheable, look at the response headers first.

```yaml title="Stateless APIs should not be creating sessions at all"
spring:
  security:
    # SessionCreationPolicy.STATELESS in your SecurityFilterChain
```
</Callout>

## Stampedes

When a popular key expires, every concurrent request for it misses at once and all of them hit the
upstream.

<Mermaid
  caption="proxy_cache_lock lets one request refresh while the rest wait for it, instead of every miss becoming an upstream request."
  alt="Diagram contrasting an unlocked cache where all concurrent misses reach the upstream simultaneously with a locked cache where one request refreshes and the others wait."

```nginx
proxy_cache_lock on;
proxy_cache_lock_timeout 5s;     # after this, the waiters go to the upstream anyway
proxy_cache_lock_age 5s;         # if the refresher is slow, let another try
```

This is the same problem as cache stampede in [module 04](/learn/data/caching-redis), solved one
layer out. `proxy_cache_use_stale updating` is the better half of the answer: rather than making
waiters wait, serve them the stale entry while one request refreshes.

## Rate limiting

Two different mechanisms for two different attacks.

<DecisionTable
  columns={['Limits', 'Protects against']}
  rows={[
    {
      label: 'limit_req',
      verdict: 'good',
      cells: ['Request rate, leaky-bucket', 'Brute force, scraping, accidental client retry loops'],
    },
    {
      label: 'limit_conn',
      verdict: 'good',
      cells: ['Concurrent open connections', 'Slowloris, connection exhaustion, large slow uploads'],
    },
    {
      label: 'limit_rate',
      cells: ['Bytes per second per connection', 'One client saturating your egress'],
    },
  ]}
/>

```nginx
# Zones are declared once in http; 10m holds roughly 160,000 IPs.
limit_req_zone  $binary_remote_addr zone=api_rate:10m rate=20r/s;
limit_req_zone  $binary_remote_addr zone=login_rate:10m rate=5r/m;
limit_conn_zone $binary_remote_addr zone=api_conn:10m;

server {
    location /api/ {
        # burst allows a short spike; nodelay serves it immediately rather
        # than smoothing it out, which is what a browser page load looks like.
        limit_req  zone=api_rate burst=40 nodelay;
        limit_conn api_conn 20;
        limit_req_status 429;               # default is 503, which is wrong
        limit_conn_status 429;
    }

    location /api/auth/login {
        limit_req zone=login_rate burst=3;  # no nodelay — deliberate throttling
    }
}
```

<Callout type="pitfall" title="burst without nodelay queues; nodelay without burst rejects">
`rate=20r/s` alone means the 21st request in a second is rejected — and a normal browser page load
that fires 30 parallel requests trips it immediately.

`burst=40` queues the excess and releases it at the configured rate, which adds latency.
`burst=40 nodelay` serves the burst immediately and still enforces 20r/s on average, which is what
you want for an API.

For a login endpoint, omit `nodelay` on purpose: making a brute-force attempt wait is the point.
</Callout>

<Callout type="prod">
Return **429**, not 503. `limit_req_status 429` is one line and it is the difference between a client
library backing off correctly and one treating your deliberate rejection as a server fault and
retrying harder — the retry-storm mechanism from
[module 08](/learn/resilience/retries-timeouts), triggered by your own error code.

Pair it with `Retry-After` so the client knows how long to wait rather than guessing.
</Callout>

## Where a control belongs

<DecisionTable
  columns={['Edge', 'Application', 'Why']}
  rows={[
    { label: 'Coarse per-IP rate limiting', verdict: 'good', cells: ['Yes', 'No', 'Cheapest possible rejection; no service resources used'] },
    { label: 'Per-tenant or per-plan quotas', verdict: 'mixed', cells: ['No', 'Yes', 'Needs identity and business rules the proxy does not have'] },
    { label: 'Connection limits, slow-client defence', verdict: 'good', cells: ['Yes', 'No', 'It is a connection concern, not a request concern'] },
    { label: 'Caching public, non-personalised reads', verdict: 'good', cells: ['Yes', 'Maybe', 'A hit costs nothing downstream'] },
    { label: 'Caching per-user data', verdict: 'bad', cells: ['No', 'Yes', 'A shared cache keyed wrong is a data leak'] },
    { label: 'Authentication and authorisation', verdict: 'mixed', cells: ['Coarse only', 'Yes', 'The edge can reject an absent token; only the service knows the rules'] },
    { label: 'Request body validation', cells: ['Size limit only', 'Yes', 'Schema knowledge lives with the service'] },
  ]}
/>

The rule underneath: **the edge handles what is true for every request regardless of who is asking.**
Anything requiring identity, business context or per-tenant configuration belongs behind it, because
duplicating that knowledge in the proxy means it drifts and you now have two places to be wrong.

```nginx
# Body size is an edge concern — reject before buffering 500 MB.
client_max_body_size 10m;
client_body_timeout 10s;

# Slowloris defence: a client that trickles headers is disconnected.
client_header_timeout 10s;
send_timeout 10s;
```
