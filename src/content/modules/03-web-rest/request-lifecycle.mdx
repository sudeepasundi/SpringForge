Most Spring MVC confusion comes from not knowing *where* in the pipeline something happens. A 404
that should be a 200, a `@RequestBody` that arrives null, a filter that never sees the
authenticated user — every one of these is a question about ordering.

So here is the ordering. Once you can place a stage in this pipeline, you can debug almost any web
problem by asking "which stage is this, and what does that stage know?"

Read that diagram once more and note the two nesting levels, because almost every "why did my code
not run" question resolves to them:

- **Filters** are servlet-container concepts. They wrap *everything*, including the
  `DispatcherServlet` itself and including error dispatches. They see raw
  `ServletRequest`/`ServletResponse` and know nothing about controllers, paths, or handler methods.
- **Interceptors** are Spring MVC concepts. They wrap only handler execution, and they run after
  the handler has been resolved — so they know which controller method is about to run.

<Callout type="tip" title="The rule that settles the choice">
If you need to know *which handler* is about to run, use an interceptor. If you need to run even
when no handler matched — security, tracing, request logging — use a filter.
</Callout>

## Reading a 404 correctly

A 404 from Spring MVC almost never means "the resource is missing". It means **no handler
mapping matched the request**, which is a different claim. Ask three questions in order:

<Steps>
  <Step title="Is the controller a bean at all?">

Component scanning starts at the package of your `@SpringBootApplication` class and goes
*downwards*. A controller in a sibling package is never registered, and there is no warning.

```bash
curl localhost:8080/actuator/beans | grep -i taskcontroller
```

  </Step>
  <Step title="Is the mapping registered, and at the path you think?">

The mappings endpoint is the authoritative answer — it prints exactly what
`RequestMappingHandlerMapping` holds, including the context path and any prefix.

```bash
curl localhost:8080/actuator/mappings
```

  </Step>
  <Step title="Is something narrowing the match?">

`consumes`, `produces`, `params` and `headers` all participate in matching. A mapping declared
`consumes = "application/json"` will not match a request with no `Content-Type` at all — and the
result is a 415, not a 404, which is the clue that you got past the path match.

  </Step>
</Steps>

## Filters and interceptors in code

The two look similar and are not interchangeable. Note what each one has access to.

<Compare>
  <Bad title="A filter that wants handler information">

A filter cannot know the handler — resolution has not happened yet when it runs. Reaching for the
mapping here means re-implementing `HandlerMapping`, badly.

```java
@Component
public class AuditFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws IOException, ServletException {
        // There is no handler yet. Parsing the URI to guess the controller is
        // a re-implementation of handler mapping that will drift from it.
        String guess = request.getRequestURI().split("/")[2];
        audit.record(guess);
        chain.doFilter(request, response);
    }
}
```

  </Bad>
  <Good title="An interceptor, which runs after resolution">

By `preHandle` the handler is known, so the annotation on the method is available and the audit
record is accurate.

```java
@Component
public class AuditInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) {
        if (handler instanceof HandlerMethod method) {
            Audited audited = method.getMethodAnnotation(Audited.class);
            if (audited != null) {
                audit.record(audited.value(), method.getMethod().getName());
            }
        }
        return true; // false here stops the dispatch before the controller runs
    }
}
```

  </Good>
</Compare>

Interceptors are registered explicitly — they are not picked up by being a bean:

```java title="WebConfig.java" {8-11}
@Configuration
public class WebConfig implements WebMvcConfigurer {

    private final AuditInterceptor auditInterceptor;

    public WebConfig(AuditInterceptor auditInterceptor) {
        this.auditInterceptor = auditInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(auditInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/health");
    }
}
```

<Callout type="pitfall" title="afterCompletion still runs when the handler throws">
`postHandle` is skipped if the handler throws, but `afterCompletion` always runs — it receives the
exception as its fourth argument. Any cleanup (closing a resource, stopping a timer, clearing a
`ThreadLocal`) belongs in `afterCompletion`, never in `postHandle`.
</Callout>

## Where the response body comes from

`@RestController` is `@Controller` + `@ResponseBody`, and `@ResponseBody` is what routes the return
value to an `HttpMessageConverter` instead of a view resolver. For JSON that converter is
`MappingJackson2HttpMessageConverter`, which means **your response shape is whatever Jackson
decides**, not whatever your class declares.

That single fact explains a family of bugs: a lazily-loaded JPA association serialised into an
extra query storm, an `Instant` rendered as an object instead of an ISO string, a field appearing
in the payload because it has a public getter you forgot about. It is the strongest practical
argument for the DTO boundary you will see throughout this course.

<Callout type="prod">
Turn on `spring.mvc.log-request-details` in a *non-production* profile when you are stuck. It logs
resolved arguments and the selected handler, which usually turns a twenty-minute guess into a
ten-second read. Never enable it in production — it logs request payloads, and those contain
personal data and credentials.
</Callout>
