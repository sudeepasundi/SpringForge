WebFlux was the answer to a real problem: a servlet container holds one thread per in-flight request,
threads are expensive, and a service that mostly waits on I/O runs out of threads long before it runs
out of CPU.

Java 21 answered the same problem differently, and the answer is much cheaper to adopt. This lesson
is about which tool that leaves you with.

The insight that changed the calculus: **a blocked thread is only expensive because platform threads
are expensive.** Virtual threads make them cheap, which removes the reason most teams reached for
reactive in the first place.

## Enabling virtual threads

One property. Your controllers, services and repositories do not change.

```yaml title="application.yml"
spring:
  threads:
    virtual:
      enabled: true      # Java 21+, Spring Boot 3.2+
```

Tomcat now runs each request on a virtual thread. Blocking on a JDBC call unmounts the virtual
thread from its carrier, freeing the carrier for other work, and remounts when the call returns. The
code is unchanged; the concurrency ceiling moves by orders of magnitude.

<Callout type="pitfall" title="Pinning: when a virtual thread cannot unmount">
A virtual thread blocked inside a `synchronized` block, or inside a native call, **pins** its carrier
thread — it cannot unmount, so the carrier is blocked too. With a small carrier pool that is a
throughput collapse.

Replace `synchronized` with `ReentrantLock` on any path that blocks. Check your dependencies too:
older JDBC drivers and connection pools used `synchronized` internally. Find pinning with:

```bash
java -Djdk.tracePinnedThreads=full -jar app.jar
```
</Callout>

## The connection pool is still the ceiling

The most common misunderstanding about both virtual threads and WebFlux: **neither makes your
database faster.**

If the Hikari pool has ten connections, ten queries run at a time. What changes is what happens to
request eleven:

Virtual threads make it *cheap to wait*, which is genuinely useful and also a trap: an application
that used to fail fast on thread exhaustion can now accumulate an enormous queue of waiting requests
and degrade silently. Bound the queue deliberately — module 08 covers bulkheads and load shedding.

## The cost, honestly

Reactive code is a different programming model, and the cost is not the syntax.

<Compare>
  <Bad title="What you give up">

Stack traces stop describing the call path. A breakpoint tells you about the assembly of the
pipeline, not its execution. `ThreadLocal` — and everything built on it, including MDC logging and
`SecurityContextHolder` — no longer works, because there is no thread affinity.

```java
public Mono<OrderView> getOrder(String id) {
    return orderRepository.findById(id)
            .flatMap(order -> Mono.zip(
                    customerClient.get(order.customerId()),
                    inventoryClient.check(order.items()))
                .map(t -> OrderView.of(order, t.getT1(), t.getT2())))
            .switchIfEmpty(Mono.error(new OrderNotFound(id)));
}
```

One blocking call anywhere in that chain stalls an event-loop thread and, with it, every other
request assigned to that loop.

  </Bad>
  <Good title="The same thing, blocking">

Ordinary code. The stack trace is real, the debugger works, MDC and the security context propagate,
and every developer can read it. On virtual threads it scales comparably for this workload.

`StructuredTaskScope` is a preview API in Java 21 and needs `--enable-preview`; its shape has
changed in later releases. Without it, two `CompletableFuture.supplyAsync` calls on a virtual-thread
executor get you the same parallelism with none of the scope guarantees.

```java
public OrderView getOrder(String id) {
    Order order = orderRepository.findById(id)
            .orElseThrow(() -> new OrderNotFound(id));

    // Structured concurrency: both calls run in parallel, and the scope
    // guarantees neither outlives it.
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        var customer  = scope.fork(() -> customerClient.get(order.customerId()));
        var inventory = scope.fork(() -> inventoryClient.check(order.items()));
        scope.join().throwIfFailed();
        return OrderView.of(order, customer.get(), inventory.get());
    }
}
```

  </Good>
</Compare>

<Callout type="prod">
If you do run WebFlux, the discipline that matters most is: **never block on an event-loop thread.**
Add BlockHound to your test suite — it instruments the JVM to throw when a blocking call happens on
a non-blocking thread, turning a subtle production stall into a failing test. A single
`repository.findById()` returning a blocking `Optional` inside a `flatMap` can halve throughput, and
nothing in the code will look wrong.
</Callout>

## The recommendation

**Default to Spring MVC with virtual threads enabled.** It is the simplest thing that scales for the
overwhelming majority of services: ordinary blocking code, real stack traces, working `ThreadLocal`,
and a concurrency ceiling set by your database rather than your thread pool.

Choose WebFlux when you need backpressure, or when you are holding a very large number of mostly-idle
connections, or when the team already lives there. Those are real cases — they are just not most
cases, and adopting the model without one of them buys complexity and nothing else.
