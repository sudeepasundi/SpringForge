Two topic settings are effectively permanent once traffic is flowing: the partition count, and
whether the topic deletes old data or compacts it. Both are easy to change in the console and
expensive to change in reality.

## Partition count

Partitions are the unit of parallelism. More partitions means more consumers can work in parallel —
and more of everything else.

<DecisionTable
  columns={['More partitions gives you', 'And costs you']}
  rows={[
    { label: 'Consumer parallelism', verdict: 'good', cells: ['One consumer per partition per group', '—'] },
    { label: 'Producer throughput', verdict: 'good', cells: ['Writes spread across more leaders', '—'] },
    { label: 'Open file handles', verdict: 'bad', cells: ['—', 'Each partition is directories and segment files on every replica'] },
    { label: 'Memory', verdict: 'bad', cells: ['—', 'Producer buffers and consumer fetch buffers are per partition'] },
    { label: 'Failover time', verdict: 'bad', cells: ['—', 'A failed broker means re-electing leaders for every partition it led'] },
    { label: 'End-to-end latency', verdict: 'bad', cells: ['—', 'More partitions to replicate before a record is committed'] },
  ]}
/>

A workable sizing method, which beats guessing:

<Steps>
  <Step title="Measure one consumer">

Load test a single consumer instance doing the real work — including the database writes. Suppose it
handles 800 records/second.

  </Step>
  <Step title="Divide peak throughput by that">

Peak is 12,000 records/second, so you need 15 consumers, so you need at least 15 partitions.

  </Step>
  <Step title="Add headroom, then round up">

Consumers get slower as the code grows, and traffic grows. Something like 2× is reasonable, so 30.

  </Step>
  <Step title="Sanity-check the total">

A modern KRaft cluster handles hundreds of thousands of partitions, but per-broker is what matters:
keep it in the low thousands per broker. Thirty partitions on a topic is unremarkable; three thousand
on one topic is a design smell.

  </Step>
</Steps>

<Callout type="pitfall" title="Increasing partitions breaks ordering, permanently">
Partition assignment is `hash(key) % partitionCount`. Change the count and most keys route somewhere
new — so events for an order that used to go to partition 2 now go to partition 5, and can be
consumed **before** older events still sitting in partition 2.

There is no fix. The ordering guarantee you built on is gone for every key with unprocessed history.

This is why you over-provision partitions up front. Idle partitions cost a little memory and a few
file handles. Repartitioning costs correctness.
</Callout>

## Retention or compaction

Two different answers to "what happens to old data", and choosing the wrong one loses either money or
your ability to rebuild.

The default is `delete` with `retention.ms=604800000` — seven days. That is fine for an event stream
and **wrong for anything feeding a projection**, as
[module 09](/learn/event-driven/cqrs) noted: replaying a seven-day topic to rebuild a read model
silently produces a projection missing every key that has not changed this week.

```properties title="A compacted topic for state"
cleanup.policy=compact
min.cleanable.dirty.ratio=0.1     # compact sooner; the default 0.5 is lazy
segment.ms=3600000                # the active segment is never compacted
delete.retention.ms=86400000      # how long tombstones survive for consumers to see
min.insync.replicas=2
```

<Callout type="tip" title="A tombstone is how you delete from a compacted topic">
Producing a record with a key and a **null value** marks that key deleted. Compaction removes the
key entirely once `delete.retention.ms` has passed — long enough for every consumer to observe the
deletion.

Set `delete.retention.ms` above your worst-case consumer downtime. Too short and a consumer that was
offline never learns the key was deleted, so its projection keeps a row that should be gone.
</Callout>

## Segments

A partition is a sequence of segment files. Only closed segments are eligible for deletion or
compaction — the active one is always retained.

```properties
segment.bytes=1073741824    # 1 GiB, the default
segment.ms=604800000        # or roll after 7 days, whichever comes first
```

The consequence people meet: **`retention.ms` is a floor, not a ceiling.** A low-traffic topic with a
one-hour retention and a 1 GiB segment size keeps data for days, because the segment never fills and
never rolls, and Kafka does not delete an open segment.

If retention actually matters — a compliance deletion window, say — lower `segment.ms` so segments
roll on time regardless of volume.

## Quotas

One misbehaving client can saturate a broker. Quotas throttle rather than reject, so a client that
exceeds its allowance is simply delayed.

```bash
# 10 MB/s produce, 20 MB/s consume, for one client id.
kafka-configs.sh --bootstrap-server kafka:9092 --alter \
  --add-config 'producer_byte_rate=10485760,consumer_byte_rate=20971520' \
  --entity-type clients --entity-name reporting-exporter
```

The one to set first is a **request quota**, which limits broker CPU rather than bandwidth:

```bash
kafka-configs.sh --bootstrap-server kafka:9092 --alter \
  --add-config 'request_percentage=200' \
  --entity-type clients --entity-name reporting-exporter
```

A client polling with a tiny `fetch.max.wait.ms` can consume very little bandwidth while burning
broker CPU on request handling. Bandwidth quotas do not touch that; request quotas do.

## Creating topics deliberately

<Compare>
  <Bad title="Auto-creation">

A typo in a topic name creates a topic — with the broker defaults, which are one replica and seven
days. It works in development and loses data in production, and nobody notices until the rebuild.

```properties
auto.create.topics.enable=true    # the default
```

  </Bad>
  <Good title="Explicit, reviewed topic definitions">

Topics are declared, reviewed and versioned like any other infrastructure. A typo is a failure, not a
silently misconfigured topic.

```properties
auto.create.topics.enable=false
```

```bash
kafka-topics.sh --bootstrap-server kafka:9092 --create \
  --topic shopflow.order.events \
  --partitions 30 \
  --replication-factor 3 \
  --config min.insync.replicas=2 \
  --config retention.ms=1209600000 \
  --config cleanup.policy=delete
```

  </Good>
</Compare>

<Callout type="prod">
Disable auto-creation in every environment above development. The failure it produces is exactly the
kind that survives testing: the topic exists, messages flow, and only the replication factor and
retention are wrong — which you discover when a broker dies or a rebuild comes up empty.
</Callout>
