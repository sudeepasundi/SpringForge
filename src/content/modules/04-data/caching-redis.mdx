Caching is the fastest way to make a slow endpoint fast and the fastest way to serve wrong data
confidently. The annotation is one line; the consistency decision behind it is the whole job.

## Before you cache

Three questions, in order. Two of them frequently make the cache unnecessary.

<Steps>
  <Step title="Have you measured?">

"This endpoint is slow" is not a reason to cache. Find out *why* it is slow first — an N+1 problem
or a missing index is usually cheaper to fix than a cache is to operate, and caching a bad query
just serves the bad result faster.

  </Step>
  <Step title="Is the read/write ratio high?">

A cache pays off when the same value is read many times between writes. Reference data, a
permissions lookup, an expensive aggregate: yes. A user's own recently-edited record: usually not.

  </Step>
  <Step title="How stale can this be?">

This is the question that decides everything below. "It must never be stale" and "an hour is fine"
lead to entirely different designs — and if the answer is genuinely the former, you probably do not
want a cache.

  </Step>
</Steps>

## The Spring Cache abstraction

Three annotations, backed by whichever `CacheManager` you configure.

```java title="task/TaskService.java" {6,15,22}
@Service
public class TaskService {

    // Look in the cache; on a miss run the method and store the result.
    @Cacheable(cacheNames = "tasks", key = "#id")
    public TaskResponse get(UUID id) {
        return repository.findSummaryById(id).orElseThrow(() -> new TaskNotFoundException(id));
    }

    // Always runs, then stores the result. For writes that return the new state.
    @CachePut(cacheNames = "tasks", key = "#result.id()")
    @Transactional
    public TaskResponse update(UUID id, UpdateTaskRequest request) { … }

    // Removes the entry. Note beforeInvocation — see below.
    @CacheEvict(cacheNames = "tasks", key = "#id")
    @Transactional
    public void delete(UUID id) { … }
}
```

<Callout type="pitfall" title="@Cacheable is a proxy, with everything that implies">
Calling `get(id)` from another method of the same class bypasses the cache entirely — the
self-invocation problem from [module 01](/learn/spring-core/aop-proxies). The method runs, the cache
is never consulted and never populated, and there is no error. If a cache appears to do nothing,
check the call path before checking the configuration.
</Callout>

## Redis, configured deliberately

The defaults are not what you want in production. Serialisation and TTL both need a decision.

```java title="support/CacheConfig.java" {8-10,15-19}
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    RedisCacheManager cacheManager(RedisConnectionFactory factory, ObjectMapper objectMapper) {
        RedisCacheConfiguration defaults = RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(10))
                .disableCachingNullValues()          // do not cache "not found" by default
                .serializeValuesWith(SerializationPair.fromSerializer(
                        new GenericJackson2JsonRedisSerializer(objectMapper)));

        return RedisCacheManager.builder(factory)
                .cacheDefaults(defaults)
                // Per-cache TTLs: reference data changes far less than task data.
                .withCacheConfiguration("tasks", defaults.entryTtl(Duration.ofMinutes(2)))
                .withCacheConfiguration("permissions", defaults.entryTtl(Duration.ofMinutes(30)))
                .withCacheConfiguration("countries", defaults.entryTtl(Duration.ofHours(24)))
                .build();
    }
}
```

<Callout type="prod">
**Always set a TTL, even when you evict correctly.** Eviction logic has bugs; processes die between
the write and the evict; a network partition drops the invalidation. A TTL is the backstop that
bounds how long a bug can serve wrong data. An entry with no expiry can be wrong forever.
</Callout>

Two serialisation notes that cost people real time:

- **The JDK default serializer requires `Serializable` and produces opaque bytes** nobody can inspect
  in `redis-cli`. Use JSON.
- **JSON serialisation is a compatibility surface.** Cached entries survive your deploy. Removing a
  field from a DTO means the new code deserialising an old entry — configure the `ObjectMapper` to
  ignore unknown properties, or version the cache name.

## Cache a projection, never an entity

```java
// A managed entity: lazy proxies, a version field, Hibernate internals.
// Serialising it may trigger queries; deserialising gives you a detached
// object that looks managed and is not.
@Cacheable("tasks")
public Task get(UUID id) { … }

// A record with only the fields you need. Serialises cleanly, deserialises to
// exactly what it was, and cannot be mistaken for something the ORM manages.
@Cacheable("tasks")
public TaskResponse get(UUID id) { … }
```

## Invalidation

Two viable strategies, and the choice follows from that third question above.

    },

    },

/>

The failure mode of evict-on-write is missing a path: a batch job, an admin tool, a database
migration. Every one of those writes without going through your `@CacheEvict` method, and the cache
serves the old value until the TTL saves you.

<Callout type="pitfall" title="Evict after the transaction commits, not during">
`@CacheEvict` runs when the method returns — which is *before* the transaction commits. In the window
between, another request can read the old value from the database and repopulate the cache with it.
The transaction then commits, and the cache is stale with no further writes to fix it.

Evict after commit instead:

```java
@Transactional
public void update(UUID id, UpdateTaskRequest request) {
    Task task = repository.findById(id).orElseThrow();
    task.apply(request);
    events.publishEvent(new TaskChanged(id));
}

@TransactionalEventListener(phase = AFTER_COMMIT)
void evict(TaskChanged event) {
    cacheManager.getCache("tasks").evict(event.taskId());
}
```
</Callout>

## Stampedes and hot keys

Two failure modes that only appear under load, which is the worst time to discover them.

**A stampede** happens when a popular key expires. Every concurrent request misses, and all of them
run the expensive query at once — so the moment the cache would have helped most, the database gets
the full load.

Two mitigations, and the first is nearly free:

```java
// 1. Jitter the TTL so keys written together do not expire together.
Duration ttl = Duration.ofMinutes(10)
        .plusSeconds(ThreadLocalRandom.current().nextInt(120));

// 2. Let one request rebuild while the others wait, rather than all of them.
@Cacheable(cacheNames = "expensive", sync = true)
public Report build(UUID id) { … }
```

`sync = true` is per-JVM, not cluster-wide — it stops 400 threads in one instance from piling on, not
400 instances. For genuinely expensive rebuilds you need a distributed lock, which Redisson provides;
for most workloads jitter plus `sync` is enough.

**A hot key** is a single key taking a disproportionate share of traffic — a feature flag, a
homepage. Redis is single-threaded per key, so one very hot key can become a bottleneck in its own
right. The fix is a small local cache in front of the distributed one, with a short TTL:

```java
// Caffeine in front of Redis: near-zero latency for the hottest entries,
// at the cost of up to `localTtl` of extra staleness per instance.
@Bean
CacheManager cacheManager(RedisCacheManager redis, CaffeineCacheManager local) {
    return new CompositeCacheManager(local, redis);
}
```

<Callout type="prod">
Instrument hit rate from day one. Micrometer publishes `cache.gets` tagged by `result`, and a cache
with a 12% hit rate is not a cache — it is a Redis dependency you have added to your critical path
for nothing. It is also the metric that tells you a TTL is too short long before anyone reports a
latency problem.
</Callout>
