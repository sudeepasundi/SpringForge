`@Transactional` on a method is a small annotation with a large contract: where the transaction
begins and ends, what happens when a nested call has one already, what other transactions can see,
and what rolls back.

Getting any of those wrong produces data that is subtly, permanently wrong. This lesson is the whole
contract.

## Where the boundary goes

The transaction boundary is a business-operation boundary. That puts it on the **service**, and
nowhere else.

## Propagation: what happens when one already exists

Seven values. Three matter in practice, and one of them is the source of a genuinely nasty bug.

<Callout type="pitfall" title="REQUIRES_NEW can deadlock against its own caller">
The outer transaction holds a lock on a row. The inner `REQUIRES_NEW` transaction — a genuinely
separate database transaction — tries to update the same row. It waits for a lock the outer
transaction will not release until the inner one returns.

That is a deadlock with a single thread, and it will not reproduce in a test with an empty table.
Only use `REQUIRES_NEW` when the inner work touches *different* rows.
</Callout>

<Callout type="pitfall" title="Propagation only applies through the proxy">
`REQUIRES_NEW` on a method called from another method of the same class does nothing at all — the
call goes through `this`, not the proxy, so no new transaction is created. This is the
self-invocation problem from [module 01](/learn/spring-core/aop-proxies), and propagation is where
its consequences are worst: you believe rows are being committed independently, and they are not.
</Callout>

## Rollback rules

The default surprises people, and the surprise costs data.

<Compare>
  <Bad title="A checked exception does not roll back">

`IOException` is checked, so the default rules do not roll back on it. The task is already saved;
the transaction commits it. You have a task with no notification, and no error to explain it.

```java
@Transactional
public void createAndNotify(CreateTaskRequest request) throws IOException {
    Task task = repository.save(new Task(request.title()));
    notifier.send(task);          // throws IOException — and the task stays committed
}
```

  </Bad>
  <Good title="Say what should roll back">

Either declare it, or — better — do not use checked exceptions for failures the caller cannot
meaningfully handle.

```java
@Transactional(rollbackFor = IOException.class)
public void createAndNotify(CreateTaskRequest request) throws IOException { … }

// Or, preferably:
@Transactional
public void createAndNotify(CreateTaskRequest request) {
    Task task = repository.save(new Task(request.title()));
    try {
        notifier.send(task);
    } catch (IOException e) {
        throw new NotificationFailedException(task.getId(), e);   // unchecked — rolls back
    }
}
```

  </Good>
</Compare>

The rule: **rollback on `RuntimeException` and `Error`; commit on checked exceptions.** It is a
Spring convention inherited from EJB, not a law of nature, and it is worth stating in a code review
checklist because nobody guesses it correctly.

<Callout type="pitfall" title="Catching an exception does not un-mark a rollback">
Once any transactional method has thrown a rollback-triggering exception, the transaction is marked
rollback-only. Catching the exception in an outer method does not clear that mark — the outer method
completes normally and then commit fails with
`UnexpectedRollbackException: Transaction silently rolled back`.

If an inner operation is allowed to fail without dooming the whole transaction, it must run in its
own (`REQUIRES_NEW`) or be attempted before anything you need to keep.
</Callout>

## Isolation: what you are allowed to see

Isolation levels are defined by which anomalies they prevent.

<DecisionTable
  columns={['Dirty read', 'Non-repeatable read', 'Phantom read', 'Cost']}
  rows={[
    { label: 'READ_UNCOMMITTED', verdict: 'bad', cells: ['Possible', 'Possible', 'Possible', 'Never worth it'] },
    { label: 'READ_COMMITTED', verdict: 'good', cells: ['Prevented', 'Possible', 'Possible', 'Postgres, Oracle and SQL Server default'] },
    { label: 'REPEATABLE_READ', verdict: 'good', cells: ['Prevented', 'Prevented', 'Possible*', 'MySQL default'] },
    { label: 'SERIALIZABLE', verdict: 'mixed', cells: ['Prevented', 'Prevented', 'Prevented', 'Real contention; needs retry logic'] },
  ]}
/>

The three anomalies, concretely:

- **Dirty read** — you see a change another transaction has not committed, and may roll back.
- **Non-repeatable read** — you read a row twice in one transaction and get different values.
- **Phantom read** — you run the same query twice and the second returns rows the first did not.

**Leave the default.** `READ_COMMITTED` is right for the overwhelming majority of work, and raising
the level is almost never the correct answer to a concurrency problem. Locking is.

<Callout type="prod">
The lost-update problem is not solved by isolation level. Two transactions read a row at
`READ_COMMITTED`, both compute a new value from what they read, both write — and the second silently
overwrites the first. No anomaly definition covers it, and no isolation level below SERIALIZABLE
prevents it. Locking does.
</Callout>

## Locking

<Compare>
  <Bad title="Read, modify, write — the lost update">

Two concurrent requests both read a balance of 100, both subtract 30, both write 70. Thirty units
have vanished, with no error anywhere.

```java
@Transactional
public void withdraw(UUID accountId, BigDecimal amount) {
    Account account = repository.findById(accountId).orElseThrow();
    account.setBalance(account.getBalance().subtract(amount));   // last writer wins
}
```

  </Bad>
  <Good title="Optimistic locking with @Version">

Hibernate adds `where version = ?` to the update. The second transaction updates zero rows and
throws `OptimisticLockException`, so the caller can retry against fresh data.

```java
@Entity
public class Account {
    @Version
    private long version;        // Hibernate manages this; you never set it
}

@Transactional
public void withdraw(UUID accountId, BigDecimal amount) {
    Account account = repository.findById(accountId).orElseThrow();
    account.setBalance(account.getBalance().subtract(amount));
}
```

```sql
update accounts set balance = ?, version = 4 where id = ? and version = 3
-- 0 rows updated → OptimisticLockException
```

  </Good>
</Compare>

Optimistic locking is the right default: no locks are held, and conflicts are detected rather than
prevented. It requires the caller to handle the retry, which `@Retryable` on
`ObjectOptimisticLockingFailureException` makes mechanical.

Pessimistic locking is for high-contention rows where retrying would mostly fail:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select a from Account a where a.id = :id")
Optional<Account> findByIdForUpdate(@Param("id") UUID id);   // SELECT … FOR UPDATE
```

  columns={['How', 'Use when', 'Cost']}
  rows={[
    {
      label: 'Optimistic (@Version)',
      verdict: 'good',
      cells: ['Detect the conflict at write time', 'Contention is rare', 'The caller must retry'],
    },
    {
      label: 'Pessimistic (FOR UPDATE)',

/>

<Callout type="prod">
Always set a lock timeout with pessimistic locking. Without one, a stuck transaction blocks every
other writer of that row indefinitely, and the symptom is an application that appears to hang with
no CPU usage and no errors.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
```
</Callout>

## Keep transactions short

A transaction holds a database connection and, for writes, row locks. Anything slow inside one is
holding both.

<Compare>
  <Bad title="A network call inside the transaction">

The HTTP call might take five seconds, or thirty on a timeout. For all of it, this transaction holds
a connection from a pool of ten and a lock on the task row.

```java
@Transactional
public void complete(UUID id) {
    Task task = repository.findById(id).orElseThrow();
    task.complete();
    billingClient.charge(task.getAccountId());     // remote call, unbounded duration
    emailClient.sendCompletion(task);              // another one
}
```

  </Bad>
  <Good title="Commit, then do the slow work">

The transaction commits in milliseconds. The remote calls happen afterwards, triggered by an event
bound to the commit — so they never run for work that rolled back.

```java
@Transactional
public void complete(UUID id) {
    Task task = repository.findById(id).orElseThrow();
    task.complete();
    events.publishEvent(new TaskCompleted(task.getId(), task.getAccountId()));
}

@Component
class TaskCompletedListener {

    @TransactionalEventListener(phase = AFTER_COMMIT)
    void onCompleted(TaskCompleted event) {
        billingClient.charge(event.accountId());
        emailClient.sendCompletion(event.taskId());
    }
}
```

  </Good>
</Compare>

`@TransactionalEventListener(AFTER_COMMIT)` is the tool for this and is worth knowing well: the
listener runs only if the transaction actually committed, which removes an entire class of "we
emailed the customer about an order that rolled back" bugs. Module 09 turns this into the outbox
pattern, which also survives the process dying between commit and listener.
