There are exactly two ways a schema gets created. One is a tool that applies ordered, versioned
scripts you wrote and reviewed. The other is Hibernate guessing from your entities at startup.

Only one of them can be reasoned about.

## Turn off ddl-auto

`spring.jpa.hibernate.ddl-auto` decides what Hibernate does to your schema at startup.

<DecisionTable
  columns={['Does', 'Safe in production?']}
  rows={[
    { label: 'none', verdict: 'good', cells: ['Nothing', 'Yes — the only correct answer'] },
    { label: 'validate', verdict: 'good', cells: ['Checks entities against the schema and fails on a mismatch', 'Yes, and useful'] },
    { label: 'update', verdict: 'bad', cells: ['Adds missing tables and columns; never removes or alters', 'No — see below'] },
    { label: 'create / create-drop', verdict: 'bad', cells: ['Drops and recreates the schema', 'Absolutely not'] },
  ]}
/>

`update` is the dangerous one because it *almost* works. It adds a column, so development feels fine.
It will not narrow a type, will not add a constraint to existing rows, will not rename anything, and
will not remove a column you deleted — so the schema slowly drifts into a state that matches nothing
in your repository and cannot be reproduced anywhere. There is no record of what changed or when.

```yaml title="application.yml"
spring:
  jpa:
    hibernate:
      ddl-auto: validate      # Flyway owns the schema; Hibernate only checks it
  flyway:
    enabled: true
```

`validate` is worth using rather than `none`: it fails at startup when an entity and the schema
disagree, which catches a forgotten migration before any request is served.

## Versioned migrations

Flyway applies numbered scripts in order and records what it has applied in a `flyway_schema_history`
table.

```text
src/main/resources/db/migration/
├── V1__create_tasks.sql
├── V2__add_task_assignee.sql
├── V3__backfill_assignee.sql
└── R__task_summary_view.sql        # repeatable: re-applied whenever its checksum changes
```

```sql title="V2__add_task_assignee.sql"
alter table tasks add column assignee_id uuid;

alter table tasks
    add constraint fk_tasks_assignee
    foreign key (assignee_id) references users (id);

create index idx_tasks_assignee on tasks (assignee_id);
```

<Callout type="pitfall" title="Never edit an applied migration">
Flyway stores a checksum of each script. Editing `V2` after it has run in any environment makes
Flyway refuse to start with a checksum mismatch — correctly, because the database it is looking at
was built from a different script than the one in the repository.

Fix a mistake with `V3`, always. `flyway.repair` exists for genuine emergencies and its use should be
rare enough to be memorable.
</Callout>

## Zero-downtime schema change

During a rolling deploy, old and new versions of your application run **simultaneously against the
same database**. Any migration that only the new code can tolerate breaks the old instances that are
still serving traffic.

The rule follows directly: **every migration must be compatible with the currently deployed code.**
That makes destructive changes a sequence, not a step.

Renaming `tasks.name` to `tasks.title`, in full:

<Steps>
  <Step title="Expand — add the new column, write both">

The column is nullable, so the currently-running old code is unaffected. Deploy application code that
writes both columns and still reads `name`.

```sql title="V4__add_task_title.sql"
alter table tasks add column title varchar(200);
```

  </Step>
  <Step title="Migrate — backfill in batches, then switch reads">

Backfill in bounded batches. A single `update tasks set title = name` on ten million rows takes a
long lock and can exhaust the write-ahead log.

```sql title="V5__backfill_task_title.sql"
-- Bounded batches keep the lock short and the transaction small.
do $$
declare
    updated integer;
begin
    loop
        update tasks set title = name
        where title is null
          and id in (select id from tasks where title is null limit 5000);

        get diagnostics updated = row_count;
        exit when updated = 0;
        commit;
    end loop;
end $$;
```

Then deploy code that reads `title` and still writes both.

  </Step>
  <Step title="Contract — stop writing, then drop">

Deploy code that no longer references `name` at all. Only once that is fully rolled out — and you
are confident you will not roll back past it — drop the column.

```sql title="V6__drop_task_name.sql"
alter table tasks drop column name;
```

  </Step>
</Steps>

Three releases to rename a column. That is the actual cost of zero downtime, and it is why the
cheapest schema change is the one you designed correctly the first time.

<Callout type="prod">
Adding a `not null` column with a default rewrites the entire table in older PostgreSQL and MySQL,
holding an exclusive lock for the duration. On a large table that is an outage.

The safe sequence is always: add nullable → backfill in batches → add the constraint with
`NOT VALID` and validate separately. Check what your specific database version does before running
any `ALTER TABLE` against a table with real volume.
</Callout>

## Where migrations run

Flyway runs at application startup by default, which is simple and has one sharp edge: during a
rolling deploy, **several instances start at once and all try to migrate.**

Flyway takes a database lock, so they do not corrupt each other — the others wait. But a slow
migration means every instance sits at the lock, and readiness probes may time out and kill them
mid-wait.

For anything beyond a small service, run migrations as a separate step. It makes the migration
failure distinguishable from an application failure, which matters a great deal at 3am.

## Rollback, honestly

Flyway Community has no `undo`. That is less of a limitation than it sounds, because **most schema
changes cannot be rolled back anyway** — dropping a column destroys the data in it, and no script
brings it back.

The real strategy is to make rollback unnecessary:

- **Every migration is additive and backwards-compatible** with the running code. Then rolling back
  the *application* is always safe, because the schema still supports the old version.
- **Destructive changes are separated in time** from the deploy that stopped using them, so there is
  a window where rollback is free.
- **Write the down script anyway** for the ones that can be reversed, and keep it out of the
  automatic path.

<Callout type="tip" title="Test migrations against a copy of production">
The migration that works on your 200-row development database is not the same operation on 40 million
rows. Restore a recent production snapshot into a scratch database in CI and run the migration
against it, with a timer. That is the only reliable way to find out that an `ALTER TABLE` takes eleven
minutes and holds an exclusive lock.
</Callout>
