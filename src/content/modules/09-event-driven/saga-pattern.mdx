Placing an order reserves stock, charges a card and schedules a shipment. In a monolith that is one
transaction. Across three services it cannot be — there is no shared transaction manager, and
two-phase commit across HTTP and Kafka is not something you want to operate.

A saga is a sequence of local transactions where each step has a **compensating action** that undoes
it.

## Compensation is not rollback

This distinction is the whole lesson, and it is where most saga designs go wrong.

<DecisionTable
  columns={['Rollback', 'Compensation']}
  rows={[
    { label: 'When', cells: ['Before commit', 'After commit — the effect already happened'] },
    { label: 'Visibility', verdict: 'bad', cells: ['Nobody saw the intermediate state', 'Others may have observed it and acted'] },
    { label: 'Result', cells: ['As if it never happened', 'A new fact that offsets the old one'] },
    { label: 'Example', cells: ['UPDATE undone by the database', 'A refund, which is a second transaction'] },
    { label: 'Always possible?', verdict: 'bad', cells: ['Yes', 'No — you cannot unsend an email'] },
  ]}
/>

A refund is not the absence of a charge. The customer saw the charge, their bank recorded it, and the
statement shows both lines. Compensation produces a **new fact**, and the design question is whether
the domain can express one.

<Callout type="pitfall" title="Order the steps by how hard they are to compensate">
Put the easily-reversible steps first and the irreversible ones last. Reserving stock is trivially
released; sending a "your order has shipped" email cannot be recalled.

If an irreversible step runs early, a later failure leaves you with no way to make the customer
whole — and you find out at the worst possible time.
</Callout>

## Choreography

Each service reacts to events. No coordinator exists.

```java title="inventory/OrderEventsConsumer.java" {6,12,19}
@Component
public class OrderEventsConsumer {

    @KafkaListener(topics = "shopflow.order.events", groupId = "inventory-service")
    @Transactional
    public void onOrderPlaced(OrderPlaced event) {
        if (processed.contains(event.eventId())) return;   // at-least-once delivery

        try {
            stock.reserve(event.orderId(), event.items());
            events.publish("inventory", event.orderId().toString(),
                    new StockReserved(event.orderId(), event.items()));
        } catch (InsufficientStockException e) {
            // A business failure is a fact, not an exception to retry.
            events.publish("inventory", event.orderId().toString(),
                    new StockReservationFailed(event.orderId(), e.getMessage()));
        }
        processed.record(event.eventId());
    }

    @KafkaListener(topics = "shopflow.payment.events", groupId = "inventory-service")
    @Transactional
    public void onPaymentFailed(PaymentFailed event) {
        // The compensation. Must be idempotent — this may arrive twice.
        stock.releaseIfReserved(event.orderId());
        events.publish("inventory", event.orderId().toString(),
                new StockReleased(event.orderId()));
    }
}
```

Note that `InsufficientStockException` becomes a **published event**, not a thrown exception. A
business failure is an outcome the saga must react to; throwing would retry the message and
eventually dead-letter it, leaving the saga stuck with no cancellation.

## Orchestration

One component owns the workflow and issues commands.

```java title="order/OrderSaga.java" {13,22,33,44}
@Component
public class OrderSaga {

    private final SagaStateRepository state;
    private final CommandGateway commands;

    @Transactional
    public void start(UUID orderId, List<OrderItem> items, Money total) {
        state.save(SagaState.started(orderId, items, total));
        commands.send(new ReserveStock(orderId, items));
    }

    @KafkaListener(topics = "shopflow.inventory.events", groupId = "order-saga")
    @Transactional
    public void onStockReserved(StockReserved event) {
        SagaState saga = state.load(event.orderId());
        if (!saga.advanceTo(Step.STOCK_RESERVED)) return;   // idempotent by state check

        commands.send(new CapturePayment(saga.orderId(), saga.total()));
    }

    @KafkaListener(topics = "shopflow.payment.events", groupId = "order-saga")
    @Transactional
    public void onPaymentFailed(PaymentFailed event) {
        SagaState saga = state.load(event.orderId());
        if (!saga.advanceTo(Step.COMPENSATING)) return;

        // Compensate every completed step, in reverse order.
        saga.completedSteps().reversed()
                .forEach(step -> commands.send(compensationFor(step, saga)));
    }

    @KafkaListener(topics = "shopflow.inventory.events", groupId = "order-saga")
    @Transactional
    public void onStockReleased(StockReleased event) {
        SagaState saga = state.load(event.orderId());
        saga.markCompensated(Step.STOCK_RESERVED);

        if (saga.fullyCompensated()) {
            commands.send(new CancelOrder(saga.orderId(), saga.failureReason()));
            saga.advanceTo(Step.CANCELLED);
        }
    }

    /** A saga stuck in a non-terminal state past its deadline needs attention. */
    @Scheduled(fixedDelay = 60_000)
    public void findStuckSagas() {
        state.findStuckBefore(Instant.now().minus(Duration.ofMinutes(15)))
                .forEach(saga -> alerts.sagaStuck(saga.orderId(), saga.currentStep()));
    }
}
```

The `advanceTo` guard is how the orchestrator stays idempotent: an event that does not move the state
machine forward is ignored, so redelivery is harmless.

The practical rule: **choreography up to three participants, orchestration beyond that.**

The reason is the debugging row. With three services you can hold the flow in your head. With six,
"why is this order stuck?" becomes an archaeology exercise across six sets of logs — and orders do get
stuck, so that question gets asked in production, under time pressure.

<Callout type="prod">
Whichever you choose, **persist the saga state**. Choreography's implicit state is fine until you
need to answer "how many orders are currently mid-saga, and which step are they on?" — a question
that arrives during your first incident.

Even a choreographed saga benefits from one service tracking progress for observability, without
issuing commands.
</Callout>

## Semantic locking

A saga's intermediate states are visible to everyone. Between "stock reserved" and "payment
captured", the order exists in a state that is neither confirmed nor cancelled.

Make that state explicit rather than pretending it does not exist:

```java title="order/Order.java" {6-11,17}
public enum OrderStatus {
    PENDING,            // saga in flight — do not treat as confirmed
    CONFIRMED,          // every step succeeded
    CANCELLED,          // compensated
    FAILED              // compensation itself failed — needs a human
}

@Entity
public class Order {

    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    /**
     * A pending order is a promise, not a fact. Anything that would act on a
     * confirmed order must check, or it will act on one that is about to cancel.
     */
    public boolean isVisibleToCustomer() {
        return status != OrderStatus.PENDING;
    }
}
```

Without this, a report run mid-saga counts revenue for an order whose payment is about to decline.

## When compensation fails

The case people skip, and the one that generates support tickets: stock was reserved, payment
declined, and the release-stock compensation also fails.

You cannot compensate the compensation. Three responses, and you need all three:

<Steps>
  <Step title="Retry with backoff">

Most compensation failures are transient — a service restarting, a network blip. Retry generously,
because the alternative is manual work.

  </Step>
  <Step title="Move to a terminal FAILED state and alert">

After retries are exhausted, stop. Do not keep retrying forever and do not silently give up. A saga
in `FAILED` is a known-bad state with a human owner, which is far better than one still claiming to
be in progress.

  </Step>
  <Step title="Make it operable">

Someone will have to fix this by hand. Give them what they need: the saga state, the completed steps,
the failure reason, and an endpoint to retry or force-complete after they have corrected the
underlying data.

```java
@PostMapping("/admin/sagas/{orderId}/retry-compensation")
@PreAuthorize("hasAuthority('saga.admin')")
public SagaState retryCompensation(@PathVariable UUID orderId) { … }
```

  </Step>
</Steps>

<Callout type="tip" title="Test the compensation paths">
The happy path gets tested because it is the feature. Compensations get tested when they run in
production, which is when they matter most.

Write a test per failure point: fail payment after stock is reserved and assert the stock is
released; fail shipping after payment and assert the refund is issued; fail the compensation itself
and assert the saga reaches `FAILED` and raises an alert.
</Callout>
