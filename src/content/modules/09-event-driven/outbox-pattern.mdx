Save the order to the database, then publish `OrderPlaced` to Kafka. Two writes, two systems, and no
transaction spanning both.

Whatever order you put them in, there is a moment where one has happened and the other has not. That
is the dual-write problem, and the outbox pattern is the standard solution.

## Why it cannot be fixed by reordering

<Compare>
  <Bad title="Database first, then publish">

The commit succeeds. The process is killed — a deploy, an OOM, a node failure — before the send. The
order exists and nothing downstream ever hears about it: no stock reserved, no confirmation, no
invoice. Silent, and invisible until a customer asks.

```java
@Transactional
public void place(PlaceOrderCommand command) {
    Order order = repository.save(Order.from(command));
    // ── commit happens here ──
    kafkaTemplate.send("orders", order.id().toString(), new OrderPlaced(order));
    // If the process dies between those two lines, the event is lost forever.
}
```

  </Bad>
  <Good title="Publish first, then save">

Not better — worse, and in a way that is harder to detect. Downstream services reserve stock and
send a confirmation for an order that was never persisted.

```java
public void place(PlaceOrderCommand command) {
    kafkaTemplate.send("orders", command.orderId().toString(), new OrderPlaced(command));
    // If the transaction now fails, every consumer has acted on an order
    // that does not exist. You have created phantom work.
    repository.save(Order.from(command));
}
```

  </Good>
</Compare>

Both panels are wrong; the second is only there to show that reordering is not a fix. Two-phase
commit would work in theory, and Kafka does not support XA in any way you want to operate. The
solution is to stop making two writes.

## One write, then relay

Write the event into the **same database, in the same transaction** as the business data. A separate
process reads the table and publishes.

The insight is that the event and the data now share a transaction because they share a database.
Whether the event reaches Kafka is a separate problem, and — crucially — a **retryable** one, because
the record is durable.

## The table

```sql title="V3__create_outbox.sql"
create table outbox (
    id             uuid         primary key,
    aggregate_type varchar(100) not null,
    aggregate_id   varchar(100) not null,   -- becomes the Kafka key
    event_type     varchar(150) not null,
    payload        jsonb        not null,
    created_at     timestamptz  not null default now(),
    published_at   timestamptz                        -- null until published
);

-- The relay's only query: unpublished rows, oldest first.
-- Partial index, so it stays small no matter how large the table grows.
create index idx_outbox_unpublished
    on outbox (created_at)
    where published_at is null;
```

## Writing the event

```java title="order/OrderService.java" {9,16-21}
@Service
public class OrderService {

    private final OrderRepository orders;
    private final OutboxRepository outbox;

    @Transactional
    public OrderResponse place(PlaceOrderCommand command) {
        Order order = orders.save(Order.from(command));

        // Same transaction. If this insert fails, the order rolls back too;
        // if the order fails, no event is recorded. There is no in-between.
        outbox.save(OutboxRecord.of(
                "order",
                order.id().toString(),
                "OrderPlaced",
                new OrderPlaced(order.id(), order.items(), order.total(), order.placedAt())));

        return OrderResponse.from(order);
    }
}
```

<Callout type="tip" title="Wrap it so nobody has to remember">
Two lines that must stay together are two lines someone will eventually separate. Publish through an
abstraction that writes to the outbox, so the correct behaviour is the default:

```java
@Component
public class DomainEvents {

    private final OutboxRepository outbox;

    /** Must be called inside a transaction — the whole point is that it joins one. */
    public void publish(String aggregateType, String aggregateId, Object event) {
        Assert.state(TransactionSynchronizationManager.isActualTransactionActive(),
                "Domain events must be published within a transaction");
        outbox.save(OutboxRecord.of(aggregateType, aggregateId,
                event.getClass().getSimpleName(), event));
    }
}
```

The assertion is worth the line. It converts "someone published outside a transaction and we lost
events for a week" into a failing test.
</Callout>

### Polling

```java title="order/OutboxRelay.java" {10,14,26,31}
@Component
public class OutboxRelay {

    private static final int BATCH_SIZE = 100;

    private final OutboxRepository outbox;
    private final KafkaTemplate<String, Object> kafka;

    @Scheduled(fixedDelay = 500)
    @SchedulerLock(name = "outboxRelay", lockAtMostFor = "PT30S")   // one instance at a time
    @Transactional
    public void publishPending() {
        // SELECT … FOR UPDATE SKIP LOCKED lets several instances work the table
        // concurrently without contending on the same rows.
        List<OutboxRecord> pending = outbox.findUnpublishedForUpdate(BATCH_SIZE);

        for (OutboxRecord record : pending) {
            try {
                kafka.send(topicFor(record), record.aggregateId(), record.payload())
                        .get(5, TimeUnit.SECONDS);      // synchronous: we must know it landed
                record.markPublished(Instant.now());
            } catch (Exception e) {
                // Leave published_at null and stop. The rest of the batch is
                // retried next tick — and stopping preserves ordering, since
                // skipping ahead would publish a later event before an earlier one.
                log.warn("Outbox publish failed for {}, will retry", record.id(), e);
                break;
            }
        }
    }
}
```

Three decisions in there are load-bearing.

**`SKIP LOCKED`** lets multiple instances relay concurrently. Without it they contend on the same
rows and you are limited to one worker.

**`@SchedulerLock`** (ShedLock) is belt and braces — it keeps the scheduled job to one instance,
which reduces useless contention even with `SKIP LOCKED`.

**The `break` on failure.** Continuing past a failed record would publish event #5 while #4 is still
unpublished, breaking per-aggregate ordering. Stopping preserves it.

<Callout type="pitfall" title="The outbox is at-least-once, not exactly-once">
Between `kafka.send()` succeeding and `markPublished` committing, the process can die. On restart the
row is still unpublished, so the event is sent again.

That is unavoidable — you would need a transaction spanning Kafka and the database, which is what you
were avoiding. **Consumers must be idempotent.** The next lessons take that as a given.
</Callout>

### Change data capture

Debezium tails the write-ahead log, so there is no polling query at all and ordering matches the
commit order exactly.

```json title="Debezium connector, with the outbox event router"
{
  "name": "order-outbox-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "orders-db",
    "database.dbname": "orders",
    "table.include.list": "public.outbox",
    "plugin.name": "pgoutput",

    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
    "transforms.outbox.route.by.field": "aggregate_type",
    "transforms.outbox.table.field.event.key": "aggregate_id",
    "transforms.outbox.table.field.event.payload": "payload",
    "transforms.outbox.route.topic.replacement": "shopflow.${routedByValue}.events"
  }
}
```

The `EventRouter` transform understands the outbox shape: it routes by `aggregate_type`, uses
`aggregate_id` as the Kafka key, and unwraps `payload` so consumers see the event rather than a
database change record.

for most business events. Move to CDC when the polling load or the latency becomes a real constraint,
not before.

## Housekeeping

The outbox grows forever unless something prunes it. Keep published rows for a while — they are
useful for debugging — then delete in bounded batches.

```sql title="Nightly, in batches, so no single statement takes a long lock"
delete from outbox
where id in (
    select id from outbox
    where published_at < now() - interval '7 days'
    limit 10000
);
```

<Callout type="prod">
Alert on **the age of the oldest unpublished row**, not on table size. A row that has been sitting
unpublished for five minutes means the relay has stopped — a crashed scheduler, a Kafka outage, a
poison payload — and every downstream service is silently missing events.

Table size tells you about retention. Oldest-unpublished-age tells you the system is broken.
</Callout>
