Every performance problem you have ever guessed at had a cause you could have measured. The guessing
is not faster — it is just more comfortable, because measuring requires admitting you do not know.

## The method

<Steps>
  <Step title="Define the problem as a number">

"The API is slow" is not actionable. "p99 on `POST /api/orders` is 2.4s against an SLO of 500ms at
200 requests per second" is.

Without a number and a load level, you cannot tell whether a change helped.

  </Step>
  <Step title="Reproduce it under load">

A single request on a quiet system exercises none of the interesting behaviour: no queueing, no lock
contention, no pool exhaustion, no GC pressure. Most production performance problems only exist under
concurrency.

  </Step>
  <Step title="Measure where the time goes">

A profiler or a trace waterfall. Not a hypothesis — the actual distribution of time.

  </Step>
  <Step title="Change one thing, measure again">

Two changes at once and you learn nothing about either. This is slower per iteration and much faster
overall.

  </Step>
</Steps>

<Callout type="pitfall" title="Do not optimise from a single-request measurement">
A method that takes 8ms alone can take 800ms under load — because it holds a lock, or waits for a
connection, or triggers GC pressure that costs everything else.

Conversely, a method that dominates a single-request profile may be irrelevant at 200 requests per
second, where the bottleneck is a pool with ten connections. **Profile under the load you care
about**, or you will optimise the wrong thing convincingly.
</Callout>

## Load testing that resembles reality

```javascript title="k6/checkout.js"
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 50 },    // ramp: find where behaviour changes
    { duration: '5m', target: 200 },   // sustained: this is where the truth is
    { duration: '2m', target: 400 },   // past capacity: does it degrade or collapse?
    { duration: '3m', target: 0 },     // recovery: does it come back on its own?
  ],
  thresholds: {
    'http_req_duration{name:placeOrder}': ['p(99)<500'],
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const res = http.post(`${__ENV.BASE_URL}/api/orders`,
    JSON.stringify(order()),
    { headers: { 'Content-Type': 'application/json',
                 // A stable key per iteration: retries must not double-charge.
                 'Idempotency-Key': `k6-${__VU}-${__ITER}` },
      tags: { name: 'placeOrder' } });

  check(res, { 'created': (r) => r.status === 201 });
  sleep(Math.random() * 2);   // think time — back-to-back requests are not real traffic
}
```

Four properties separate a useful load test from a misleading one:

- **A ramp**, so you can see *where* behaviour changes rather than only whether it fails.
- **Sustained load**, long enough for the JIT to warm, caches to fill and GC to reach steady state.
- **Past capacity**, because how a system fails matters as much as when.
- **Recovery**, because a system that never recovers after load subsides has a queue that never
  drains.

<Callout type="prod">
Load test with **production-shaped data**. A table with a thousand rows behaves nothing like one with
fifty million: index selectivity changes, the query planner picks different plans, and a full scan
that was instant becomes a minute.

Restore a production snapshot (anonymised) into a scratch environment. It is the difference between a
load test that predicts production and one that produces reassuring numbers.
</Callout>

## Profiling

```bash
# Continuous, low overhead, always available. Start here.
java -XX:StartFlightRecording=duration=120s,filename=app.jfr,settings=profile -jar app.jar

# Attach to a running process without a restart — often the only option
# when a problem is happening now.
jcmd <pid> JFR.start duration=60s filename=/tmp/live.jfr settings=profile

# async-profiler: better at native frames and lock contention, and its
# flame graphs are easier to read.
./profiler.sh -d 60 -e cpu -f cpu.html <pid>
./profiler.sh -d 60 -e lock -f lock.html <pid>     # who is waiting on what
./profiler.sh -d 60 -e alloc -f alloc.html <pid>   # what is producing garbage
```

Reading a flame graph, compressed to one rule: **width is time, and you look for wide plateaus.** A
wide frame near the top is a method doing the work itself; a wide frame near the bottom with narrow
children is a method whose time is spread thin. Depth means nothing.

web application for the first time are often disappointed: the CPU profile is flat because the
service is waiting, not computing.

## The connection pool is usually the answer

For a database-backed service, the pool is the bottleneck far more often than the code.

```yaml title="application.yml"
spring:
  datasource:
    hikari:
      # Sized against the database's capacity, not the application's thread count.
      # More connections than the database can serve concurrently makes things
      # slower, not faster — contention moves into the database.
      maximum-pool-size: 10
      minimum-idle: 10              # equal to max: avoid creating connections under load
      connection-timeout: 3000      # fail fast rather than queue indefinitely
      max-lifetime: 1800000         # under any proxy or database idle timeout
      leak-detection-threshold: 20000
```

<Callout type="tip" title="Smaller pools are usually faster">
The intuition says more connections means more throughput. Beyond a point the opposite is true: the
database has a fixed number of cores and disks, and more concurrent queries means more context
switching, more lock contention and more memory per connection.

HikariCP's own guidance suggests something close to `cores × 2` for many workloads. Ten connections
frequently outperforms fifty. Measure it — this is one of the few tuning parameters where the wrong
direction is the intuitive one.
</Callout>

The metric that tells you the pool is the constraint:

```promql
# Threads waiting for a connection. Sustained above zero means the pool
# is the bottleneck — not the query, not the CPU.
hikaricp_connections_pending

# How long acquiring a connection takes. If this is a meaningful fraction
# of request latency, the pool is your problem.
histogram_quantile(0.99, rate(hikaricp_connections_acquire_seconds_bucket[5m]))
```

## Thread pools under virtual threads

With virtual threads enabled, the request thread pool stops being a limit — which changes what to
tune, and removes a bound you may have been relying on:

```yaml
spring:
  threads:
    virtual:
      enabled: true
server:
  tomcat:
    # Largely irrelevant with virtual threads: threads are no longer scarce.
    threads:
      max: 200
    # This still matters enormously. It is the queue of connections waiting to
    # be accepted, and it is now the main thing bounding how much work you take on.
    accept-count: 100
    max-connections: 8192
```

The shift is that **the bound moves from threads to whatever is genuinely scarce** — the connection
pool, the downstream service, memory. If you do not add an explicit bound, the service accepts work
until something less graceful stops it.

## Caching, measured

Caching is the highest-leverage optimisation and the easiest to apply pointlessly:

```promql
# Hit ratio. Below ~80% and the cache is mostly overhead plus a dependency.
sum(rate(cache_gets_total{result="hit"}[5m]))
  / sum(rate(cache_gets_total[5m]))
```

Before adding a cache, check whether the query is slow because it is genuinely expensive or because
of an N+1 or a missing index. Caching a bad query just serves the bad result faster and adds an
invalidation problem you did not have.

The ordering is the lesson. Almost every dramatic improvement comes from the top three, and almost
every wasted week comes from the bottom two.

<Callout type="prod">
Scaling out is the fastest fix and it is a way of paying to avoid understanding a problem. If the
constraint is shared — a database, a downstream service, a lock — more instances make it worse, as
[module 11](/learn/cloud-native/kubernetes) noted about autoscaling.

Scale out to buy time during an incident. Then find the actual cause, because the bill compounds and
the constraint does not move.
</Callout>
