A distributed system does not fail the way a monolith does. A monolith is up or down. A distributed
system is mostly up, partially degraded, and occasionally taking itself apart in a way that nobody
designed.

This lesson is the mechanisms. The next four are the countermeasures.

## The failure that is not a failure

The hardest case is not a service that is down — that is easy, you get a connection refused
immediately. The hard case is a service that is **slow**.

Two things in that loop are worth staring at.

**The blast radius is not scoped to the dependency.** Requests to unrelated endpoints queue behind
the blocked ones, because they share a thread pool. One slow dependency degrades everything.

**The last arrow closes a positive feedback loop.** Removing an instance sends its traffic to the
survivors, which pushes them over the same edge. This is how a partial degradation becomes a total
outage in under a minute.

<Callout type="pitfall" title="Most clients default the read timeout to unlimited">
`RestTemplate`, `RestClient` and most HTTP clients default to no read timeout. A dependency that
accepts your connection and then never responds will hold that thread until the OS gives up — which
can be minutes.

An unbounded wait is the single most common cause of the cascade above. Every remote call needs an
explicit timeout, and "the default is probably fine" is how you find out it was not.
</Callout>

## Retry amplification

Retries are the countermeasure that most reliably makes an outage worse.

A service is struggling at 100% capacity. Every client retries three times. The service now receives
**three times** the traffic at precisely the moment it has least capacity to serve it. It cannot
recover, because recovery requires load to drop, and the retries guarantee it will not.

Add a layer and the arithmetic gets worse:

Three layers, three retries each, and one user request becomes twenty-seven at the bottom of the
stack. That is a self-inflicted denial of service, and it is why the retry lesson later in this
module spends most of its time on when *not* to.

## Thundering herds

Failures synchronise things that were previously spread out, and the synchronised recovery is often
worse than the failure.

- **Cache expiry.** A popular key expires and every in-flight request misses at once — the stampede
  from [module 04](/learn/data/caching-redis).
- **Reconnection.** A broker restarts and 500 consumers reconnect in the same second.
- **Scheduled work.** Every service runs its cleanup job at `0 0 * * *`, so the database gets a
  synchronised spike at midnight.
- **Retry alignment.** Clients that failed together retry together, at exactly the same backoff
  interval, forever.

The fix for all four is the same one word: **jitter**. Randomising a delay by ±30% breaks the
synchronisation, and it costs nothing.

```java
// Every client retries at exactly 1s, then 2s, then 4s — in lockstep.
Duration delay = Duration.ofMillis(1000L << attempt);

// Spread across a window, so the load arrives smeared rather than as a spike.
long base = 1000L << attempt;
Duration delay = Duration.ofMillis(base / 2 + ThreadLocalRandom.current().nextLong(base));
```

Every cascade ends at a bounded resource. Knowing which one tells you where to put the limit.

<Callout type="prod">
Virtual threads change the first row and not the others. With
[virtual threads](/learn/web-rest/reactive-intro) the thread pool stops being the binding constraint —
but the connection pool, memory and the downstream service still are.

Worse, the failure gets quieter: instead of failing fast on thread exhaustion, the service
accumulates a large queue of cheap waiting threads and degrades gradually. You still need explicit
bounds; you have just removed the one that used to enforce them accidentally.
</Callout>

people who would never write the database version.

## Designing for partial failure

The shift is from "did it work?" to "what do I do when part of it did not?"

<Compare>
  <Bad title="All or nothing">

One unavailable dependency means the whole page fails, including the eight parts that were fine.
Recommendations are a nice-to-have, and here they can take down the product page.

```java
public ProductPage page(UUID productId) {
    Product product = catalogClient.get(productId);
    Stock stock = inventoryClient.check(productId);
    List<Review> reviews = reviewClient.forProduct(productId);
    List<Product> recommended = recommendationClient.forProduct(productId);

    return new ProductPage(product, stock, reviews, recommended);
}
```

  </Bad>
  <Good title="Degrade by criticality">

The product is essential — if that fails, the request fails. Everything else has a defined
degradation, and the response says what is missing so the client can render honestly.

```java
public ProductPage page(UUID productId) {
    // Essential: no product, no page.
    Product product = catalogClient.get(productId);

    // Important, but a stale or unknown value beats an error page.
    Stock stock = attempt(() -> inventoryClient.check(productId))
            .orElse(Stock.unknown());

    // Optional: absent is a perfectly good answer.
    List<Review> reviews = attempt(() -> reviewClient.forProduct(productId))
            .orElse(List.of());
    List<Product> recommended = attempt(() -> recommendationClient.forProduct(productId))
            .orElse(List.of());

    return new ProductPage(product, stock, reviews, recommended,
            // Tell the client what is missing rather than pretending it is empty.
            degradedSections(stock, reviews, recommended));
}
```

  </Good>
</Compare>

The classification is the design work, and it is a product decision rather than a technical one.
Before writing any resilience code, get the list: for each dependency, is it **essential**
(fail the request), **important** (degrade visibly), or **optional** (omit silently)?

<Callout type="tip" title="Say what is missing">
Returning an empty reviews list when the review service is down is a lie — the client cannot
distinguish "no reviews" from "we could not load reviews". Include a degradation marker in the
response so the UI can show "Reviews unavailable" instead of "Be the first to review".
</Callout>
