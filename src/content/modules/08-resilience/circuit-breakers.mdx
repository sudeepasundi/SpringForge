When a dependency is failing, continuing to call it is worse than useless. Each call waits for a
timeout, holds a resource, and adds load to a service that is already struggling.

A circuit breaker notices the failure rate and stops calling for a while.

The value is in the **open** state. Failing in microseconds instead of waiting five seconds for a
timeout means the thread is returned immediately, so the cascade from the previous lesson never
starts. You have converted a slow failure into a fast one, which is the entire point.

## Configuration that reflects reality

```yaml title="application.yml"
resilience4j:
  circuitbreaker:
    configs:
      default:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 50                 # decide on 50 calls, not 5
        minimum-number-of-calls: 20             # do not judge before there is evidence
        failure-rate-threshold: 50              # percent
        slow-call-duration-threshold: 2s
        slow-call-rate-threshold: 80            # slow counts as failed — see below
        wait-duration-in-open-state: 10s
        permitted-number-of-calls-in-half-open-state: 5
        automatic-transition-from-open-to-half-open-enabled: true
        # A timeout is a failure; a 404 is an answer.
        record-exceptions:
          - java.io.IOException
          - java.util.concurrent.TimeoutException
          - org.springframework.web.client.HttpServerErrorException
        ignore-exceptions:
          - dev.springforge.shopflow.catalog.ProductNotFoundException
    instances:
      catalog:
        base-config: default
      payment:
        base-config: default
        failure-rate-threshold: 30              # money: trip earlier
        wait-duration-in-open-state: 30s
```

Four of those settings carry most of the behaviour.

**`minimum-number-of-calls`** stops a breaker tripping on two failures during a quiet period. Without
it, a low-traffic endpoint opens constantly on statistically meaningless samples.

**`slow-call-rate-threshold`** is the one people omit and then regret. A dependency answering
successfully in eight seconds is not failing by any error-rate measure, and it is still destroying
you. Counting slow calls as failures is what makes a breaker useful against the most dangerous case
from the previous lesson.

**`ignore-exceptions`** is essential for correctness. A `404` means the dependency is healthy and
answered your question. Counting business outcomes as failures trips the breaker during normal
operation and teaches everyone to distrust it.

**`wait-duration-in-open-state`** is a guess about recovery time. Ten seconds is a reasonable default;
for a dependency that restarts slowly, longer is better than flapping.

<Callout type="pitfall" title="Do not put a breaker on everything">
A circuit breaker has state, a sliding window, and a failure mode of its own — a misconfigured one
opens under normal load and creates the outage it was meant to prevent.

Use them for **remote calls that can fail slowly**. Do not wrap local method calls, cache lookups, or
anything already fast-failing. Each breaker is a thing to tune and monitor, and a fleet of untuned
breakers is worse than none.
</Callout>

## Fallbacks that degrade rather than lie

```java title="order/CatalogClient.java" {6,17,25}
@Component
public class CatalogClient {

    private final RestClient client;
    private final ProductNameRepository localNames;   // event-fed projection

    @CircuitBreaker(name = "catalog", fallbackMethod = "fromLocalProjection")
    @Retry(name = "catalog")                          // retry sits inside the breaker
    public ProductView byId(UUID productId) {
        return client.get()
                .uri("/api/products/{id}", productId)
                .retrieve()
                .body(ProductView.class);
    }

    /**
     * Fallback signature: the same parameters, plus the exception, and the same
     * return type. Getting this wrong fails at runtime, not compile time.
     */
    ProductView fromLocalProjection(UUID productId, Exception cause) {
        log.warn("Catalog unavailable, serving projection for {}", productId, cause);

        return localNames.find(productId)
                .map(ProductView::stale)              // marked stale for the caller
                .orElseThrow(() -> new CatalogUnavailableException(productId, cause));
    }
}
```

Three things about that fallback are deliberate.

**It serves data the service already owns** — the projection from
[module 07](/learn/microservices-fundamentals/communication-styles) — rather than inventing a value.

**It marks the result stale** so the caller knows it is not current, instead of silently presenting
old data as fresh.

**It still throws when it has nothing.** A fallback with no good answer must fail; returning an empty
or default object is how a temporary outage becomes permanently wrong data written back to a
database.

## Ordering: retry inside, breaker outside

Resilience4j applies its decorators in a defined order, and the default is the one you want:

```text
Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( call ) ) ) ) )
```

Read from the inside out: a bulkhead limits concurrency, a time limiter bounds duration, a rate
limiter caps throughput, the breaker decides whether to attempt at all, and retry re-runs the whole
thing.

The consequence worth understanding: **when the breaker is open, retries fail instantly.** Three
retry attempts against an open breaker cost microseconds, not fifteen seconds. If the order were
reversed, every retry would test the dependency and the breaker would never protect you.

<Callout type="prod">
The composition also means retry counts are multiplied by the breaker's sliding window. Three retries
per request means one user request contributes up to three failures to the window — so a
`sliding-window-size` of 50 is really about 17 requests. Size the window in requests you expect, not
in calls.
</Callout>

## Watch it, or it will surprise you

A breaker that opens silently is a service that got quietly slower for reasons nobody can see.

```java title="support/CircuitBreakerMetrics.java" {8-13}
@Component
class CircuitBreakerEvents {

    private static final Logger log = LoggerFactory.getLogger(CircuitBreakerEvents.class);

    CircuitBreakerEvents(CircuitBreakerRegistry registry, MeterRegistry meters) {
        registry.getAllCircuitBreakers().forEach(breaker -> {
            breaker.getEventPublisher().onStateTransition(event -> {
                // A state transition is an operational event, not a debug detail.
                log.warn("Circuit breaker {} moved {} → {}",
                        event.getCircuitBreakerName(),
                        event.getStateTransition().getFromState(),
                        event.getStateTransition().getToState());
                meters.counter("circuitbreaker.transitions",
                        "name", event.getCircuitBreakerName(),
                        "to", event.getStateTransition().getToState().name()).increment();
            });
        });
    }
}
```

Two alerts are worth having: **a breaker open for longer than a minute** (the dependency is properly
down, not blipping), and **a breaker that flaps** between open and half-open repeatedly, which means
`wait-duration-in-open-state` is shorter than the dependency's recovery time.

Resilience4j also publishes `resilience4j.circuitbreaker.state` to Micrometer, so a dashboard panel
per breaker takes minutes.

## Testing it

A breaker you have never seen open is a configuration you are guessing at.

```java title="order/CatalogClientCircuitBreakerTest.java" {12,18,25}
@SpringBootTest
class CatalogClientCircuitBreakerTest {

    @Autowired CatalogClient client;
    @Autowired CircuitBreakerRegistry registry;

    @Test
    void opens_after_the_failure_threshold_and_then_fails_fast() {
        CircuitBreaker breaker = registry.circuitBreaker("catalog");
        stubCatalogToFail();

        // Drive it past minimum-number-of-calls and the failure rate.
        for (int i = 0; i < 20; i++) {
            assertThatThrownBy(() -> client.byId(UUID.randomUUID()));
        }

        assertThat(breaker.getState()).isEqualTo(CircuitBreaker.State.OPEN);

        // The point of the breaker: the next call does not touch the network.
        long start = System.nanoTime();
        assertThatThrownBy(() -> client.byId(UUID.randomUUID()));
        assertThat(Duration.ofNanos(System.nanoTime() - start)).isLessThan(Duration.ofMillis(50));

        // And no further requests reached the dependency.
        verifyNoMoreCatalogRequests();
    }
}
```

The last two assertions are the ones that matter. Checking the state proves the counting works;
checking that the call was fast and never reached the dependency proves the breaker is doing its
actual job.
