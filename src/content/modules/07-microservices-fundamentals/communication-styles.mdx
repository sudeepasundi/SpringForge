How two services talk decides how they fail together. That is the whole lesson: the choice looks
like a technical preference and is actually a decision about coupling and availability.

## Availability multiplies

A service that synchronously calls three dependencies cannot be more available than all of them
combined.

The arithmetic is unforgiving and it is why "just add a service call" is never neutral. Two mitigations
exist: remove the hop (own the data, as the previous lesson argued), or remove the *dependency* on
the hop succeeding right now — which is what asynchronous messaging buys you.

The distinction between a command and an event is worth being precise about, because it decides who
owns a business rule.

```java
// Command: the sender decides what should happen. The receiver's job is to obey.
// Coupling: order-service knows inventory-service exists and what it should do.
inventory.send(new ReserveStock(orderId, items));

// Event: the sender states what happened. Who reacts, and how, is not its business.
// Coupling: order-service knows nothing about inventory at all.
events.publish(new OrderPlaced(orderId, items, placedAt));
```

Events invert the dependency. With `OrderPlaced`, adding a fraud check means deploying a new
consumer — the order service does not change, does not redeploy, and does not know. That property is
the main reason event-driven architectures scale organisationally.

<Callout type="pitfall" title="A command dressed as an event">
`OrderPlacedSoReserveStock` is a command with an event's name. So is any event whose payload exists
purely to tell one specific consumer what to do.

The test: **could you add a second consumer without changing the event?** If the event only makes
sense to one recipient, it is a command, and you should call it one — pretending otherwise hides the
coupling rather than removing it.
</Callout>

## When synchronous is right

Async is not automatically better. Synchronous calls are correct when:

- **The caller genuinely needs the answer to continue.** A price quote, an authorisation check,
  validation before accepting a request.
- **The user is waiting.** Nobody wants "we will let you know whether your search worked".
- **The operation must be rejected on failure.** Eventual consistency is wrong when the answer is
  "no, and the request should fail".

The mistake is not using synchronous calls. It is using them for things that could have been
asynchronous — notifications, analytics, downstream side effects — and thereby coupling your
availability to services you did not need to wait for.

<Compare>
  <Bad title="Everything synchronous">

The request takes as long as the slowest dependency and fails if any of them is down — including the
email service, which the customer does not need in order to have an order.

```java
@Transactional
public OrderResponse place(PlaceOrderRequest request) {
    Order order = repository.save(Order.from(request));

    inventoryClient.reserve(order.id(), order.items());   // needed: reject if no stock
    paymentClient.authorise(order.id(), order.total());   // needed: reject if declined
    emailClient.sendConfirmation(order);                  // not needed to place the order
    analyticsClient.track("order_placed", order.id());    // definitely not needed
    searchClient.index(order);                            // not needed

    return OrderResponse.from(order);
}
```

  </Bad>
  <Good title="Synchronous only where the answer changes the outcome">

Two calls decide whether the order can be placed, so they stay synchronous. Everything else reacts
to an event after commit — and none of it can fail the request or slow it down.

```java
@Transactional
public OrderResponse place(PlaceOrderRequest request) {
    inventoryClient.reserve(request.items());             // must succeed or reject
    paymentClient.authorise(request.total());             // must succeed or reject

    Order order = repository.save(Order.from(request));
    events.publish(new OrderPlaced(order.id(), order.items(), order.total()));

    return OrderResponse.from(order);
}
```

Email, analytics and search each subscribe to `OrderPlaced`. Adding a sixth consumer changes nothing
here.

  </Good>
</Compare>

<Callout type="prod">
Note where the two synchronous calls sit: **before** the local write, not after. If `authorise`
throws, nothing has been persisted. Doing it the other way round leaves an order row with no payment
and a transaction that has already committed the row before the failure — the dual-write problem that
module 09 is largely about.
</Callout>

## Surviving a downstream outage

The read path is where this bites hardest, and it has a good answer: keep a local copy.

```java title="order/ProductNames.java — a projection, not a cache"
@Component
class ProductNames {

    private final ProductNameRepository repository;   // our own table

    // Kept current by catalog's events. No runtime dependency on catalog at all.
    @KafkaListener(topics = "catalog.product-events")
    void onProductEvent(ProductEvent event) {
        switch (event) {
            case ProductRenamed(UUID id, String name) -> repository.upsert(id, name);
            case ProductDiscontinued(UUID id) -> repository.markDiscontinued(id);
            default -> { }
        }
    }

    String nameOf(UUID productId) {
        return repository.findName(productId).orElse("Unknown product");
    }
}
```

The difference from a cache matters. A cache is a copy of something you would otherwise fetch — a
miss means a synchronous call. A projection is **data you own**, kept current by events, with no
fallback path to the other service. If catalog is down for an hour, your order list keeps working
and simply does not learn about renames until it recovers.

## What asynchrony costs

It is not free, and the costs are real enough to be worth stating plainly.

- **Eventual consistency.** The user places an order and the confirmation email arrives two seconds
  later. Usually fine — but "usually" needs checking with the business, not assumed.
- **Read-after-write surprises.** A user updates their profile and the next screen shows the old
  value because it reads a projection that has not caught up. Design for it: return the new value
  from the write, or read your own writes from the authoritative source.
- **Debugging is harder.** A synchronous failure has a stack trace. An asynchronous one has a
  message that stopped somewhere, and you need tracing across the broker to find where.
- **Broker operations.** Kafka is another system to run, monitor, upgrade and reason about.
- **Ordering and duplicates.** At-least-once delivery means consumers must be idempotent, and
  ordering is only guaranteed within a partition. Module 09 covers both properly.

<Callout type="tip" title="The decision, compressed">
**Does the caller need the answer to decide what to do next?** Yes → synchronous. No → event.

That single question resolves most cases correctly, and the ones it does not — a command that must
be reliably delivered but not waited on — are usually async commands.
</Callout>
