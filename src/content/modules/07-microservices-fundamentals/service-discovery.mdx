Instances come and go — deployments replace them, autoscaling adds them, crashes remove them. Their
addresses are not knowable in advance, so something has to answer "where is order-service right
now?"

There are two families of answer, and on Kubernetes there is a good chance you already have one and
do not need the other.

<Callout type="tip" title="On Kubernetes you probably do not need Eureka">
A Kubernetes `Service` gives you a stable DNS name, health-based endpoint management, and load
balancing — the whole problem, solved by the platform, with nothing in your application.

Running Eureka on top means operating a registry, embedding a client in every service, and
maintaining two sources of truth about which instances are alive. They will disagree during a
rollout.

Eureka earns its place when you are **not** on a platform that solves this — VMs, ECS without
service discovery, a hybrid estate — or when you need client-side load balancing specifically.
</Callout>

## Eureka, when you need it

```yaml title="order-service/application.yml"
spring:
  application:
    name: order-service          # this becomes the registry key

eureka:
  client:
    service-url:
      defaultZone: http://eureka-1:8761/eureka/,http://eureka-2:8761/eureka/
  instance:
    prefer-ip-address: true      # containers rarely have resolvable hostnames
    lease-renew-interval-in-seconds: 10       # heartbeat
    lease-expiration-duration-in-seconds: 30  # evict after three missed beats
```

Then call by name rather than by address:

```java title="order/CatalogClient.java" {4,10}
@Configuration
class ClientConfig {

    @Bean
    @LoadBalanced                       // teaches RestClient to resolve lb:// names
    RestClient.Builder loadBalancedBuilder() {
        return RestClient.builder();
    }

    @Bean
    RestClient catalogClient(RestClient.Builder builder) {
        return builder.baseUrl("http://catalog-service").build();   // a registry key, not a host
    }
}
```

## The stale registration problem

This is the failure mode that surprises people, and it is inherent to heartbeat-based registries.

An instance dies. The registry does not know until it misses enough heartbeats — with the settings
above, up to 30 seconds. Meanwhile clients hold a cached copy of the registry, refreshed on their own
schedule, so they may keep the dead address for **another** 30 seconds after eviction.

You cannot eliminate the window, so design for it:

- **Deregister gracefully on shutdown.** Spring Boot sends a deregistration on a clean shutdown, so
  a rolling deploy skips the heartbeat delay entirely. It only helps for graceful termination — a
  crash still takes the full window.
- **Retry on a different instance.** A connection refused should be retried against the next
  address, not surfaced. Spring Cloud LoadBalancer does this when configured.
- **Circuit-break per instance**, so a dead one is skipped quickly rather than tried on every
  request. That is module 08.

<Callout type="pitfall" title="Do not tighten the heartbeat to fix this">
Cutting the lease interval to 2 seconds cuts the detection window and multiplies registry traffic —
with 200 instances that is 100 heartbeats a second, and the registry becomes a bottleneck whose own
failure is far worse than a stale entry.

Detection is the wrong lever. **Handle the failure at the caller**, where a retry costs one request
rather than loading a shared component.
</Callout>

## Client-side load balancing

Once the caller has the list, it chooses. The default is round robin, which is fine until instances
are not equivalent.

```java title="order/LoadBalancerConfig.java"
@Configuration
@LoadBalancerClient(name = "catalog-service", configuration = CatalogLoadBalancerConfig.class)
class LoadBalancerConfig { }

class CatalogLoadBalancerConfig {

    /**
     * Round robin assumes every instance is equally able to serve the next
     * request, which stops being true the moment one is slow or cold.
     */
    @Bean
    ReactorLoadBalancer<ServiceInstance> loadBalancer(Environment environment,
                                                      LoadBalancerClientFactory factory) {
        String name = environment.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
        return new RandomLoadBalancer(
                factory.getLazyProvider(name, ServiceInstanceListSupplier.class), name);
    }
}
```

```yaml title="Zone awareness: prefer instances in the caller's own zone"
spring:
  cloud:
    loadbalancer:
      configurations: zone-preference
      health-check:
        initial-delay: 10s
        interval: 15s          # active health checks, not just registry state
eureka:
  instance:
    metadata-map:
      zone: eu-west-1a
```

Zone preference is the setting with the clearest payoff: cross-zone traffic costs latency and, on
most cloud providers, money. Keeping calls in-zone while still failing over across zones is close to
free.

## Configuration for the two worlds

The same service should run in both, which is a profile concern rather than a code one:

```yaml title="application.yml — platform discovery, the default"
spring:
  cloud:
    discovery:
      enabled: false          # Kubernetes DNS resolves service names
    kubernetes:
      discovery:
        enabled: true

---
spring:
  config:
    activate:
      on-profile: vm          # no platform discovery available here
  cloud:
    discovery:
      enabled: true
eureka:
  client:
    enabled: true
    service-url:
      defaultZone: ${EUREKA_URL}
```

<Callout type="prod">
Whichever mechanism you use, the readiness probe is what actually protects you. A registry or
endpoint list only knows what the instance reports, so an instance that reports ready before its
connection pool is warm will receive traffic it cannot serve.

Make readiness mean "I can serve a real request" —
[module 02](/learn/boot-essentials/actuator-logging) covers what belongs in it — and discovery
becomes far less interesting, because instances stop being registered when they cannot work.
</Callout>
