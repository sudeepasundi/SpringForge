Without a gateway, every client needs to know every service's address, implement authentication
against each one, and make six calls to render one screen. A gateway is the single front door that
removes all three problems — and, if you are careless, becomes the shared component that couples
every team together.

The split in that diagram is the important one. **Authentication at the edge, authorisation in the
service.** The gateway can verify a token cryptographically without knowing anything about your
domain. It cannot know whether this user may cancel that particular order — that requires the order,
and the order lives in the service.

## Spring Cloud Gateway

Configuration-first for the common cases:

```yaml title="gateway/application.yml"
spring:
  cloud:
    gateway:
      default-filters:
        - DedupeResponseHeader=Access-Control-Allow-Origin, RETAIN_UNIQUE
      routes:
        - id: orders
          uri: lb://order-service            # lb: → resolved via service discovery
          predicates:
            - Path=/api/orders/**
          filters:
            - name: CircuitBreaker
              args:
                name: orders
                fallbackUri: forward:/fallback/orders
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 20     # steady state, per key
                redis-rate-limiter.burstCapacity: 40     # allowance for bursts
                key-resolver: "#{@userKeyResolver}"

        - id: catalog
          uri: lb://catalog-service
          predicates:
            - Path=/api/catalog/**
          filters:
            # Catalog data is public and changes rarely — cache it at the edge.
            - name: LocalResponseCache
              args:
                timeToLive: 60s
                size: 50MB
```

The rate limiter needs a key, and the choice of key is a policy decision:

```java title="gateway/RateLimitConfig.java" {6-9}
@Bean
KeyResolver userKeyResolver() {
    return exchange -> exchange.getPrincipal()
            .filter(JwtAuthenticationToken.class::isInstance)
            .map(principal -> ((JwtAuthenticationToken) principal).getToken().getSubject())
            // Fall back to the IP for unauthenticated traffic. Note this punishes
            // everyone behind a shared NAT, so keep the anonymous limit generous
            // and the authenticated limit tight.
            .switchIfEmpty(Mono.just(clientIp(exchange)))
            .map(Objects::toString);
}
```

<Callout type="pitfall" title="Spring Cloud Gateway is reactive">
It is built on WebFlux and Netty. **Any blocking call in a custom filter stalls an event-loop
thread** and, with it, every other request assigned to that loop — the failure mode from
[module 03](/learn/web-rest/reactive-intro), concentrated at your single front door.

A JDBC lookup, a blocking HTTP client, or a synchronous cache call in a filter will not throw. It
will quietly halve your throughput under load. Everything in a gateway filter must be reactive.
</Callout>

## Keeping the gateway thin

The gateway is shared by every team. Every rule you put in it is a change that must be coordinated,
tested and deployed centrally — so the question for anything you are about to add is: *does this
genuinely need to be here?*

<Compare>
  <Bad title="Business logic at the edge">

Discount rules now live in the gateway. Changing them means a gateway deploy, which risks every
service. The pricing team does not own the code that implements their rules, and nobody can test
this in isolation.

```java
@Component
public class DiscountFilter implements GlobalFilter {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String tier = exchange.getRequest().getHeaders().getFirst("X-Customer-Tier");
        if ("GOLD".equals(tier)) {
            exchange.getAttributes().put("discount", new BigDecimal("0.15"));
        } else if ("SILVER".equals(tier)) {
            exchange.getAttributes().put("discount", new BigDecimal("0.10"));
        }
        return chain.filter(exchange);
    }
}
```

  </Bad>
  <Good title="Cross-cutting concerns only">

The gateway propagates identity and correlation. What a GOLD customer is entitled to is a pricing
decision, owned and deployed by the pricing service.

```java
@Component
public class CorrelationFilter implements GlobalFilter, Ordered {

    static final String TRACE_HEADER = "X-Request-Id";

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String requestId = Optional
                .ofNullable(exchange.getRequest().getHeaders().getFirst(TRACE_HEADER))
                .orElseGet(() -> UUID.randomUUID().toString());

        ServerHttpRequest mutated = exchange.getRequest().mutate()
                .header(TRACE_HEADER, requestId)
                .build();

        exchange.getResponse().getHeaders().add(TRACE_HEADER, requestId);
        return chain.filter(exchange.mutate().request(mutated).build());
    }

    @Override
    public int getOrder() {
        return Ordered.HIGHEST_PRECEDENCE;   // before anything that might log
    }
}
```

  </Good>
</Compare>

<Callout type="prod">
A gateway is a single point of failure by construction, so treat it accordingly: run at least three
replicas, keep its own dependencies minimal (a Redis outage should degrade rate limiting, not reject
traffic), and give it a stricter deployment process than your services. When the gateway is down,
everything is down.
</Callout>

## Aggregation, and why to be wary

The tempting next step is to have the gateway call three services and merge the responses, so mobile
makes one request instead of three. It works, and it has a cost: the gateway now knows the shape of
three services' responses, and a change to any of them can break it.

The backend-for-frontend is the pattern worth knowing. It is an aggregation service owned by the team
that owns the client — mobile's BFF is deployed by the mobile team, on their schedule, and its
coupling to three services is *their* problem rather than everyone's.

## What a gateway is not

Two clarifications that save architectural arguments:

**Not a service mesh.** A gateway handles north–south traffic — clients into the system. A mesh
handles east–west traffic — services talking to each other. They solve different problems and many
systems run both.

**Not always necessary.** If you are running on Kubernetes with an ingress controller, you already
have TLS termination, routing and often rate limiting. Adding Spring Cloud Gateway on top is a second
hop and a second thing to operate. Add it when you need something the ingress cannot do — token
validation, request transformation, per-route circuit breaking — not by default.
