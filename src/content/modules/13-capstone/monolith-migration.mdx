The rewrite is the most reliably catastrophic decision in software. It takes eighteen months, the
business freezes features for the duration, the new system reaches 80% of the old one's behaviour,
and the last 20% — the accumulated special cases that are the actual business — turns out to be the
hard part.

The strangler fig pattern is the alternative: extract one piece at a time, with the old system
running throughout.

## The pattern

A strangler fig grows around a host tree, gradually taking over until the host is gone. The
architectural version puts a routing layer in front, then moves one capability at a time behind it.

The property that makes it work: **at every point, the system is deployable and the last step is
reversible.** A rewrite has no such point until the end.

## What to extract first

Not the most valuable thing. The thing that teaches you the most for the least risk.

**The first extraction is a rehearsal.** Its purpose is to build the facade, the deployment pipeline,
the observability and the team's confidence. Pick something where getting it wrong is embarrassing
rather than expensive.

## The sequence, per capability

<Steps>
  <Step title="Put the facade in front, routing everything to the monolith">

Nothing changes behaviourally. Deploy it, watch it, and confirm the monolith is unaffected. You now
have the mechanism you need for every subsequent step.

```yaml title="Everything still goes to the monolith"
spring:
  cloud:
    gateway:
      routes:
        - id: monolith
          uri: http://monolith:8080
          predicates:
            - Path=/**
```

  </Step>
  <Step title="Build the new service, and dual-write to it">

The new service is written to but never read from. Its data is built up in parallel while the
monolith remains authoritative.

```java title="In the monolith — temporary, and clearly labelled"
@Transactional
public Product updateProduct(UUID id, UpdateProductCommand command) {
    Product product = repository.save(applyUpdate(id, command));

    // Dual-write during extraction. Failures are logged, never thrown:
    // the new service must not be able to break the system of record.
    try {
        catalogServiceClient.upsert(ProductDto.from(product));
    } catch (Exception e) {
        log.warn("Catalog dual-write failed for {}; reconciliation will fix it", id, e);
        migrationMetrics.dualWriteFailure("catalog");
    }
    return product;
}
```

  </Step>
  <Step title="Backfill and reconcile">

Backfill history into the new service, then run a continuous comparison until the divergence rate is
zero for long enough to trust it.

```java title="The check that decides whether you can proceed"
@Scheduled(cron = "0 */15 * * * *")
void reconcile() {
    List<Divergence> divergences = comparator.compare(
            monolithRepository.findAllSummaries(),
            catalogClient.findAllSummaries());

    // Not "did the backfill run" but "do the two agree, right now".
    migrationMetrics.divergenceCount("catalog", divergences.size());
    divergences.forEach(d -> log.warn("Catalog divergence: {}", d));
}
```

  </Step>
  <Step title="Shadow-read: call both, serve the old, compare">

Reads go to both systems. The monolith's answer is returned; the new service's answer is compared
and any difference recorded. This is where the subtle bugs surface — rounding, sort order, null
handling, timezone.

```java
public ProductView get(UUID id) {
    ProductView authoritative = monolith.get(id);

    // Fire-and-forget: a shadow read must never affect the response.
    shadowExecutor.execute(() -> {
        try {
            ProductView candidate = catalogClient.get(id);
            if (!candidate.equalsIgnoringMetadata(authoritative)) {
                migrationMetrics.shadowMismatch("catalog", "get");
                log.warn("Shadow mismatch for {}: {} vs {}", id, authoritative, candidate);
            }
        } catch (Exception ignored) { /* never affects the caller */ }
    });

    return authoritative;
}
```

  </Step>
  <Step title="Move reads, a percentage at a time">

Only once the shadow mismatch rate has been zero for days. Move 1%, then 10%, then 50%, then all —
watching error rate and latency at each step, ready to route back instantly.

```yaml
- id: catalog-reads
  uri: lb://catalog-service
  predicates:
    - Path=/api/catalog/**
    - Method=GET
    - Weight=catalog-group, 10        # 10% here, 90% to the monolith
```

  </Step>
  <Step title="Move writes, then remove the old path">

Writes last, because they are the irreversible half. Once they have moved and been stable, delete the
monolith's implementation — and only then the dual-write code.

  </Step>
</Steps>

<Callout type="prod">
Steps 3 and 4 are where the value is, and they are the ones under schedule pressure people skip.

A shadow-read period that finds nothing is not wasted — it is the evidence that lets you move
traffic without holding your breath. Skipping it means the first real divergence is discovered by a
customer.
</Callout>

## The hard part is the data

Code extraction is mechanical. Untangling a shared database is the actual project.

<Compare>
  <Bad title="A join across the new boundary">

The monolith joins `orders` to `products`. Extracting catalog breaks this query, and it is one of
several hundred.

```sql
select o.id, o.placed_at, p.name, p.price
from orders o
join products p on p.id = o.product_id
where o.customer_id = ?;
```

  </Bad>
  <Good title="Denormalise at write time">

The order stores what it needs at the moment it is placed. The join disappears — and the result is
more correct, because an order should show the price it was placed at, not today's.

```sql
alter table orders add column product_name varchar(300);
alter table orders add column product_price_minor bigint;

-- Backfill from the current join, then populate on write from then on.
update orders o
set product_name = p.name, product_price_minor = p.price_minor
from products p
where p.id = o.product_id and o.product_name is null;
```

  </Good>
</Compare>

Four techniques, in the order you should reach for them:

<DecisionTable
  columns={['How', 'When']}
  rows={[
    {
      label: 'Denormalise at write time',
      verdict: 'good',
      cells: ['Copy the fields you need onto your own row', 'Almost always — and often more correct'],
    },
    {
      label: 'Event-fed projection',
      verdict: 'good',
      cells: ['Subscribe and keep a local read model', 'You need to filter or sort by the other side’s data'],
    },
    {
      label: 'API composition',
      verdict: 'mixed',
      cells: ['Fetch and join in application code', 'Small result sets, non-critical path'],
    },
    {
      label: 'A shared read replica',
      verdict: 'bad',
      cells: ['Both read the same tables', 'A transitional crutch only — set a date to remove it'],
    },
  ]}
/>

The last row deserves a warning. A "temporary" shared replica removes the pressure to finish the
extraction, and it will still be there in three years, with two services now depending on a schema
neither owns.

## What goes wrong

<Callout type="pitfall" title="Extracting a service that still shares the database">
The most common failed migration: the code is split into six services and they all point at the
original schema. You now have every cost of distribution — network calls, no shared transaction,
deployment coordination — plus a schema no service owns and every team must agree to change.

This is worse than the monolith you started with. **The database boundary is the service boundary.**
If the data has not moved, the service has not been extracted.
</Callout>

<Callout type="pitfall" title="Stopping halfway, permanently">
The strangler pattern's honest risk is that the residual monolith is always the hardest part, and
there is always something more urgent. Teams end up maintaining a monolith *and* eight services —
the operational cost of both.

Two defences: sequence the extractions so the residue shrinks meaningfully each time, and decide
explicitly whether the endpoint is "no monolith" or "a small monolith plus these services". The
second is a legitimate destination; drifting into it is not.
</Callout>
