Three structural decisions are visible in that picture:

- **Every service owns its database.** No shared schema, no cross-service reads — the rule from
  [module 07](/learn/microservices-fundamentals/decomposition).
- **Services communicate with events, not calls.** The availability arithmetic from
  [module 07](/learn/microservices-fundamentals/communication-styles) means four synchronous hops at
  99.9% each would cap the system at 99.6%.
- **order-service keeps a projection of catalog.** Catalog can be down for an hour and the order list
  keeps working.

The shape worth noticing: **the response is returned at step 6, before any of the cross-service work
has happened.** The order is `PENDING` — a promise, not a fact — and the client is told so. That is
what lets checkout stay fast and available while the coordination happens behind it.

## When payment declines

The path that matters more, because it is the one that exercises the design.

<Mermaid
  caption="Compensation runs backwards through the steps that completed. Nothing irreversible has happened yet — that is by construction."
  alt="Sequence diagram of a declined payment: payment publishes PaymentFailed, the saga enters compensating, inventory releases the stock, and the order is cancelled."
  chart={`
sequenceDiagram
    participant P as payment
    participant K as Kafka
    participant O as order-service
    participant I as inventory
    participant C as Client

    P->>K: PaymentFailed(card_declined)
    K->>O: saga → COMPENSATING
    Note over O: Compensate completed steps,<br/>in reverse order.
    O->>K: ReleaseStock
    K->>I: consume
    I->>I: releaseIfReserved (idempotent)
    I->>K: StockReleased
    K->>O: fully compensated
    O->>O: order → CANCELLED

    Note over O,C: Shipping was never reached,<br/>so nothing irreversible occurred.
    O-->>C: webhook / poll: CANCELLED
`}
/>

<Callout type="prod">
The reason this is safe is the step ordering, decided long before any code was written: **reserve
stock (reversible) → capture payment (reversible via refund) → ship (irreversible)**.

Reverse the first and last and a declined payment leaves you with a parcel already collected and no
way to unsend the dispatch email. The ordering is the design; the compensation code is just what
implements it.
</Callout>

## What this design costs

A capstone that only lists benefits is a sales pitch. The honest accounting:

<Compare>
  <Bad title="What you have given up">

Every one of these was free in a monolith.

```text
- Placing an order is no longer one transaction. It is a saga with
  five states, compensations, and a stuck-saga sweep.

- "Why is this order PENDING?" requires a distributed trace, not a
  stack trace.

- The order list shows product names that may be seconds stale.

- Six deployment pipelines, six sets of dashboards, six on-call
  surfaces, and a Kafka cluster to operate.

- Changing a shared event shape is a two-release dance across teams.
```

  </Bad>
  <Good title="What you bought">

Each is something a single deploy unit genuinely cannot provide.

```text
- Teams deploy independently. The payment team ships without
  coordinating with anyone.

- A catalog outage degrades the order list; it does not stop checkout.

- Payment is in PCI scope on its own; nothing else is dragged in.

- Inventory can scale to 20 instances at peak while catalog stays at 3.

- A memory leak in shipping cannot take down checkout.
```

  </Good>
</Compare>

<Callout type="pitfall" title="For most systems, this is the wrong architecture">
ShopFlow is a teaching artefact: it is deliberately distributed so that every pattern has somewhere
to live. A real business at this scale should almost certainly build the modular monolith from
[module 07](/learn/microservices-fundamentals/why-microservices) and extract only when a specific
module gives a specific reason.

The value of having read this is knowing what the distributed version costs — so that when someone
proposes it, you can price the proposal rather than agree with it.
</Callout>

## Reading it yourself

The whole project is on the [demos page](/demos), 21 files across six services. Two paths through it:

**Follow one order.** `OrderService.place` → `DomainEvents.publish` → `OutboxRelay.publishPending`
→ `StockConsumer.onReserveStock` → `OrderSaga.onStockReserved` → `PaymentService.charge` →
`ShipmentConsumer.onOrderConfirmed`. That is the entire happy path, and it is seven methods.

**Follow one failure.** Start at `OrderSaga.onPaymentFailed` and trace the compensation backwards.
That path is shorter and tells you more about whether the design holds.
